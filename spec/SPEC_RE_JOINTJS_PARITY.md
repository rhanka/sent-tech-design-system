## 2. Enumeration method and completeness guard

"100 %" is defined mechanically and only over the parity denominator. `tools/re-jointjs/enumerate.mjs` (primary extractor, TypeScript AST via `ts.createSourceFile`) extracts raw items from the pinned sources under the conventions below; every raw item becomes exactly one inventory entry. `tools/re-jointjs/verify.mjs` does not reuse that extraction: it compares the stored inventory bidirectionally with a second, independently written extractor, `tools/re-jointjs/extract-ast.mjs` (TypeScript AST via `ts.createProgram` + TypeChecker, separate traversal code, no whitelist, constant or helper shared with the generator: module surfaces come from `checker.getExportsOfModule`, inherited fields from `checker.getPropertiesOfType` filtered by declaring file and namespace, and every other set is derived from the pinned sources rather than restated). The comparison covers the detail as well as the identifier: for every matched pair the guard requires the stored `source` pointer (path and line) to equal the anchored declaration, the stored `name` to equal the derived label, type-only rows to be type-only on both sides, and a stored `signature` to equal the derived declaration header when both sides carry one. Any item present on exactly one side — or any detail mismatch — fails the guard and is printed. "100 %" may be asserted only when the guard exits 0; it then means 2 277 of 2 277 parity items carry an entry — not that 2 277 behaviours are implemented (current implementation coverage is §3). The 109 JointJS+ tracked rows are outside the denominator (§1.2).

## 4. Renderer-independent target architecture

The specification is written against a contract, not against a renderer, so that it can be replayed first on the current stack and later on the WebGL graph (the capitalisation requirement). JointJS couples its model to SVG views; our stack deliberately separates the five objects already fixed by the programme (semantic document, view document, processing snapshot, scene/geometry frame, text source). Parity is therefore defined as contract equivalence, never as API-shape or DOM equivalence.

### 4.1 The four contracts

**Model contract (`diagram-core`).** A JointJS graph JSON (cells with `type`, attributes, `source`/`target`, `vertices`, `labels`, ports, embeds, `z`) maps to a `SemanticDocument` plus a `ViewDocument`: entities and relations carry business truth; occurrences carry position, size, angle, `z`, port side/order/anchor (already the shape of `PortOccurrence` in `packages/diagram-core/src/view.ts:66`), and persisted route waypoints. JointJS attributes that have no schema counterpart travel as preserved extensions with a conversion report (`converted`, `preserved-extension`, `degraded`, `ignored`, `unsupported`), consistent with the transversal contract of `docs/graph-dataviz-migration-plan.md`. Layers (GraphLayer) map to view planes; embedding maps to occurrence grouping, never to a second parent pointer.

**Command contract (`diagram-core`).** Every mutating `dia` behaviour (add/remove/reset cells, translate, resize, rotate, connect, embed, label and vertex edits, batch start/stop) maps to a transactional command or a transaction batch with `baseRevision` checking and a logical inverse — the existing `applyTransaction` semantics (`packages/diagram-core/src/commands.ts:1016`). A JointJS operation that cannot be expressed is a specification gap to be recorded, not a silent mutation. Undo/redo is transaction replay, as today.

**Event contract (`diagram-core` for model events, `diagram-canvas` for paper events).** Each inventoried event name maps to a typed host event with the same emission conditions and argument content, translated to contract types (occurrence and relation references instead of views; world points instead of DOM events). `change:<attribute>`, `batch:start`/`batch:stop`, collection `add`/`remove`/`reset`/`sort`/`update`, and layer events are model events. Pointer, blank, magnet, connect, render, and camera events (`translate`, `scale`, `transform`, `resize`) are paper events over the scene. Dynamic patterns stay patterns: the contract carries the attribute or prefix as data.

**Abstract rendering contract (`diagram-canvas` → `graph`).** `diagram-canvas` extends the `SceneFrame` (today: nodes, ports, edges with persisted paths, paint order, exclusions — `packages/diagram-canvas/src/scene.ts:103`) into a multi-primitive display list (§4.4): per occurrence, an ordered list of primitives indexed by stable part id (the contract replacement for JointJS markup `selector`s), plus computed link geometry — anchors, connection points, routed vertices, connector samples, label placements, highlighter overlays, and tool handles — all as plain geometry in world coordinates. `@sentropic/graph` consumes that geometry through its existing buffer contract (`setGraph`, `setStyle`, `setPositions`, `updatePositions`, `fitView`, `setCamera`, `render`, `snapshot` in `packages/graph/src/types.ts:418`) extended with the display-list buffers of §4.4, without learning what a router or a tool is. An SVG path string upstream is compared as sampled points on our side (§5.3); the contract value is the sample sequence, not the string. Today `SceneNode` is a single flat rectangle (`packages/diagram-canvas/src/scene.ts:52`) and `@sentropic/graph` node shapes are seven codes (`packages/graph/src/shape-geometry.ts:27`): neither can hold a JointJS cell's sub-node tree, which is why §4.4 is a required extension, not a mapping note.

Supporting kernels sit under the contracts: a pure geometry kernel (`g.*`, target `graph`), and a new support module for the `util`, `mvc`-replacement, Vectorizer-replacement (SVG import/export and text measurement), presentation-attribute evaluation, and global configuration surfaces (target `new-module`). DS components (target `ds-component`) own palettes, toolbars, inspectors, minimaps, menus, and the `@joint/react`-equivalent bindings for the four frameworks.

### 4.3 Non-goals of the architecture

No SVG DOM is carried into the target contracts: Vectorizer parity means parity of geometric results and of serialised SVG where SVG is an import/export format, not a live `VElement` API over our renderer. In particular `vel.attr(...)` called by user or plugin code has no live-DOM counterpart on our stack: the compatibility surface either rejects it with a named diagnostic or applies it as a display-list attribute patch (§4.4); it never silently no-ops. CSS-selector addressing of cell parts (JointJS markup selectors) is represented by stable contract part ids. JointJS themes are design-system themes on our side; `setTheme` parity is a theme-name registry, not JointJS CSS.

### 4.4 Display list: compiling `markup`/`selector` trees to WebGL

Each JointJS cell carries a markup tree whose nodes are named by `selector` (for example `HeaderedRectangle` exposes `root`, `body`, `header`, `headerText`, `bodyText`; a ported element adds one `portMarkup` + `portLabelMarkup` subtree per port). The target contract therefore extends `SceneFrame` with a `RenderDisplayList` between `diagram-canvas` and `@sentropic/graph`:

- Per occurrence, `parts: Map<partId, Primitive[]>` in markup order, where `partId` is the stable selector name (`root` is the occurrence itself) and each primitive is one of: positioned rect/ellipse, tessellated path (§4.8), measured text run, marker instance, or overlay. Paint order is occurrence `z`, then part order, then primitive order.
- Attributes are evaluated per part against a reference box. Resolution order is fixed: (1) the part's own box from its tag geometry and `calc(...)` (§4.5); (2) `ref: '<selector>'` rebases the reference box to the named sibling part's already-computed box, with `ref-x`/`ref-y`/`ref-dx`/`ref-dy`/`ref-width`/`ref-height`/`ref-d`/`ref-points` and the `x-alignment`/`y-alignment` rules applied in that order; a missing or cyclic `ref` is a conversion diagnostic (`degraded`), never a silent origin fallback. Port parts resolve after element parts, link label parts after the connection geometry of §4.7.
- `@sentropic/graph` receives the list as typed buffers (part index, primitive kind, geometry, paint, text-run index) and draws it without interpreting selectors. The Canvas2D text overlay already used by the WebGL backend (`boxTextDraws`/`onTextDraws` in `packages/graph/src/renderer.ts`) remains the text path: display-list text runs are measured once (§5) and handed to that overlay, so SVG `getBBox` text metrics are never required at render time.

### 4.5 The `calc(...)` evaluator

All `shapes.standard.*` sizing runs through `evalAttributes`/`evalAttribute` (`packages/joint-core/src/dia/attributes/eval.mjs:46` in the pinned sources, read via `.ds-scrap/re-sources/joint/packages/joint-core/src/dia/attributes/eval.mjs`), which the previous inventory omitted entirely. The contract evaluator is pure: `eval(attrs, refBBox) -> attrs`.

- It applies only to the 20 names of `calcAttributesList` (`transform`, `x`, `y`, `cx`, `cy`, `dx`, `dy`, `x1`, `y1`, `x2`, `y2`, `points`, `d`, `r`, `rx`, `ry`, `width`, `height`, `stroke-width`, `font-size`) whose value contains `calc(`; every `calc(<formula>)` occurrence in the string (including inside `d`/`points` such as `M 0 0 H calc(w) V calc(h) H 0 Z`) is replaced by its numeric result. `r`, `rx`, `ry`, `width`, `height`, `stroke-width`, `font-size` results are clamped to `>= 0`. Other attributes pass through unchanged.
- Formula grammar (from `src/util/calc.mjs`): `[coef*](w|h|x|y|s|l|d)[/divisor][(+|-)offset]` with `w`=ref width, `h`=ref height, `x`/`y`=ref origin, `s`=`min(w,h)`, `l`=`max(w,h)`, `d`=`sqrt(w²+h²)`; whitespace is ignored; an unparseable formula throws `Invalid calc() expression` upstream and is a conversion error on our side. The same grammar text is carried on every `presentation-attribute` inventory row so Lots 2–4 need no source access.

### 4.6 Camera unification (blocking decision for Lots 5–6)

The repository today has two incompatible camera readings (recorded at `packages/diagram-canvas/README.md:62`): `diagram-canvas` treats `camera.x/y` as the world point at the view origin (`view = (world - camera) * zoom`, `packages/diagram-canvas/src/transform.ts:178`), while `@sentropic/graph` treats it as the viewport centre (`screen = (world - camera) * zoom + viewport/2`, `packages/graph/src/mat4.ts:114` and the closures in `packages/graph/src/gitflow-labels.ts`). JointJS `Paper.matrix()` is a third spelling of the same affine (`view.x = world.x * sx + tx` with `tx = -camera.x * zoom` under the origin reading).

Parity adopts the `diagram-canvas` origin reading as the single contract camera, because the view document persists it and `worldToDevice` already fixes the chain. `@sentropic/graph` keeps its centre-based device projection internally but receives the contract camera converted at the display-list boundary (`centre = origin + viewport/(2*zoom)`); no fixture may carry a raw JointJS `tx/ty` without that conversion. Resolving the `diagram-canvas → graph` edge also requires lifting the current import prohibition (`packages/diagram-canvas/README.md:124`, enforced by `tests/no-dom.test.ts`) for the display-list types only, and the `private: true` publication gate (§6) still applies. Until Lot 5 implements the conversion, every Paper transform row stays at most `partial`.

### 4.7 Pure replacement for `(view, magnet: SVGElement)`

Upstream anchors, connection points and connection strategies receive `(view, magnet: SVGElement, ref, opt)` and call DOM APIs (`V.isSVGGraphicsElement`, `magnet.getAttribute('stroke-width')`, `view.getNodeShape(node)`, `view.getNodeMatrix(node)`). None of that exists over WebGL. The pure contract descriptor is:

```ts
{ shape: Rect | Ellipse | PathOutline | PolygonOutline, // world geometry of the magnet part
  localMatrix: Affine,        // part-local -> world, rotation included
  strokeWidth: number,        // resolved presentation value, never read from a DOM node
  portId?: string,            // stable part/port identity when the magnet is a port
  bbox: Rect }                // unrotated bounding box used by pinRelative-style rules
```

Anchors and connection points are pure functions of that descriptor plus the reference point; `connectionPoints.boundary` intersects the end segment with `shape` (with `insideout`, `extrapolate`, `sticky`, `stroke`, `offset` as declared options) instead of descending a DOM subtree and inverting SVG matrices. Connection strategies rewrite the end definition from the descriptor (`pinRelative` computes `dx`/`dy` percentages, rounded to 3 decimals, against `bbox` after rotating the drop point by `-angle`, and fixes `anchor: { name: 'topLeft', args: { dx, dy, rotate: true } }` on elements or `connectionRatio` on links). Any upstream behaviour that genuinely needs a live node shape beyond this descriptor is recorded as a named degradation in the conversion report.

### 4.8 Tessellation, markers, gradients, patterns and filters

WebGL2 has no SVG path, gradient, pattern or filter engine, so the display list fixes the policy per feature instead of claiming a generic "mapping to halo/alpha passes" (the previous §4 wording, withdrawn):

- Paths and polygons: `g.Path`/`g.Polygon` outlines (including concave polygons, where `TRIANGLE_FAN` in `packages/graph/src/render-geometry.ts` is incorrect) are flattened (curves at the connector's stated precision) and triangulated on CPU by ear-clipping into an indexed vertex buffer; strokes are expanded as triangle strips with the declared join/cap. Hit testing consumes the same flattened outline.
- Markers (`source-marker`, `target-marker`, `vertex-marker`): each distinct marker definition becomes a tessellated template; per link end/vertex the renderer draws one oriented instance (position, tangent angle, scale) from the template buffer. Arbitrary marker subtrees that are not paths are degraded to their flattened outline.
- Paint servers: solid fills/strokes are native. `linearGradient`/`radialGradient` with at most the declared stops are evaluated into a 1-D atlas texture sampled per primitive; `<pattern>` fills are rasterised once into the same atlas at the pattern's declared tile size. Filters: `dropShadow`, `blur`, `outline`, `highlight` map to the existing halo/outline passes with the declared radii; `grayscale`, `sepia`, `saturate`, `hueRotate`, `invert`, `brightness`, `contrast` map to a per-primitive colour-matrix uniform. Anything outside that list (nested filters, pattern transforms beyond translation) is an explicit degradation recorded per occurrence, never a silent solid fill.

## 5. Differential parity harness

### 5.1 Principle

The same inputs are played on JointJS (@joint/core 4.3.3, from the pinned checkout) and on our implementation, and the observable outputs are compared: resulting model (canonical serialisation), emitted event sequence, computed geometry, and — only where geometry cannot decide — pixels. A lot is done when its inventory rows move to `covered` on the strength of harness passes, not on code presence.

### 5.2 Tooling

- Browser driver: headless Chrome via `playwright-core`. It is already declared in this repository (`apps/docs/package.json:186` and `packages/skills/package.json:37`, `playwright-core ^1.60.0`); it is not installed in this worktree (no `node_modules/playwright-core`), and no install is performed in this lot. The harness must resolve the browser binary the way the existing graph golden harness does (`CHROME_BIN` or the system candidates in `packages/graph/tests/golden/cdp-harness.mjs:33`).
- The existing Chrome/CDP golden harness of `@sentropic/graph` (`packages/graph/tests/golden/cdp-harness.mjs`, with `webgl-preflight.mjs`) is the proven pattern for deterministic capture: it pins fonts, awaits `document.fonts.ready`, and reads canvas backing-store pixels directly. The parity harness reuses that pattern and its fixture/diff helpers rather than inventing a second capture path.
- JointJS runs in the harness page from the pinned sources (built bundle of the checkout); our implementation runs from the worktree packages. Fixtures are plain data (graph JSON, operation scripts, pointer scripts) shared verbatim by both sides; each side adapts fixtures to its own API behind a thin driver, so a fixture never encodes JointJS calls.
- Node-side differential suites (geometry, model, commands) need no browser and run under the repository's existing test runners.

### 5.3 Comparisons and tolerances

| Compared artefact | Comparison | Tolerance |
|---|---|---|
| Model result | canonical serialisation (sorted keys, our `canonicalise` on one side, stable stringify of the JointJS JSON echo on the other) after the contract mapping of §4.1 and the event projection of §5.5 | exact, except floating geometry (below) |
| Geometry (points, vertices, routes, anchors, boxes) | point sequences in world coordinates, after reproducing the function's own rounding (below) | residual 1e-6 world units; exact for integer fixtures |
| Connector output | JointJS path string sampled at fixed arc-length steps vs our polyline/curve samples | residual 1e-6 world units per sample after the connector's rounding; sample count fixed per fixture |
| Events | ordered event-name sequence plus contract-translated arguments through the §5.5 projection | exact projected sequence; pointer coordinates compared after the shared world transform |
| Labels and text | fitted text, line breaks, and label positions with the shared measurement of the golden harness | exact fitted string; position within 1 device pixel (see the text note below) |
| Pixels (only where geometry cannot decide: highlighters, tools, shape rendering) | canvas backing-store capture per the golden harness | per-channel delta and mismatch budget fixed per fixture in the harness, as in `packages/graph/tests/golden/` |
| Algorithmic layouts (dagre, MSAGL, force) | invariants (no NaN, containment, ordering constraints, cluster nesting), never exact coordinates across different algorithms | invariant-based; exact only for the integer geometry kernel |

Rounding is part of the contract, not noise under the 1e-6 tolerance (the previous blanket 1e-6 claim is withdrawn). Each geometry oracle first reproduces the upstream rounding, then compares the residual: `connectors.straight` rounds corners to `precision=1`, `connectors.curve` rounds the path to `precision=3`, `routers.manhattan` rounds to `precision=1`, `routers.metro` calls `point.round()` (integer) on its fallback, `layout.ports.*` calls `p.round()` (integer) on every port position, and `connectionStrategies.pinRelative` rounds percentages to 3 decimals. A comparator that skips the rounding step fails those functions by construction. Edge convention: the JointJS-compatibility layer exposes the closed `g.Rect` convention (`<=` on all sides, §3); the native `diagram-canvas` half-open convention stays for native callers, and hit-test fixtures state which convention they exercise — border points on the right/bottom edges are compared explicitly, never folded into an "off-border" tolerance. Text: JointJS measures through SVG text layout while our WebGL backend draws box text on a Canvas2D overlay (`packages/graph/src/renderer.ts`), so `breakText`/`textWrap` oracles compare the fitted string and line breaks exactly under the pinned font and the line positions within 0.5 device pixels; a fixture that needs SVG-exact advances is marked `unknown`, not forced.

### 5.4 Oracle modes and explicit exclusions

Every inventory row carries exactly one oracle mode; exclusions are bounded to this table (a row outside it always has an oracle):

| Oracle mode | Families | Comparison |
|---|---|---|
| `pure-geometry-oracle` | `geometry`, `router`, `connector`, `anchor`, `link-anchor`, `connection-point`, `layout-port`, `layout-port-label`, `alg` | §5.3 geometry comparison with per-function rounding |
| `model-state-oracle` | `dia-api` (model classes), `mvc`, model `event`s, `core-config` | canonical model + §5.5 projected effects |
| `cdp-scene-oracle` | `dia-api` (view/paper classes), `paper-option`, paper `event`s, `highlighter`, `link-tool`, `element-tool`, `shape`, `presentation-attribute`, `connection-strategy` | scripted interaction + scene/display-list geometry (+ pixels only where geometry cannot decide) |
| `typecheck-only` | `package-api` rows with `kind: "type"` (including most `@joint/react` type exports) | consumer fixture must typecheck identically; no runtime oracle |
| `greenfield-recipe-no-oracle` | the 109 JointJS+ tracked rows | excluded from the harness and from every gate; capability-closure review only (§7.3) |

Excluded from differential comparison (recorded `unknown` in the harness report, never asserted): live DOM identity or structure (all `VElement` node-mutating members without a pure contract, including live `vel.attr(...)` effects), SVG attribute spelling, CSS cascade results, JointJS internal scheduling (async Paper batching is compared as final state plus projected event order, not as frame timing), browser text metrics beyond the pinned-font rule above, `@joint/cli` command side effects beyond exported names and configuration shape, and anything JointJS+.

### 5.5 Event/effect projection (required for any "0 divergence" claim)

JointJS emits synchronous mutable Backbone-style events (`change:position`, `change:attrs`, `batch:start`/`batch:stop`, collection `add`/`remove`/`reset`/`sort`/`update`) while `diagram-core` returns immutable transaction `Effect`s (`packages/diagram-core/src/commands.ts`). "0 divergence" is therefore defined only after this projection, which Lot 0 freezes and Lot 3 implements: each JointJS event name maps to the transaction effect(s) that imply it (for example a position patch implies `occurrence-moved` then the projected `change:position`; a batch maps to the transaction boundary with its contained effects in order; a rejected transaction projects to `invalid` with no state effects). Arguments are translated to contract types (occurrence/relation refs, world points) before comparison. A JointJS event with no projecting effect, or an effect with no JointJS counterpart, is a harness failure to be specified — never silently dropped from the sequence.

### 8.2 Pre-mortem

It is 2027 and the programme is judged to have failed. The most probable story, in order: (1) Lot 6 was attempted before the Lot 0 harness could prove projected event-order parity, so "covered" was declared on code presence and later revoked — the gates in §6 exist to prevent exactly this, and any gate claimed without harness output should be treated as void; (2) JointJS+ catalogue rows were reported inside the same percentage as the @joint/core surface, overstating parity by up to 109 rows — §6 and §7.3 forbid merging the figures; (3) text measurement was left to the end, and label-bearing shapes (the majority of real diagrams) blocked Lots 4, 6, and 9 simultaneously — Lot 0 therefore includes the pinned-font measurement from the start; (4) the model contract silently dropped JointJS attribute-bag behaviours instead of recording degradations, so imported diagrams changed meaning without a report — Lot 3 makes the conversion report a gate artefact.

### 8.3 Unknowns (`unknown`, not assumed)

- Behaviours outside the §2.1 conventions: runtime-only surface reachable through options objects, callbacks, and subclassing (for example custom routers, anchors, views, and tools written by applications) is specified by contract (a host may register equivalents) but cannot be enumerated from the pinned sources; the guard does not cover it.
- JointJS+ interaction fidelity for the 109 commercial rows: no reference exists in this checkout (§7.3).
- Whether `playwright-core` in this repository resolves a usable headless Chrome with WebGL2 in the CI environment: declared in two manifests, not installed in this worktree, and not exercised by this lot. Lot 0 must prove it (the graph golden lane is evidence the pattern works, not proof for this harness).
- Exact upstream semantics where the type surface and the runtime disagree (for example options honoured only in legacy Paper mode): each such case becomes a behaviour probe in the owning lot; until probed, the inventory row's behaviour text states the typed contract only.
- Performance parity: this spec defines functional parity only. Frame budgets, worker thresholds, and large-graph limits of our stack are governed by the existing graph specifications, not by JointJS benchmarks.
- The final package topology for the `new-module` target (one support module or several) and for DS editor chrome: decided by the owning lots under the existing package architecture; this spec fixes contracts, not package names, beyond the targets already named.
