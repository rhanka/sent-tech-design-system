## 4. Renderer-independent target architecture

The specification is written against a contract, not against a renderer, so that it can be replayed first on the current stack and later on the WebGL graph (the capitalisation requirement). JointJS couples its model to SVG views; our stack deliberately separates the five objects already fixed by the programme (semantic document, view document, processing snapshot, scene/geometry frame, text source). Parity is therefore defined as contract equivalence, never as API-shape or DOM equivalence.

### 4.1 The four contracts

**Model contract (`diagram-core`).** A JointJS graph JSON (cells with `type`, attributes, `source`/`target`, `vertices`, `labels`, ports, embeds, `z`) maps to a `SemanticDocument` plus a `ViewDocument`: entities and relations carry business truth; occurrences carry position, size, angle, `z`, port side/order/anchor (already the shape of `PortOccurrence` in `packages/diagram-core/src/view.ts:66`), and persisted route waypoints. JointJS attributes that have no schema counterpart travel as preserved extensions with a conversion report (`converted`, `preserved-extension`, `degraded`, `ignored`, `unsupported`), consistent with the transversal contract of `docs/graph-dataviz-migration-plan.md`. Layers (GraphLayer) map to view planes; embedding maps to occurrence grouping, never to a second parent pointer.

**Command contract (`diagram-core`).** Every mutating `dia` behaviour (add/remove/reset cells, translate, resize, rotate, connect, embed, label and vertex edits, batch start/stop) maps to a transactional command or a transaction batch with `baseRevision` checking and a logical inverse — the existing `applyTransaction` semantics (`packages/diagram-core/src/commands.ts:1016`). A JointJS operation that cannot be expressed is a specification gap to be recorded, not a silent mutation. Undo/redo is transaction replay, as today.

**Event contract (`diagram-core` for model events, `diagram-canvas` for paper events).** Each inventoried event name maps to a typed host event with the same emission conditions and argument content, translated to contract types (occurrence and relation references instead of views; world points instead of DOM events). `change:<attribute>`, `batch:start`/`batch:stop`, collection `add`/`remove`/`reset`/`sort`/`update`, and layer events are model events. Pointer, blank, magnet, connect, render, and camera events (`translate`, `scale`, `transform`, `resize`) are paper events over the scene. Dynamic patterns stay patterns: the contract carries the attribute or prefix as data.

**Abstract rendering contract (`diagram-canvas` → `graph`).** `diagram-canvas` extends the `SceneFrame` (today: nodes, ports, edges with persisted paths, paint order, exclusions — `packages/diagram-canvas/src/scene.ts:103`) with computed link geometry: anchors, connection points, routed vertices, connector samples, label placements, highlighter overlays, and tool handles, all as plain geometry in world coordinates. `@sentropic/graph` consumes that geometry through its existing buffer contract (`setGraph`, `setStyle`, `setPositions`, `updatePositions`, `fitView`, `setCamera`, `render`, `snapshot` in `packages/graph/src/types.ts:418`) without learning what a router or a tool is. An SVG path string upstream is compared as sampled points on our side (§5.3); the contract value is the sample sequence, not the string.

Supporting kernels sit under the contracts: a pure geometry kernel (`g.*`, target `graph`), and a new support module for the `util`, `mvc`-replacement, Vectorizer-replacement (SVG import/export and text measurement), presentation-attribute evaluation, and global configuration surfaces (target `new-module`). DS components (target `ds-component`) own palettes, toolbars, inspectors, minimaps, menus, and the `@joint/react`-equivalent bindings for the four frameworks.

### 4.2 What changes in each existing package (specified, not implemented here)

- `diagram-core`: new diagram commands for JointJS-shaped edits (cell attribute patches, vertex/label edits, embedding, layer operations) behind the same transaction and inverse rules; a JointJS JSON import/export codec with the conversion report above; model-event emission derived from transaction effects.
- `diagram-canvas`: router/connector/anchor/connection-point evaluation into `SceneEdge` geometry; port-group layouts; camera semantics completing the Paper transform set (`worldToDevice` already fixed in `packages/diagram-canvas/src/transform.ts:200`); scene-level highlight and tool overlays; pointer-interaction state machines producing commands (no direct model mutation).
- `graph`: the `g.*` geometry kernel as a DOM-free subpath; standard-shape glyph coverage beyond the current nine shape codes (`packages/graph/src/shape-geometry.ts:27`); edge geometry for routed polylines and connector samples; processing layouts completing Lot 6.
- New module(s) and DS components per the `new-module` / `ds-component` targets above.

### 4.3 Non-goals of the architecture

No SVG DOM is carried into the target contracts: Vectorizer parity means parity of geometric results and of serialised SVG where SVG is an import/export format, not a live `VElement` API over our renderer. CSS-selector addressing of cell parts (JointJS markup selectors) is represented by stable contract part ids. JointJS themes are design-system themes on our side; `setTheme` parity is a theme-name registry, not JointJS CSS.

## 5. Differential parity harness

### 5.1 Principle

The same inputs are played on JointJS (@joint/core 4.3.3, from the pinned checkout) and on our implementation, and the observable outputs are compared: resulting model (canonical serialisation), emitted event sequence, computed geometry, and — only where geometry cannot decide — pixels. A lot is done when its inventory rows move to `covered` on the strength of harness passes, not on code presence.

### 5.2 Tooling

- Browser driver: headless Chrome via `playwright-core`. It is already declared in this repository (`apps/docs/package.json:186` and `packages/skills/package.json:37`, `playwright-core ^1.60.0`); it is not installed in this worktree (no `node_modules/playwright-core`), and no install is performed in this lot. The harness must resolve the browser binary the way the existing graph golden harness does (`CHROME_BIN` or the system candidates in `packages/graph/tests/golden/cdp-harness.mjs:33`).
- The existing Chrome/CDP golden harness of `@sentropic/graph` (`packages/graph/tests/golden/cdp-harness.mjs`, with `webgl-preflight.mjs`) is the proven pattern for deterministic capture: it pins fonts, awaits `document.fonts.ready`, and reads canvas backing-store pixels directly. The parity harness reuses that pattern and its fixture/diff helpers rather than inventing a second capture path.
- JointJS runs in the harness page from the pinned sources (built bundle of the checkout); our implementation runs from the worktree packages. Fixtures are plain data (graph JSON, operation scripts, pointer scripts) shared verbatim by both sides; each side adapts fixtures to its own API behind a thin driver, so a fixture never encodes JointJS calls.
- Node-side differential suites (geometry, model, commands) need no browser and run under the repository's existing test runners.

### 5.3 Comparisons and tolerances

| Compared artefact | Comparison | Tolerance |
|---|---|---|
| Model result | canonical serialisation (sorted keys, our `canonicalise` on one side, stable stringify of the JointJS JSON echo on the other) after the contract mapping of §4.1 | exact, except floating geometry (below) |
| Geometry (points, vertices, routes, anchors, boxes) | point sequences in world coordinates | 1e-6 world units; exact for integer fixtures |
| Connector output | JointJS path string sampled at fixed arc-length steps vs our polyline/curve samples | 1e-6 world units per sample; sample count fixed per fixture |
| Events | ordered event-name sequence plus contract-translated arguments | exact sequence; pointer coordinates compared after the shared world transform |
| Labels and text | fitted text, line breaks, and label positions with the shared measurement of the golden harness | exact fitted string; position within 1 device pixel |
| Pixels (only where geometry cannot decide: highlighters, tools, shape rendering) | canvas backing-store capture per the golden harness | per-channel delta and mismatch budget fixed per fixture in the harness, as in `packages/graph/tests/golden/` |
| Algorithmic layouts (dagre, MSAGL, force) | invariants (no NaN, containment, ordering constraints, cluster nesting), never exact coordinates across different algorithms | invariant-based; exact only for the integer geometry kernel |

### 5.4 What is not compared

Live DOM identity or structure, SVG attribute spelling, CSS cascade results, JointJS internal scheduling (async Paper batching is compared as final state plus event order, not as frame timing), browser text metrics beyond the pinned-font measurement above, and anything JointJS+ (no observable reference exists in this checkout; §7.3). A behaviour that cannot be compared is recorded as `unknown` in the harness report rather than asserted.

## 7. Licence and clean-room rules

### 7.1 What the licences say

- `@joint/core` is MPL-2.0: `packages/joint-core/package.json` declares `"license": "MPL-2.0"`, and the monorepo `LICENSE` file is the Mozilla Public License 2.0 text. Most monorepo packages carry the same grant (per-package `license` fields, inventoried in the `package` family); `@joint/cli` (0.2.4) and `@joint/eslint-config` (4.3.0) are MIT.
- MPL-2.0 is a file-level copyleft: it governs JointJS source files and modifications of them. It does not require our independently written code to be MPL-2.0, and it does not license JointJS+ (below).
- Our target packages are MIT (`packages/graph/package.json`), with `diagram-core` and `diagram-canvas` private and unpublished at this stage.

### 7.2 Clean-room method (binding for all lots)

1. This specification and inventory describe behaviours (inputs, outputs, invariants, tolerances) and never reproduce JointJS code, comments, markup strings, or asset content. Inventory `behaviour` text is written from the observable contract; `source` pointers exist so a reviewer can audit that claim.
2. Implementers work from this spec, the inventory, and public documentation. A person who has read JointJS source to write inventory rows does not copy expressions, structure, or constants from it into implementation code; where a numeric constant is itself the observable behaviour (a default padding, a threshold), the inventory states the value as a behaviour fact and the harness proves it, instead of the code transcribing it.
3. Differential fixtures are authored from behaviours, and expected outputs are produced by running JointJS as a black box in the harness — never by transcribing its source into fixtures.
4. No JointJS file (source, CSS, demo asset) is copied into this repository by any lot. If a future lot concludes that direct reuse of an MPL-2.0 file is preferable to reimplementation, that is a separate licensing decision, recorded before the fact, and the file would have to keep its licence and notices. The default and the plan above assume no reuse.
5. Provenance: each lot records, per inventory row, the spec section and harness fixture that prove parity. The inventory `source` field is an audit pointer, not an implementation input.

### 7.3 JointJS+

JointJS+ is the commercial product; it has no source in this checkout and this spec grants no right to obtain or reproduce it. 109 of the 186 catalogue rows are marked `JointJS+` in `source_license_marker` (77 are `Open source`). For JointJS+ rows, behaviour is specified only at the level of the public catalogue (name, tags, capability mapping) and our own target contract; no JointJS+ code, demo source, or asset may be consulted, copied, or reconstructed. Fidelity for those rows remains `unknown` where the public description cannot decide it, and the reporting rule of §6 (never merge the two figures) applies. Open-source catalogue rows may be observed as running public demos for behaviour confirmation, under the same no-copy rule.

| Text measurement divergence (fonts, wrapping, `breakText`) | Label geometry and shapes that depend on text never reach exact parity | Pinned-font harness measurement (§5.2); text rows carry the shared-measurement tolerance (§5.3); residual divergence stays `partial` |
| `manhattan` / `metro` obstacle semantics tied to rendered SVG views | Contract routing over scene geometry diverges on rotated, embedded, or port cases | Lot 3 fixtures include rotated and embedded cases; semantics settled from behaviour probes before coding |
| Paper async scheduling and view management (`async`, `frozen`, `viewManagement`) | Event order and intermediate states diverge under load | Compared as final state plus event order (§5.4); intermediate-frame parity is not claimed |
| Embedding and layer semantics (GraphLayer, embeds, `z`) exceed the occurrence model | Model-contract rows stall at `partial` | Lot 2 records inexpressible semantics as named degradations with a conversion report instead of silent loss |
| Algorithmic layouts (dagre, MSAGL) expected to match exactly | Unachievable without porting those algorithms | Invariant-based gates (§5.3, Lot 6); exact parity would be a separate decision |
| WebGL text and glyph coverage | Shape and label pixels diverge from the Canvas2D reference | The golden harness already separates backing-store capture per backend; Lot 4 gates per shape, not in bulk |
| Scope pressure from 186 applications | Lots 1–7 (the reusable surface) starve in favour of visible demos | Lot 8 is last and gated on capability closure; applications never redefine core contracts |

### 8.2 Pre-mortem

It is 2027 and the programme is judged to have failed. The most probable story, in order: (1) Lot 5 was attempted before the Lot 0 harness could prove event-order parity, so "covered" was declared on code presence and later revoked — the gates in §6 exist to prevent exactly this, and any gate claimed without harness output should be treated as void; (2) JointJS+ catalogue rows were reported inside the same percentage as the @joint/core surface, overstating parity by up to 109 rows — §6 and §7.3 forbid merging the figures; (3) text measurement was left to the end, and label-bearing shapes (the majority of real diagrams) blocked Lots 4, 5, and 8 simultaneously — Lot 0 therefore includes the pinned-font measurement from the start; (4) the model contract silently dropped JointJS attribute-bag behaviours instead of recording degradations, so imported diagrams changed meaning without a report — Lot 2 makes the conversion report a gate artefact.

### 8.3 Unknowns (`unknown`, not assumed)

- Behaviours outside the §2.1 conventions: runtime-only surface reachable through options objects, callbacks, and subclassing (for example custom routers, anchors, views, and tools written by applications) is specified by contract (a host may register equivalents) but cannot be enumerated from the pinned sources; the guard does not cover it.
- JointJS+ interaction fidelity for the 109 commercial rows: no reference exists in this checkout (§7.3).
- Whether `playwright-core` in this repository resolves a usable headless Chrome with WebGL2 in the CI environment: declared in two manifests, not installed in this worktree, and not exercised by this lot. Lot 0 must prove it (the graph golden lane is evidence the pattern works, not proof for this harness).
- Exact upstream semantics where the type surface and the runtime disagree (for example options honoured only in legacy Paper mode): each such case becomes a behaviour probe in the owning lot; until probed, the inventory row's behaviour text states the typed contract only.
- Performance parity: this spec defines functional parity only. Frame budgets, worker thresholds, and large-graph limits of our stack are governed by the existing graph specifications, not by JointJS benchmarks.
- The final package topology for the `new-module` target (one support module or several) and for DS editor chrome: decided by the owning lots under the existing package architecture; this spec fixes contracts, not package names, beyond the targets already named.
