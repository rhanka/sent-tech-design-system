## 1. Question and scope

The owner asks whether the collaborative functions known from “le mode canvas” — anticipating concurrent editing, and the lock — can be integrated natively into the DS editor.

“Native in the DS editor” is ambiguous until the DS boundary is fixed. The reading adopted here, and defended in §4–§5, is:

- the DS owns **editor-surface collaboration affordances**: presence and lock display components, a provider port injected by the host, awareness rendering (carets, selections — stage two only, §5.2), and the editor-side rules that make concurrent input safe locally;
- the DS does **not** own transport, persistence, workspace membership, authentication, or any business API. No WebSocket, no SSE, no `fetch`, no database, no Track write enters a DS package. That boundary is already normative in FE-2 (`spec/SPEC_EVOL_DS_RICH_TEXT_EDITOR.md` §0.2, §5.9) and is not renegotiated here.

Three collaboration levels are distinguished throughout:

| Level | Meaning | Concurrency posture |
| --- | --- | --- |
| L0 | Pessimistic object or field locks with presence, as in sentropic `COLLAB.md` today | One writer at a time per locked unit; other users see who holds the lock and may request release |
| L1 | Paragraph-level or block-level locks inside one document | One writer per paragraph/block; several writers may work in one document on disjoint blocks |
| L2 | Real concurrent editing with a CRDT (Yjs + y-prosemirror), plus awareness (carets, selections, presence) | Several writers edit the same paragraph concurrently; merges are automatic; conflicts surface as merged text, not as refusals |

The question is therefore threefold:

1. What exists today under the name “canvas mode”, and what of it is actually delivered code versus intent?
2. Which level(s) should the DS editor support natively, through which port, without breaking the DS boundary?
3. What must be designed into RT-1 now so that a later L2 is not blocked — identities, transaction shape, provider slot — and what must explicitly wait?

Out of scope for this study: the B1 inventory of sentropic editables, the B3 spreadsheet design, any implementation, any new Track event kind, and any change to the h2a Focus edit-return contract. Where this study touches those, it names an interface (§6) and stops.

## 2. Measured inventory

### 2.1 “Le mode canvas” — what the name denotes today

The phrase does not denote one delivered surface. Three distinct referents were found, and conflating them would misstate the starting point.

**(a) The sentropic canvas intent (`SPEC_VOL_INTERACTIVE_CANVAS`).** `sentropic:spec/SPEC_VOL_INTERACTIVE_CANVAS.md:1` is headed “raw intent: live canvas, agent-scope awareness, CLI integration, track/dossier as canvas” and self-describes at line 3 as “SPEC_VOL = volition / raw owner intent, NOT a reviewed study”. Its intentions:

- I1: live canvas editions are preferred over background-agent filesystem edits on the same object (`SPEC_VOL_INTERACTIVE_CANVAS.md`, intention I1). The filesystem mode is the headless affordance; the canvas is the human/foreground affordance.
- I2: if a background agent is working — or plans to work, via a declared scope of work framed by h2a/track — on an object the user is currently visualising, the user must be made aware (live presence / lock / notice on the canvas).
- I4: the track Kanban view is a bidirectional canvas (AI updates, human creates actions).
- I5: the decision dossier is an interactive canvas with live spec amendment and human/machine diff tracking.
- I6: a reusable interactive-canvas + annotation module in sentropic, co-designed with track, lifting the annotation/circling primitive out of diag/mermaid-editor.

Its own open questions (`SPEC_VOL_INTERACTIVE_CANVAS.md` §4) name the concurrency model as undecided: “when a human edits live AND a bg agent holds a scope on the same object — lock (deny the agent), CRDT merge, or present-and-warn (live wins, agent yields)?” No decision is taken in that file. Its promotion path (§5) defers to amendments of ARCH-16, ARCH-09, and a new study for the reusable canvas module. Measured consequence: **I1/I2 are the closest sentropic statement to “canvas-mode collaboration”, and they are intent, not delivered behaviour.** Any B2 claim that a CRDT or a live multi-writer canvas already exists in sentropic is contradicted by this source.

**(b) The `LiveDocumentStore` port stub (ARCH-16 carve-out).** `sentropic:packages/chat-core/src/ports.ts:68` carries the comment “Per SPEC §10.3 — canvas bidirectional editing. LiveDocumentStore carries the diff round-trip abstraction beyond the message log”, and lines 70–72 define the whole surface:

```ts
export interface LiveDocumentStore {
  readonly _kind: 'LiveDocumentStore';
}
```

There is no read, watch, submit, or reconcile method. The h2a specification records the same fact as capital K15: “`LiveDocumentStore` is a `_kind` interface stub, not a usable read/watch/submit/reconcile implementation” (`SPEC_EVOL_FOCUS_EDIT_RETURN.v3.md` §2, K15), and `docs/focus/document-editing.md` at h2a `98060bd0a` states the offline increment must not depend on it. A file named `SPEC_EVOL_CHAT_CANVAS.md` does not exist on `origin/main` (verified: `git -C /home/antoinefa/src/sentropic ls-tree -r --name-only origin/main` lists `SPEC_EVOL_EVENT_SPINE.md` and `SPEC_EVOL_RESOURCE_FS.md`, and `git show origin/main:spec/SPEC_EVOL_CHAT_CANVAS.md` fails). The catalog source confirms the carve-out posture in code: `sentropic:api/src/services/catalog/sources/canvas-template-source.ts:18` states “canvas runtime is carved out to `SPEC_EVOL_CHAT_CANVAS`; it is a named carve-out only, not yet a present file”, and that source ships only two static template seeds (`blank-markdown`, `structured-plan`) with “No `LiveDocumentStore`/CRDT/editor runtime is included or imported” (same file, header comment). Measured consequence: **there is no canvas editing runtime to reuse. B2 designs the DS side of a future port; it does not extract an existing one.**

**(c) The comments “canvas” anchor kind.** `sentropic:packages/comments/src/types.ts:11` defines `CommentTargetKind = 'message' | 'canvas' | 'artifact' | 'field' | 'record'`. The `canvas` kind is an annotation target, not an editor. The follow-on annotations specification generalises anchors to field, text, UI, and capture variants with immutable, hashed revisions and compare-and-swap on the head (`sentropic:spec/SPEC_EVOL_COMMENTS_ANNOTATIONS.md` §4.2 anchor table; §4 concurrency paragraph: “All state-changing commands use an idempotency key and expected current revision/hash or expected aggregate version… Concurrent edits from the same head yield one accepted result and a conflict for the other; no last-write-wins loss”). That CAS discipline is directly relevant to FE-6 (§2.4) and is reused as a design constraint in §5, but it annotates content; it does not edit it concurrently.

**Net answer to “what is le mode canvas”.** In delivered code, “canvas” collaboration today means: object locks + presence (§2.2), comments anchored to canvas-typed targets, and a set of volition intentions (live-preferred editing, agent-scope awareness) that have no runtime behind them. The owner’s phrase “les fonctions collaboratives (prévoir l'édition concurrente et le lock)” maps, in delivered code, to the L0 lock + presence system, not to a CRDT. That mapping is the factual baseline for the options in §4.

### 2.2 Sentropic L0 today: object locks, unlock flow, lifecycle, UI, presence

Source: `sentropic:spec/COLLAB.md` (426 lines on `origin/main`), plus the implementation files below. All reads via `git -C /home/antoinefa/src/sentropic show origin/main:<path>`.

**Lock model.** `spec/COLLAB.md` §“Object Edition Locks / Lock Model”: scope is the triple (workspaceId + objectType + objectId); storage is a single table `object_locks` with TTL (`expires_at`); TTL is “1 minute max, UI refresh every 30s”; write enforcement blocks mutations (PUT/DELETE) when a lock exists and is held by another user, returning `409` with `{ code: 'OBJECT_LOCKED', lock }`. The implementation narrows the type: `api/src/services/lock-service.ts:8` declares `LockObjectType = 'organization' | 'folder' | 'initiative'`. `lock-service.ts:29` sets `DEFAULT_TTL_MS` to 60 000 ms when `LOCK_TTL_MS` is unset (the variable carries no floor); the 5 000 ms floor applies to the per-call `options.ttlMs` in `acquireLock` (`lock-service.ts:139`: `Math.max(5_000, options.ttlMs)`), not to the environment variable. Acquisition is transactional (`acquireLock`, `lock-service.ts:131`): expired rows for the same object are deleted first, an existing live lock owned by the same user is refreshed idempotently, a lock owned by another user returns `{ acquired: false }`, and a unique-violation (`23505`) on insert is treated as a conflict. The mutation guard is `requireLockOwnershipForMutation` (`lock-service.ts:50`): it loads the active lock (`lock-service.ts:56–57`); **if no lock is active it returns and the mutation proceeds** — there is no requirement to hold a lock in order to write. Only a live lock held by another user throws `409 OBJECT_LOCKED` carrying the `LockSnapshot`. `LockSnapshot` (`lock-service.ts:10`) carries `id`, `workspaceId`, `objectType`, `objectId`, `lockedAt`, `expiresAt`, `lockedBy { userId, email, displayName }`, and the three unlock-request fields.

**Three distinct guarantees — do not conflate them.** (a) *Exclusion by an active lock:* while a live lock row exists and names another user, guarded mutations for that object are refused with `409`. This is the only guarantee the existing code provides, and it ends at expiry, at release, at force-unlock, or at any write path that does not call the guard. (b) *Draft protection:* a client that keeps editing locally after losing the lock holds an unsaved draft; the server holds no copy of it and cannot protect it. Protecting it (keep the text, warn, offer copy/export) is a client posture that must be specified per host; it does not follow from `409`. (c) *Atomic control at save:* the initiative `PUT` illustrates the gap — it checks the guard and then writes unconditionally (`api/src/services/business/initiatives.ts:451` calls the guard, `:505` performs the `update` with no version, base-hash or `WHERE expiresAt > now` condition in between). Between the check and the write a lock can expire and another writer can save, and the later unconditional write overwrites that save with no conflict detected: the classic check-then-write race. A host that needs “no silent overwrite after expiry” must add an atomic save control the current code does not have — for example a single transaction that re-checks lock ownership and expected version/base and writes conditionally, refusing with a conflict when either no longer matches. None of the options in §4 may cite `409` as evidence that (b) or (c) already exists.

**Lock API.** `spec/COLLAB.md` §“Lock API” lists: `GET /api/v1/locks?objectType=…&objectId=…` → `{ lock }`; `POST /api/v1/locks` → acquire/refresh, `201 { acquired: true, lock }` or `409 { acquired: false, lock }`; `DELETE /api/v1/locks?…` → release (owner or workspace admin); `POST /api/v1/locks/request-unlock`; `POST /api/v1/locks/accept-unlock` (transfer to requester); `POST /api/v1/locks/force-unlock` (admin only); `POST /api/v1/locks/presence`; `GET /api/v1/locks/presence?…`; `POST /api/v1/locks/presence/leave`. The router confirms the surface: `api/src/routes/namespaces/locks.ts:11` `LOCK_PATHS = ['/locks', '/locks/request-unlock', '/locks/accept-unlock', '/locks/force-unlock', '/locks/presence', '/locks/presence/leave']`, assembled by `createLocksNamespaceModule` with an author fence. The client mirror is `ui/src/lib/utils/object-lock.ts`: `fetchLock`, `acquireLock` (mapping `409` to `{ acquired: false }` and `403` to a lock re-read), `releaseLock`, `requestUnlock`, `acceptUnlock`, `forceUnlock`, `sendPresence`, `fetchPresence`, `leavePresence` (with a `sendBeacon`/`keepalive` leave path).

**Unlock request flow.** `spec/COLLAB.md` §“Unlock Request Flow”: the request is stored directly on the lock row (`unlock_requested_at`, `unlock_requested_by_user_id`, `unlock_request_message`); the owner accepts by transferring the lock to the requester (there is no explicit “refuse”); the request is cleared when the owner leaves the page (no timeout). The implementation matches and adds one rule: `requestUnlock` in `lock-service.ts` returns `{ requested: false }` when there is no lock or the caller owns it, and throws `409 'Unlock already requested'` when a different user already holds the request slot — so at most one pending requester exists per lock. `acceptUnlock` requires owner or admin, swaps `lockedByUserId` to the requester, renews the TTL, clears the three request fields, and notifies. `forceUnlock` requires admin and deletes the row. `releaseLock` requires owner or admin.

**Lock lifecycle (SSE and cleanup).** `spec/COLLAB.md` §“Lock Lifecycle”: all locks are purged at API startup (no persistence across restarts); locks are purged if a user has no active SSE connections; a periodic sweep removes expired locks and emits `lock_update` so clients can re-acquire. Notification in code is PostgreSQL `NOTIFY lock_events` with a JSON payload of workspace/object coordinates (`lock-service.ts`, `notifyLockEvent`), fanned out to the existing `/streams/sse` channel as `lock_update` / `presence_update` events per `spec/COLLAB.md` §“SSE Events”. `clearLocksForUser` deletes every lock of one user and notifies each affected object. Measured limits: locks do not survive a restart by design; expiry is time-based, not heartbeat-renewed beyond the client’s 30 s refresh; and the object types are the three host record kinds only — there is no paragraph, field, diagram-element, or cell granularity anywhere in this system.

**Lock UI and presence badge.** `spec/COLLAB.md` §“Lock UI”: a compact badge near the header actions — lock icon plus overlapping rounded avatars, owner’s avatar on top; hover tooltip “`n users connected, {Name} is locking the document, click to request unlock`”; click triggers request-unlock with no message prompt; admin force-unlock is a secondary action inside the tooltip; when the current user owns the lock the badge shows “You are editing”; the avatar list excludes the current user while the count includes them. §“Presence Badge (all roles)”: the badge is shown for viewer/editor/admin even in read-only mode; in read-only mode request-unlock is disabled and the tooltip omits the request wording; the read-only lock icon is hidden when the badge is visible; a requester’s avatar carries a small key overlay; the owner sees “Unlock for {user}” only when a request exists. The component confirms the contract: `ui/src/lib/components/LockPresenceBadge.svelte` takes `lock`, `lockLoading`, `lockError`, `lockOwnerLabel`, `lockRequestedByMe`, `isAdmin`, `isLockedByMe`, `isLockedByOther`, `avatars`, `connectedCount`, `canRequestUnlock`, `showHeaderLock`, and dispatches `requestUnlock` / `forceUnlock` / `releaseLock`. It computes initials locally, orders the owner’s avatar last in the stack, and renders the key overlay when `lock.unlockRequestedByUserId` matches an avatar. Most visible strings go through the injected i18n catalogue (`$_('locks.presence.…')`), but not all: the component declares a built-in English default `lockOwnerLabel = 'User'` (`ui/src/lib/components/LockPresenceBadge.svelte:10`), so “every string comes from the catalogue” is false of the existing badge. A DS badge must not copy that default; every label, including the owner fallback, comes from injected messages (§5, CB-0 witness 3).

**Presence (separate from the lock).** Presence answers “who is looking at this object”, independently of who may write. `api/src/services/lock-presence.ts:21` sets `PRESENCE_TTL_MS = 90_000` over an in-memory `Map` keyed by `workspaceId:objectType:objectId`. `recordPresence` upserts the caller with a `lastSeen` timestamp and emits `NOTIFY presence_events`; `listPresence` prunes entries older than the TTL and returns `{ users, total }`; `removePresence` and `clearPresenceForUser` delete and notify. Presence is therefore ephemeral, per-process, and lost on restart — acceptable for a “who is here” display, and a deliberate contrast with the persisted lock row. Roles gate the whole collaboration surface: `spec/COLLAB.md` §“Workspace Membership Roles” (`viewer` view-only, `commenter` view + comments, `editor` view + edit, `admin` all + lifecycle), §“Permission Enforcement” (viewers get `403` on mutations; the viewer UI is read-only — create/delete hidden, `EditableInput` and TipTap locked, a lock icon explains the state), and the COLLAB requirement cited by the h2a specification that editors are locked for a viewer. That viewer rule is already a DS component requirement (FE-2 §5.4, RED 1) and is reused unchanged by every option in §4.

**What L0 does not do.** While a lock is live, no second user can save through a guarded mutation path; that is weaker than “no second user can write”. After expiry (or via a path that skips the guard) a second user *can* write, and the initiative `PUT` then overwrites unconditionally (§2.2, three guarantees). There is no merge, no caret sharing, no per-paragraph granularity; a second editor’s only recourses while the lock is live are waiting, requesting, or (as admin) forcing. Presence shows object-level co-viewing only — no cursor, no selection, no “agent is working on this object” scope signal beyond the lock itself. The I2 agent-scope awareness of §2.1(a) has no delivered equivalent: the lock records a human user (`lockedByUserId` joined to `users`), and nothing in `lock-service.ts` or `lock-presence.ts` represents an agent, a declared scope of work, or a planned (not yet active) edit.

### 2.3 Canvas anchors in comments (SPEC_EVOL_COMMENTS and packages/comments)

`sentropic:spec/SPEC_EVOL_COMMENTS.md` (SCOPING v2 for `@sentropic/comments`, BR-42c) establishes the package posture that B2 mirrors for collaboration: the package is isolated (no Drizzle, no `pg`, no `api/` imports; the host supplies adapters), domain types and a `CommentStore` port live in the package with an in-memory reference adapter, wire events are transport-agnostic and mapped by the host onto `NOTIFY comment_events` / SSE `comment_update`, and identity/RBAC/presence are host concerns (“Presence / live cursors / unread-tracking UI → host”, §0 OUT of scope). The live comment model it generalises: `comments` table with `(contextType, contextId, sectionKey)`, flat threads sharing a `threadId` with no `parent_id`, thread-level cascade for assign/close/reopen, per-row content edit and per-row hard delete, and `toolCallId` provenance linking a comment to an AI tool call.

The package surface on `origin/main` matches: `packages/comments/src/types.ts:11` `CommentTargetKind`, `CommentTarget { kind, id, sectionKey?, recordType? }` with `sectionKey` preserved verbatim (`'description'`, `'matrix.cell.x.y'`, “a livedoc range, or a field path”), `CommentAuthor { id, kind?: 'human'|'agent'|'nhi', displayLabel? }` as an opaque host identity, and `CommentThreadSummary` promoted as a package surface with verbatim live field names for the host AI assistant. Two facts matter for B2. First, the target vocabulary already includes `canvas` and a free-form `sectionKey`, so a comment can anchor to a canvas object or a sub-range without a new kind — B2 needs no comment-model change to display discussions next to a locked or co-edited document. Second, the annotations evolution (`SPEC_EVOL_COMMENTS_ANNOTATIONS.md`) hardens anchors into versioned, hashed, immutable revisions with explicit resolver outcomes (exact match / source changed / unresolved / unavailable) and CAS on the annotation head. If L1/L2 ever move text under a comment anchor, that resolver — not a text match — is the mechanism that must report the anchor as moved or unresolved. B2 records this as an interface constraint (§6), not as work to redo.

### 2.4 The h2a edit-return contract and the FE-6 connected lot (CAS)

The DS owns none of this contract. It is pinned at h2a merge `98060bd0a` and read read-only via `git -C /home/antoinefa/src/h2a show 98060bd0a:<path>`. What B2 must stay compatible with:

**Identities and manifest.** `packages/focus/src/editing/contract.ts` at `98060bd0a` defines `Paragraph { paragraphId, blockKind: 'paragraph', parentId: null, order, range { start, end, unit: 'utf16' } }` inside `FocusEditingManifest { schemaVersion: 1, manifestId, documentRef, baseHash, manifestBaseHash, fields[], paragraphs[], retiredParagraphIds[] }`. `retiredParagraphIds` is durable mapping data, included in the digest projection, and prevents reallocation. `seedManifest` derives deterministic IDs once for a first baseline; later revisions use `carryManifest` with explicit retained IDs and must not reseed (`docs/focus/document-editing.md`, “Source profile and identity”). The five-tuple address is `(documentRef, nodeId, targetRef, field, paragraphId)`; array indexes, DOM paths, display order, content hashes, and ProseMirror/UTF-16 offsets are never identities (h2a spec D13, C4).

**Per-paragraph diff.** `ParagraphChange { paragraphId, changeId, operation: 'replace'|'insert'|'delete'|'move', before: string|null, after: string|null, beforeAnchors, anchors }` with `Anchors { parentId: null, previousParagraphId, nextParagraphId }` and explicit `null` boundaries. `diffParagraphs` compares identity-bearing baseline/draft values; splits keep the leading ID and insert fresh units, merges keep the leading ID and delete consumed units, moves preserve text (`docs/focus/document-editing.md`, “Source profile and identity”). The return envelope `FocusReturn` embeds the full manifest, typed `answers[]`/`notes[]`, and `editReturn { mode: 'cumulative', transactions[], supersedesReturnId?, supersededReturnIds[] }` — each frozen return states the complete desired delta against its named baseline and transports its full transitive ancestry, immediate predecessor first. Only `supersedesReturnId` is optional; absence means a lineage root with `supersededReturnIds: []`.

**Reconciliation: never silently overwrite third-party text.** `reconcile.ts` is pure (data in, data out; “Persistence and the final publication boundary belong to the host”). Its posture, confirmed in `docs/focus/document-editing.md` §“Cumulative reconciliation” and h2a spec D16/C7: a return already superseded by the registered head is refused and never applied, even if every `before` precondition still matches; a fork or an ancestry that does not prove succession is refused as lineage-order-indeterminate, fail-closed; same-paragraph divergence, a missing target, or an ambiguous mapping yields a structured conflict carrying baseline / lineage-applied (when it exists) / current / requested values; nothing of an atomic group applies if one member conflicts; third-party content changed after a lineage application is never overwritten by a revocation. Equality with an `after` string alone grants no attribution. Digests are RFC 8785 canonical JSON, UTF-8, SHA-256 with `sha256:` prefix (`digest.ts`); the inherited dossier `hash` is carried verbatim and proves nothing about a paragraph.

**FE-6: connected application with CAS.** The v3 specification defers connected multi-writer application to lot FE-6 (§1.3, §9 items 2–3: “Collaborative / multi-writer live editing: CRDTs, presence, simultaneous cursors, a document server… are NOT covered by the first increment”; “Connected application claims before FE-6” are excluded). FE-6 (§6) requires: two writers on the same base — the second never overwrites the first, an unrelated-part change rebases, a same-paragraph conflict blocks the whole batch, and the final check plus publication happen inside one compare-and-swap or equivalent single-writer boundary. Its RED list adds wrong-workspace / missing-item / unauthenticated refusal before any append, stale-`baseHash` detection by the host before append, three crash windows with receipt-based recovery, and live-delivery cases (producer present/absent/successor/wrong generation) that keep exported / delivered / processed / applied / recorded distinct. §5.5 and `docs/focus/document-editing.md` add the offline discipline B2 inherits: all cooperating offline producers share the state directory’s single-writer lock; the consumer re-checks source bytes immediately before publication, fsyncs a pending journal, atomically renames, then commits manifest, lineage, and receipt; non-cooperating writers outside the lock are explicitly not protected by a filesystem CAS. Measured consequence for B2: **the connected path already has a specified concurrency contract (OCC/CAS at publication, cumulative lineage, fail-closed ancestry). A CRDT live session, if added, must feed that contract at freeze/apply time; it does not replace it.** Section 4.5 works out the coexistence in detail.

**What FE-2 requires of the editor surface (h2a §5.7).** Controlled document in / transactions out; paragraph-identity attributes carried as editor attributes supplied by the Focus adapter, so ProseMirror positions and Tiptap JSON never leak into the wire contract; `editable`/`disabled`/read-only effective immediately (a locked editor cannot type, paste, or trigger any save — the viewer rule); selection and caret preserved across controlled external updates, with a concurrent external update during typing surfaced rather than silently overwriting local work; IME composition respected (no diff, no export capture mid-composition); undo/redo, Enter-split, and Backspace-merge preserving the D14 identity rules; labels injected by the host; no network, no persistence, no business API, no Track or Focus-model types inside the component; unmount leaves no listeners; mounting on demand per active field. The DS concretisation is FE-2 §5, summarised in §2.6.

### 2.6 The DS rich-text editor: FE-2 as specified, RT-0 as built

**FE-2 specification** (`spec/SPEC_EVOL_DS_RICH_TEXT_EDITOR.md` on `origin/main`, 703 lines; latest version on branch `feat/rich-text-core`, 803 lines — the delta adds the pinned-contract limits of §5.10 / M8 and the pure/`./editor` entry split; section numbers below follow the `feat/rich-text-core` version, which is the RT-1 input):

- Package: `packages/rich-text` (`@sentropic/design-system-rich-text`) with two entries that must never be conflated (§4.2). Entry `"."` is pure — model, messages, profile descriptors, theme mapping, document equality, the §5.6 external-update decision rules, capture/readiness state — importing no `@tiptap/*`, no `prosemirror-*`, no framework module, no DOM global. Entry `"./editor"` is the Tiptap-bound factory (`createRichTextEditor`): P0 extensions, the `preservedBlock` node, the live paragraph-identity plugin, `RichTextDocument` ↔ ProseMirror conversion with the `paragraphId` attribute, per-paragraph Markdown via `@tiptap/markdown`. Tiptap is a peer dependency (mirroring `packages/codemirror`); `@tiptap/markdown` is a runtime dependency reachable only from `"./editor"`. The Svelte adapter is exposed only via the subpath `@sentropic/design-system-svelte/rich-text-editor`; the barrel gains no rich-text export, so a Button/Card import never loads Tiptap (§4.2, RED-P).
- Controlled surface (§5): `RichTextDocument { format, blocks: [{ paragraphId, kind: 'paragraph'|'preserved', text?, raw?, preservedKind? }] }` in; `RichTextChangeEvent { document, gesture, representability }` out. **No-diff rule (blocking):** the component emits the complete document plus gesture provenance (`split`/`merge`/`paste` with fresh/retired identities) and representability flags — never a `before`/`after` pair, never anchors, never a baseline. The host adapter alone computes the per-paragraph diff with `@sentropic/focus/editing` (`diffParagraphs`) against its retained baseline. Baseline advancement happens only via `carryManifest` on a new acknowledged authoritative version — never on echo, freeze, export, or local edit (§5.3, with the A→B→undo-to-A witness: the second freeze must carry `transactions: []` against the still-retained baseline `A`).
- Identity carriage (§5.2): `paragraphId` node attribute rendered as `data-paragraph-id`; split keeps the leading ID and allocates fresh tail IDs through the injected `allocateId`; merge retires consumed IDs without reallocation; clear-field keeps the first block’s ID on the single empty block; undo restores identities by construction; internal paste allocates fresh IDs; external paste strips incoming `data-paragraph-id` before insertion, without exception.
- States (§5.4): `editable` (default `true`) and `disabled` (default `false`); effective editing is `editable && !disabled`, applied immediately via `setEditable` without remount; in a non-editable state typing, paste, drop, cut, and every mutation shortcut are inert — no mutation, no `onChange`, no save-like callback. This is the viewer/locked rule as a component property.
- External updates and IME (§5.6): a pure decision function returns exactly one of echo / defer / conflict / apply, evaluated in that order with composition and local divergence taking precedence over focus state. Echo suppresses replacement and records acknowledgement without advancing any baseline; composition defers the update until after the composition commit and its single `onChange`; local divergence (displayed ≠ last-acknowledged, focused or blurred) never overwrites local work and emits exactly one `onExternalConflict { incoming, local }`; otherwise the update applies with both selection ends re-anchored. `captureDocument()` is the deferred-capture surface: during composition it waits for the commit and resolves with the committed revision; pending captures at unmount reject once with the neutral `RichTextCaptureUnavailable` error; capture is a pure read that never mutates the live document.
- Representability (§6.6, non-mutating rule): a paragraph’s wire is exactly the untouched source bytes, or the literal `text/plain` mapping (`hardBreak` ⇔ `"\n"`), or the `@tiptap/markdown` bridge serialisation without post-processing. Representability (bridge re-parse deep-equals live content **and** the wire passes the pinned `assertParagraphText`) is a reported property via `RichTextRepresentability { nonRepresentableParagraphIds }`, never a transformation: capture never rewrites the draft to fit the limit. §5.10 generalises every residual refusal (pinned `assertParagraphText`, `validateManifest` range checks, §6.6 fixed-point failure) to “reported unsupported at export, draft preserved, no baseline advance”, with the single authorised input-side exception of the Shift+Enter no-op when a `hardBreak` would become the first child of a Markdown paragraph.
- Content profile P0 (§6.1–§6.4): only `paragraph` (with `paragraphId`), `text`, `hardBreak`, and marks `bold`/`italic`/`code` are editable; `preservedBlock` (atom, `contenteditable=false`) carries headings, lists, tables, code blocks, diagrams, blockquotes, images, and raw HTML verbatim. `StarterKit` is never enabled wholesale. Paste never creates a preserved block under the pinned contract (the return transports only `blockKind: 'paragraph'` values); a paste that would create a non-paragraph block is refused whole via `onUnsupportedPaste` with the document unchanged. Lists stay preserved until the three-condition gate (h2a evolution, new pin, joint FE-1/FE-2 witnesses) passes.
- No language, no network (§5.7, §5.9): every label comes from injected `RichTextMessages` with the marker form `⟦untranslated:rich-text.<key>⟧` plus `data-untranslated`; mount on demand, destroy on unmount with no surviving listener/observer/task; no `fetch`, `XMLHttpRequest`, beacon, remote asset, or network call of any kind, observed at runtime and not only by import scan.

**RT-0 code** (read-only, `git show feat/rich-text-core:packages/rich-text/src/<file>`): `model.ts` declares the type-only controlled model (`RichTextFormat`, `RichTextBlock`, `RichTextDocument`, `RichTextGesture`, `RichTextChangeEvent`, `RichTextUnsupportedPasteEvent`); `index.ts` (the `"."` entry) re-exports only pure modules (`model`, `messages`, `profile`, `identity`, `document`, `theme`) and states the side-effect-free invariant; `editor.ts` (the `"./editor"` entry) builds a real Tiptap `Editor` from `editor-extensions.ts` (granular extensions, `ParagraphWithIdentity`, atom `PreservedBlock`, `UndoRedo` from `@tiptap/extensions`, `Markdown` from `@tiptap/markdown`), installs identity/paste/composition handling, applies the pure §5.6 decision to the live instance, and implements deferred capture. `profile.ts` freezes the P0 extension-name list (`P0_EXTENSION_NAMES`) as data in the pure entry; `identity.ts` freezes `PARAGRAPH_ID_ATTRIBUTE = "paragraphId"` and its DOM names. `package.json` on that branch: `@sentropic/design-system-rich-text` 0.1.0, `private: true`, `license: MIT`, exports `"."` and `"./editor"`, Tiptap peers `^3.0.0` with dev pins `3.32.0`, dependency `@tiptap/markdown ^3.32.0`. ### 3.1 Rich-text document (the FE-2 editor) under each level

| Behaviour | L0 (object/field lock) | L1 (block lock) | L2 (CRDT + awareness) |
| --- | --- | --- | --- |
| Open a document someone else is editing | Read-only rendering; badge shows owner avatar + “{Name} is editing”; typing/paste inert | Paragraphs locked by others render read-only in place; free paragraphs stay editable | Fully editable; remote carets and selections visible in the text |
| Start editing | Acquire the lock (or wait / request it); badge flips to “You are editing” | Click a free paragraph to claim it; the claim is shown to others immediately | No claim step; typing merges with concurrent typing |

### 3.2 Agent (background) activity on a visualised object — intention I2

Today: not delivered (§2.1). ### 3.3 Diagram canvas (diagram-canvas)

Today: single-user; no presence, no lock, no caret sharing (§2.5). ## 4. Options

Four options were considered. Each is scored on: effort, risk, licence, offline behaviour, framework parity, fit with FE-2, and fit with the h2a contract. “Native” is interpreted per §1 in all four: no transport, persistence, or business API inside a DS package.

### Option A — L0 only, natively: DS lock/presence components + provider port, no CRDT

**Shape.** The DS ships: (1) a framework-neutral collaboration model in `packages/rich-text` `"."` (lock/presence value types, badge message keys, colour assignment as data); (2) a `LockPresenceBadge` component per framework adapter (Svelte first), functionally the sentropic badge of §2.2 re-expressed with DS tokens and injected messages; (3) an editor integration where the host drives `editable`/`disabled` from lock state and presence is rendered beside the field. The host implements acquire/refresh/release/request/accept/force and presence heartbeat against its own API (sentropic already has exactly this API, §2.2) and feeds snapshots into the components. No Yjs, no provider socket, no new dependency.

**Trade-offs.** Effort: lowest — the host protocol exists and is field-proven in sentropic; the DS work is one badge component, message keys, and tests. Risk: lowest; every failure mode is the known L0 set (expiry, stale badge, force-unlock) and the editor degrades to read-only. Licence: clean (no new dependency). Offline: the badge simply shows the last known state and the editor stays read-only or locally editable per host policy when disconnected; the offline `file://` dossier is unaffected because no lock exists there (single-user by construction). Framework parity: one small component to replicate per framework. Fit with FE-2: lock state maps onto the existing `editable`/`disabled` props and the §5.6 conflict channel is unused. Fit with h2a: at publication, FE-6 CAS remains the concurrency control; locks are an advisory UX layer in front of it, never a substitute. Two qualifications the earlier draft omitted: (i) the existing sentropic save path does **not** yet provide atomic control at save (§2.2 guarantee (c)) — a lock expiring mid-edit followed by a late save currently overwrites silently, because `requireLockOwnershipForMutation` accepts a mutation with no active lock (`lock-service.ts:57`) and the write is unconditional. A host adopting Option A that needs “no silent overwrite after expiry” must add that atomic control host-side (CB-2 prerequisite, §7); the DS badge cannot supply it. (ii) For sentropic `apiPut` surfaces (B1, §6.2) there is no Focus reconciler in the path at all, so no reconcile-time safety net exists there either — the same host atomic control is the only protection. Claiming FE-6 covers those surfaces would be false.

**Limits.** No simultaneous writing at all. Two users who both need the same document serialise completely. Agent-scope awareness (I2) is display-only. This option answers the owner’s “prévoir l'édition concurrente et le lock” literally — anticipate concurrency by locking — and nothing more.

### Option B — L0 + L1: block-level locks inside the document

**Shape.** As Option A, plus: the editor claims/releases individual `paragraphId` blocks through the provider port; locked blocks render with the holder’s colour/avatar and are locally non-editable (`contenteditable=false` per block, in the manner of `preservedBlock`); unclaimed blocks stay editable; the host stores block locks (sentropic’s `object_locks` generalised from `(objectType, objectId)` to `(objectType, objectId, blockId)` or an equivalent host schema — host-side, not DS). Undo, paste, and structural gestures that would touch a locked block are refused locally with the same “refused whole, document unchanged” discipline as the P0 paste rule.

**Trade-offs.** Effort: medium. The DS needs per-block lock rendering, claim-on-focus/release-on-blur-or-idle UX, gesture guards spanning locked blocks (select-all, paste-over-selection, merge across a boundary), and a `Focus`-compatible story for what a block-locked draft means at freeze time (locked blocks are simply absent from my diff — they are not my `before` values to change, which the identity-bearing diff already expresses). Risk: medium. New failure modes: lock leakage on crash (mitigated by the same TTL pattern), “paragraph held by a user who left” (presence TTL + force-release), and structural disputes (who may split a locked paragraph — answer: nobody but the holder; the gesture is refused). Licence/offline/parity as Option A. Fit with FE-2: good, but it consumes editor complexity budget before L2 exists; per-block non-editable ranges inside a ProseMirror document are a real plugin (the preserved-block guard is the precedent). Fit with h2a: good — disjoint block edits rebase cleanly under D16 (unrelated-part change rebases; same-paragraph divergence conflicts), so L1 drafts compose with FE-6 without contract change.

**Limits.** Still no same-paragraph concurrency. The “two people in one document” case works; the “two people in one paragraph” case serialises. L1 is the highest-complexity option per unit of concurrency gained, because every structural gesture must reason about lock boundaries.

### Option C — L0 now, L2 behind a provider port designed into RT-1 (recommended)

**Shape.** Two stages behind one port. Now (with RT-1): ship Option A’s L0 components and port, **plus** the L2-ready editor seams (§5): a `CollaborationProvider` port injected by the host and a document-binding slot in `"./editor"` that can bind the ProseMirror document either to the controlled value (today) or to a `Y.XmlFragment` (later) without changing the component’s public props. Stage one ships **no awareness caret rendering** — remote carets/selections are a stage-two surface (§5.2, §9); RT-1 reserves only the binding slot and the identity discipline, so nothing in stage one displays a caret. Later (own lot, own gate): the host supplies a Yjs provider (Hocuspocus or other, host-side), the `"./editor"` entry enables `@tiptap/extension-collaboration` + `extension-collaboration-caret` behind the slot (this is where awareness rendering lands), paragraph identities are carried as stable node attributes through the CRDT (§4.5), and freeze/apply still goes through the host publication authority (§4.5). L1 is **not** built for text. That is a product choice, not a capability ranking: concurrent merge (L2) and exclusive reservation (L1) answer different needs — merge lets two writers share one paragraph, reservation guarantees one writer exclusive use of a block (review, attestation, regulated drafting). L2 does not subsume that guarantee; choosing L2 over L1 for text means accepting that no exclusive-block guarantee will be offered for text, in exchange for avoiding the L1 gesture-guard complexity. If the owner stops after stage one, the delivered system is Option A — complete, not a stub.

**Trade-offs.** Effort: stage one ≈ Option A plus a small, testable provider slot and identity discipline designed into RT-1 (the cost is design discipline now, not code volume; no awareness surface ships in stage one); stage two is the large lot (binding, awareness rendering, identity-through-merge proofs, offline merge witnesses, Hocuspocus host integration in each consuming host — never in the DS). Risk: stage one low; stage two medium-high and explicitly gated (§7). The principal stage-two risks are named and owned in §4.4–§4.5: undo-manager replacement, caret rendering under the DS token/theming rules, `paragraphId` survival through merges, and the freeze-time bridge from a live Yjs document to a cumulative per-paragraph return. Licence: all MIT, no Pro/cloud (§4.7), with new pins (`yjs`, `y-protocols`, `y-prosemirror` or `@tiptap/y-tiptap`, `@tiptap/extension-collaboration(-caret)`) entering only at stage two, only as `"./editor"`-reachable peers/dependencies, and only with the licensing guard regenerated in the same commit. Offline: stage one as Option A; stage two keeps the offline dossier path byte-identical (no provider → controlled mode) and adds Yjs offline editing only inside connected hosts that explicitly enable it (local persistence provider is a host choice; its package is `unknown` until pinned, §2.7). Framework parity: the port model is framework-neutral data; each adapter renders carets (stage two) in its idiom, staged per framework exactly like the editor itself (FE-2 §4.3). Fit with FE-2: stage one is exact; stage two extends §5.6 rather than replacing it (§4.5). Fit with h2a: stage two is designed against FE-6 from the start — the CRDT session is a live-editing transport between freezes, and every publication still passes OCC/CAS reconciliation (§4.5).

**Limits.** Real concurrent editing is not delivered by stage one and must never be announced as if it were. Stage two needs a host document server (or peer provider) that the DS does not provide; a purely offline product gets locks and presence, not co-editing.

### Option D — L2 directly in the DS core (Yjs as a DS dependency, no L0 stage)

**Shape.** Skip locks; make `Y.Doc` the editor’s document model, ship the collaboration extensions from the start, treat the controlled value as a serialisation of the CRDT.

**Assessment — rejected, on its real costs.** Two arguments sometimes made against D do not hold and are withdrawn. A local `Y.Doc` needs no server: Yjs merges replicas from binary updates that any transport (or a file, or a test) can carry, so a CRDT-mandatory editor does not intrinsically forbid `file://` use. Nor does a CRDT prevent a host from retaining a baseline and computing the per-paragraph diff host-side at freeze — §4.5 does exactly that. The rejection rests instead on costs that survive those corrections. (1) **Dependencies and qualification surface:** D pulls `yjs`, `y-protocols`, the ProseMirror binding and the caret stack into every consumer from day one, including single-user and offline consumers that gain nothing, and every one of those pins needs licensing, `pack:smoke` and four-framework qualification before the first field is validated. (2) **Controlled-contract change:** FE-2’s surface is a controlled value in / document-plus-gesture out, with the host retaining the baseline (§2.6); making the CRDT the document model inverts that contract for every consumer, so the FE-2 witnesses (including the A→B→undo-to-A cumulative witness) must be re-proved in bound mode before any consumer — even a single-user one — can adopt the editor. (3) **Undo/history migration:** P0 ships ProseMirror `UndoRedo`; Tiptap collaboration warns it is incompatible with its own history (§2.7), so D forces the Yjs `UndoManager` migration (§4.4) up front, before the single-user editor is validated. (4) **History and migration:** existing controlled-mode consumers and their stored documents would need a CRDT seeding/migration story on day one, with no L0 fallback for hosts that cannot run the new path. Option C keeps the same CRDT available behind a port for hosts that opt in, without imposing any of these four costs on the others. D is recorded so the rejection is traceable; no lot implements it.

### 4.4 Interaction with undo/redo, IME composition, read-only/disabled, and §6.6

These four interactions bind every option; L2 changes two of them materially.

**Undo/redo.** L0/L1: unchanged — ProseMirror history (`UndoRedo` from `@tiptap/extensions`, FE-2 §6.1) in a single-writer document; undo restores `paragraphId`s by construction (FE-2 §5.2). L2: the history must become the Yjs `UndoManager` (via `yUndoPlugin` / Tiptap collaboration), which undoes only the local user’s tracked origins — the correct multi-writer semantics (§3.1: my undo never removes a collaborator’s text) and the only available one, since a global ProseMirror history in a merged document would revert remote changes. Consequences that stage two must prove, not assume: (a) the P0 extension list changes exactly once (remove `UndoRedo`, add the collaboration pair) behind the binding slot, never per-session toggling; (b) undo of a split/merge still restores the same logical paragraph’s identity — now a CRDT property (the identity attribute rides the `Y.XmlElement`, §4.5) requiring a merge-interleaved undo witness; (c) `protectedNodes = {'paragraph'}` (y-prosemirror default) interacts with the DS `preservedBlock` atom — preserved blocks must be excluded from collaborative mutation entirely (see below), so the undo delete-filter needs a DS-side witness with preserved blocks present. Until stage two, RT-1 must not mix the two histories: enabling collaboration extensions alongside `UndoRedo` is the warned-against configuration (§2.7) and is a lot failure if shipped.

**IME composition — one rule, two kinds of arrival.** FE-2 keeps two deferrals apart and B2 must not merge them. *Content* arrivals are deferred: §5.6 forbids emitting or capturing mid-composition and defers an external controlled value update until after the composition commit. *Rights* arrivals are not content and are never deferred: FE-2 §5.4 (`feat/rich-text-core:spec/SPEC_EVOL_DS_RICH_TEXT_EDITOR.md:340`) requires `editable`/`disabled` to take effect immediately on the live editor via `setEditable`, without remount. The earlier draft’s sentence deferring a lock-driven `editable` change “to a gesture boundary” is withdrawn — it imported the content rule into the rights rule and contradicted §5.4. Single rule adopted here (to be carried as an FE-2 delta note and witnessed by CB-1, not presented as already acquired): (1) a host-driven revocation (`editable: true → false`, for lock loss, force-unlock, role change or session revocation) applies immediately, even mid-composition — the editor calls `setEditable` at once; (2) the in-progress composition is terminated without a commit: its uncommitted text is discarded, the displayed document reverts to the last committed revision, no `RichTextChangeEvent` is emitted for the discarded text and no save-like callback follows from it; (3) a `captureDocument()` call that was waiting for that composition commit does not hang and does not resolve with discarded text — it rejects exactly once with `RichTextCaptureUnavailable` (the same neutral error as the unmount case, FE-2 §5.6), and the host may re-capture the reverted revision once readiness returns; (4) events already emitted *before* the revocation are not retracted by the DS — whether an in-flight host save carrying such an event is accepted is decided by the host’s atomic save control (§2.2 guarantee (c)), never by the editor; after the revocation the editor emits nothing and every mutation path (typing, paste, drop, cut, shortcuts) is inert. L2 is the remaining delicate case: a remote Yjs update can arrive mid-composition and ProseMirror will apply it to the document under the composing user. That is a *content* arrival inside the bound document, not a controlled value update, so §5.6 deferral does not route it through `onExternalConflict` (§4.5); y-prosemirror’s sync plugin handles remote transactions during composition by design, but the DS-level guarantees must be re-witnessed in stage two: no `onChange` mid-composition, the committed composition emits exactly one coalesced change, deferred capture resolves with the committed revision, and the local caret (expressed via relative positions for sharing) does not jump when a remote insert lands before it. The rights rule above applies unchanged in bound mode: a session revocation mid-composition revokes immediately and discards the uncommitted composition. jsdom cannot witness real IME behaviour (FE-2 §11 reserves it for the browser suite); stage two inherits that constraint.

**Read-only / disabled.** Unchanged in meaning at every level: `editable={false}` (viewer, locked-by-other, preserved) keeps text selectable/copyable with no mutation path; `disabled` removes focusability; both take effect immediately and emit nothing (FE-2 §5.4). Collaboration adds two compositions, both host-driven: (1) L0/L1 map lock state onto these props — the editor itself never calls a lock API; (2) L2 with a read-only permission mounts the same document binding with the sync plugin in a non-editable view (remote updates still render; local mutation is inert, including paste and shortcuts — RED 1 applies verbatim). A collaboration session must never widen permissions: awareness shows who is present, the host decides who may write, the editor enforces `editable && !disabled` locally regardless of what the provider delivers.

**§6.6 representability.** The non-mutating rule is load-bearing for L2. A remote merge can produce a paragraph whose live content is non-representable (whitespace-only, leading/trailing break, bridge non-fixed-point). §6.6 already answers this without amendment: the paragraph is flagged through `RichTextRepresentability`, the draft is preserved exactly as merged, capture returns the candidate wire plus the flag, and export of that paragraph is reported unsupported under §5.10 — collaboration never “repairs” a merged paragraph to make it exportable, and no merge step may trim, reorder, or normalise live content. One addition stage two must make explicit: representability is evaluated on the merged live content at emission/capture time (as now), so two individually representable paragraphs that merge into a non-representable one are flagged once, on the result — never blamed on either writer, never blocked at input time. The Shift+Enter no-op exception stays local and Markdown-only; it has no collaborative counterpart.

**Preserved blocks under L2 (blocking constraint).** `preservedBlock` nodes carry verbatim source slices (`raw`) that the pinned h2a contract cannot transport as edits (§2.6, paste rule). In a Yjs-bound document they must be treated as immutable atoms owned by the host segmentation: present in the shared fragment for rendering context, excluded from collaborative text mutation, and re-spliced host-side exactly as in controlled mode. If a stage-two design cannot keep preserved slices byte-identical through arbitrary merges (including a collaborator deleting adjacent paragraphs), L2 applies to paragraph-only fields and preserved-bearing fields stay in controlled/L0 mode. This is a gate (§7), not a hope.

### 4.5 Compatibility with the h2a edit-return contract

This is the section the CRDT proposal stands or falls on. The contract (§2.4) is not renegotiated; the question is how a live Yjs document and the FE-2 controlled-value surface coexist with it.

**Do paragraph identities survive CRDT merges?** They must, by construction, and the construction is available: the DS already carries `paragraphId` as a ProseMirror node attribute on `paragraph` (§2.6). In the y-prosemirror binding, node attributes map onto `Y.XmlElement` attributes, so the identity rides the shared element itself rather than a position, an index, or a text offset. A concurrent split creates a new element (fresh ID via the injected allocator, exactly as §5.2 requires); a concurrent merge deletes one element (its ID retires, never reallocated — the host manifest’s `retiredParagraphIds` discipline); concurrent character inserts inside one element interleave without touching its identity attribute. Three failure modes must be excluded by witnesses, because each would silently corrupt the diff: (1) two collaborators splitting the same paragraph concurrently must not produce two tails carrying the same fresh ID — the allocator is per-session, so IDs must be collision-free across sessions (host-issued or UUID-class; deterministic producer seeding is a baseline operation, never a live-session operation); (2) an undo/redo across a merge must restore the same logical ID (attribute carriage, as in controlled mode); (3) external paste inside a session must still strip incoming `data-paragraph-id` before insertion (§5.2), now with the additional reason that a pasted ID could collide with a live remote element. With those witnessed, identity survival is a property of the binding, not of text matching — which is precisely what D13/C4 demand (never repair identity by approximate text matching).

**Does the per-paragraph diff against a retained baseline still hold?** Yes — at freeze time, unchanged. The live session is a transport between two freezes: the host retains the baseline manifest (the posture FE-3 will be required to implement once qualified — at the pin FE-3 is not yet qualified, `h2a:docs/focus/document-editing.md:6` records the first increment as not qualified, so this is a future host requirement, not a delivered behaviour), the session edits a Yjs document seeded from that baseline’s paragraphs, and at freeze the host captures the current blocks (`captureDocument()` semantics: complete document, identities, representability flags), maps blocks to `ParagraphValue[]` through the manifest identities, and computes `diffParagraphs` against the retained baseline. Repeated typing, remote merges, splits, and undos all coalesce into that one baseline-relative cumulative delta — the same statement FE-2 §5.3 makes for controlled mode (“typing to B then undoing to A yields the empty cumulative diff”), now with “merged to B” in place of “typed to B”. The DS component still computes no diff and retains no baseline in either mode.

**OCC/CAS and “never silently overwrite third-party text”.** The reconciler’s guarantee is about publication, and publication still happens exactly once per frozen return, under FE-6’s single CAS/single-writer boundary. What changes is what “third-party text” means at freeze time: inside a live session, collaborators’ merged text is not third-party divergence to be conflicted — it is the session’s joint draft, attributed by the session (the return’s production/scope facts are host-supplied; per-paragraph authorship inside a session is awareness data, not return data, unless a future contract version carries it — `unknown`, §8 Q5). Third-party divergence remains everything outside the session: a source change made by another path (offline return applied meanwhile, another session on a stale base, a filesystem edit) between baseline retention and freeze application. That case is handled at the host boundary, not inside the reconciler: the reconciler (`h2a:packages/focus/src/editing/reconcile.ts`) is pure — data in, data out; it reads no source and publishes nothing. The **host** re-reads the current source and lineage immediately before publication, passes `baseline` / `current` / `value` / `lineage` to `reconcile()`, receives the candidate, receipt and conflicts, and publishes atomically only on `ok`. On same-paragraph divergence the result carries baseline / lineage-applied (when it exists) / current / requested and nothing of the batch is published. A CRDT therefore **extends** the FE-2 §5.6 model; it does not replace it. Precisely: §5.6 governs host-controlled value updates in controlled mode (echo/defer/conflict/apply). In a bound (L2) session, remote Yjs transactions are not “external controlled updates” and must not be routed through `onExternalConflict` — they are the document. §5.6 continues to govern (a) every controlled-mode field, (b) the session’s start (seeding from the controlled value) and end (freeze capture), and (c) any host attempt to replace the whole value mid-session, which in bound mode means: end the session or surface a session-level conflict — never a silent `setContent`. The two modes share the component, the identity rules, the capture discipline, and the freeze bridge; they differ in what may mutate the document between captures. Stating this as “CRDT replaces §5.6” would break FE-3’s witnesses; stating it as “CRDT extends §5.6 with a bound mode beside the controlled mode” preserves them.

**Collective freeze: who holds the head, who serialises returns (blocking).** Convergence of the Yjs documents does not by itself produce a valid return lineage. Two participants freezing independently from the same previous head mint two returns that both name that head as predecessor; the pinned reconciler refuses the second as a fork (`h2a:packages/focus/src/editing/reconcile.ts:110–114`: succession must be proved from `supersededReturnIds`, otherwise `lineage-order-indeterminate`, fail-closed), even when their texts converged. The host therefore owns a *publication authority* per `documentRef`, with four duties the DS never carries. (1) *Common head:* the host holds the single lineage registry for the document — current head (`returnId` + full `supersededReturnIds` chain), applied transactions, seen return ids/digests, tombstones — and every session is opened against that head (§4.5 session/base discipline). Participants never mint returns and never choose a predecessor; they produce captures of the joint draft. (2) *Serialised freeze:* a freeze is a collective operation on the session, executed once by the host under a per-document single-writer boundary (mutex, CAS on the head, or equivalent). The host captures the converged session document once — verifying that the replicas it freezes from agree on the document state (state-vector / capture equality); replicas that have not converged (offline partition) are merged or the freeze waits, never silently choosing one replica. It then computes the cumulative diff against the retained baseline and mints exactly one return whose `supersedesReturnId` is the current head and whose `supersededReturnIds` carries the full transitive ancestry, immediate predecessor first. Whether any authorised participant may request that collective freeze or only a designated lead may is the owner choice Q7 (§8); the serialisation itself is a contract consequence, not a preference, and is never voted. (3) *Publication and re-check:* immediately before publication the host re-reads the current source bytes and head (the reconciler does not), runs the pure `reconcile()`, and publishes only inside the same CAS/single-writer boundary (FE-6). If the source or head moved between capture and publication — external edit, another session’s return applied, inverted delivery of two returns — the host does not publish the stale mint: unrelated paragraphs rebase through retained identity, same-paragraph divergence conflicts with the draft preserved, and a head that has advanced forces a re-freeze against the new head (new cumulative return naming it), never a fork. Delivery order therefore cannot create lineage: returns arriving out of order are ordered by the host registry, and a return whose ancestry does not prove succession from the registered head is refused, not queued into validity. (4) *Recovery:* the host journals the pending freeze (capture, minted return id, head named) before publication, fsyncs and atomically commits manifest, lineage and receipt together (the §2.4 offline discipline); on crash or reconnect the journal is replayed idempotently — a return id already seen reports its original receipt (`already-processed`), a superseded mint is tombstoned, and offline edits made during the partition re-enter only as a new capture to be merged and re-frozen, never as a second return on the old head. Session provenance (which session, which participants the host can prove) rides the return’s host-supplied production/scope facts; per-paragraph attribution is not implied (Q5).

**Session/base discipline (the rule that keeps FE-6 intact).** A live session is always opened against a named retained baseline (`documentRef`, `baseHash`, `manifestBaseHash`) **and a named lineage head** (the host registry’s current return, §4.5 collective freeze). The session record the host keeps — opaque to the DS, defined host-side — binds `sessionId`, `documentRef`, `field`, baseline hashes, head `returnId` at open, and the actor roster; the `"./editor"` binding receives only the fragment/awareness objects for that session (§5.1). If the authoritative source moves under an open session (another return applied), the host has exactly two legal moves: keep editing and let the freeze-time host re-check rebase/conflict (the default), or close and re-seed the session on the new baseline with the draft preserved as an explicit import — the C16/§5.5 draft-continuity rule. Re-seeding silently, reseeding identities, or advancing the baseline mid-session are prohibited for the same reasons FE-2 §5.3 prohibits baseline advance on echo/freeze/undo. An empty merged delta freezes to the empty cumulative return (with lineage carried forward) exactly as in controlled mode. Two qualifications stay separate and must not be announced as one: the DS client binding (CB-3) can be qualified producing a candidate capture/return against a test-double publication authority; a *connected publication* claim — live multi-writer returns actually applied to the authoritative source — additionally requires the FE-6 host gate (CAS publication, re-check, crash-window recovery, live-delivery cases, §2.4). The h2a specification excludes connected-application claims before FE-6; CB-3 green alone therefore announces at most “concurrent editing client qualified”, never “connected publication delivered”.

### 4.6 One lock and presence model for text, diagrams, and spreadsheet?

**What can be shared (proposed: yes).** The arbitration vocabulary is surface-independent: a claim is `(scopeRef, unitRef, holder, expiresAt, unlockRequest?)` where `scopeRef` is the host object (document, diagram, sheet) and `unitRef` is an opaque host reference to the claimed unit — a `paragraphId` for text, an occurrence/entity ref string for a diagram element, a cell/range ref for a sheet. Presence is `(scopeRef, actor, lastSeen)` with ephemeral TTL semantics. The DS can therefore ship one neutral model (types, TTL/expiry helpers as pure functions, badge/avatar/colour/message vocabulary, the provider port shape of §5) consumed by three thin surface integrations, exactly as `CommentTarget` generalises `(contextType, contextId, sectionKey)` without the package enumerating host record kinds (§2.3). The sentropic precedent supports the shape: one `object_locks` discipline with a closed `LockObjectType` enum host-side, one badge component, one presence service. The DS generalisation keeps the enum host-side (opaque strings) and standardises only the protocol and the rendering.

**What cannot be shared (must stay per-surface).** (1) Unit granularity and claim UX: paragraph claim-on-focus, diagram element claim-on-select, and range claim-on-select are different gestures with different expiry expectations. (2) Merge semantics: text can CRDT-merge inside a unit; diagram geometry is given no merge in this study (§3.3, §9), and spreadsheet merge semantics belong to B3 inside the Q8 ambition — for diagrams the shared contract tops out at arbitration, and for the spreadsheet it tops out at whatever Q8 selects. (3) The model each surface edits: diagram refs belong to the diagram-core meta-model (owner rule; the DS collaboration package must not import it — layering guard, §2.6 — so refs cross as opaque strings and are interpreted host-side); spreadsheet refs belong to B3’s model. **Conclusion:** one *lock/presence contract + presentation* model, three *arbitration* integrations. Claiming one concurrency semantics for all three would be false for diagrams and pre-empts the joint spreadsheet decision.

### 4.7 Security and licensing

- **Licences.** Every pinned collaboration dependency is MIT: `yjs` 13.6.33, `y-prosemirror` 1.3.7, `@tiptap/extension-collaboration` / `extension-collaboration-caret` / `y-tiptap` (Tiptap v3.32.0 line), `@hocuspocus/server` / `provider` 4.7.1 (§2.7). MIT enters MIT DS packages without the LGPL prohibition being triggered; no LGPL, EPL, or proprietary code is involved. Each stage-two addition still passes the repo gates in the same commit that introduces it: `LICENSE.THIRD-PARTY.md` regenerated (`notices:generate`), publishable-count assertion updated if a package flips publishable, `pack:smoke` wiring for every new entry/peer (§2.6). Behavioural reference versus code reuse follows the owner rule, cumulatively: consuming a public API (calling Yjs, the binding, or a provider behind the port) is ordinary dependency use under that dependency’s licence. Copying or adapting any file (source, test, or data) from another repository into a DS package is permitted only when **both** conditions hold together — (a) the source licence is compatible with the MIT DS packages, **and** (b) the owner has agreed to that reuse — recorded per file in the lot report (source path, licence, owner agreement reference). A “licence note” alone never authorises a copy; a compatible licence alone never authorises one either. LGPL code satisfies neither path into MIT DS packages (§4.7, owner rule).
- **No Tiptap Pro, no cloud.** The collaboration extensions are in the open-source Tiptap monorepo at the pinned version and depend on `yjs`, not on any Pro package (§2.7). `TiptapCloudProvider` (named only in the caret extension’s JSDoc, its provider option being typed `any`, §2.7) is the paid hosted service and is prohibited: no DS or host lot under this study may require a Tiptap account, a cloud document, or a runtime call to Tiptap infrastructure. The same prohibition covers Hocuspocus Cloud or any hosted CRDT SaaS as a *required* dependency; a host may choose its own infrastructure, but the DS must remain fully functional with a self-hosted provider (the test double qualifies the client binding only, §7 CB-3).
- **Hocuspocus stays host-side.** The server (WebSocket fan-out, `onAuthenticate`/`onLoadDocument`/`onStoreDocument`, database extensions) is transport, persistence, and auth — three things the DS boundary excludes (§1). It therefore appears in this study only as one possible host implementation behind the provider port. No DS package imports `@hocuspocus/*`; a host that uses it owns authentication (the hook is where workspace membership is checked — the DS never asserts identity, mirroring the comments package rule that the package stores opaque identities and the host gates them, §2.3), owns the database, and owns the decision to run it at all.
- **Offline packaging.** Stage one (L0) adds no network dependency to any DS artefact: the offline `file://` dossier mounts the editor in controlled mode with no provider and no lock service, byte-identical to today. Stage two must preserve that property structurally: Yjs and the provider client load only through the `"./editor"` collaboration binding, only when the host injects a provider; importing `"."` or mounting a controlled editor loads no CRDT code (witnessed by the RED-P packaging test extended to the collaboration graph). A no-CDN offline capability remains possible in both stages: every runtime dependency is bundled from the lockfile, no font/script/style is fetched, and the component performs no network access of its own (FE-2 §5.9 runtime observation, extended to assert that any socket is opened by the host-injected provider object, never by DS code).
- **Security posture of the protocol itself.** Awareness data (names, colours, caret positions) is display data supplied by the host; the DS sanitises the one injectable value it renders (caret colour validated to `#RRGGBB`, else `transparent` — the caret extension’s own rule, adopted for the DS renderer) and treats user labels as text, never markup. Lock/presence snapshots are host-authoritative: the DS renders what the host sends and never grants write access itself — `editable` remains a host decision enforced locally, so a forged “you hold the lock” snapshot can at most make a field typeable locally; publication still passes the host’s mutation guard (sentropic’s `409 OBJECT_LOCKED`, §2.2) and FE-6 reconciliation. Pasted or merged content stays inert under the P0 profile (FE-2 RED 7) in both modes; collaboration adds no HTML-rendering path.

## 5. Recommendation — `ds-proposition`

**Adopt Option C: L0 first, L2 behind a provider port, with the L2 seams designed into RT-1 now and L1 not built for text.**

In one paragraph: ship the sentropic-proven L0 protocol as DS components in the RT-1 timeframe (badge, presence, lock-driven `editable`, injected messages, host-implemented API); design three seams into RT-1 at the same time — (1) opaque block identities already carried by the editor are declared stable under a future CRDT binding, (2) the capture surface stays mode-neutral (a `captureDocument()` between two points returns the current document and representability whichever mode produced it; change *notification* is specified separately in §5.2 and is not claimed neutral yet), and (3) a host-injected `CollaborationProvider` slot exists in `"./editor"` from the start, unused in controlled mode; then deliver real concurrent editing (Yjs + y-prosemirror via the Tiptap collaboration extensions, Hocuspocus or equivalent strictly host-side) as a separate gated lot that must prove identity-through-merge and the freeze-time bridge to the cumulative h2a return before any “collaborative editing” claim is made — with connected publication announced only after the FE-6 host gate (§4.5). For diagrams, adopt the shared protocol + presentation model of §4.6 at L0/L1 granularity; for the spreadsheet, adopt the same lock/presence contract only at the ambition the joint B2/B3 owner decision selects (Q8, §8) and only with its grid lot — do not promise merged concurrent geometry or cell editing under this study.

### 5.1 The provider port (DS side; host implements transport)

The port is framework-neutral data plus callbacks, living in the pure `"."` entry as types and in `"./editor"` as the binding consumer. It carries no URL, no socket, no serialised Yjs update, and no Focus/Track type.

```ts
// packages/rich-text/src/collaboration.ts (pure entry, types + pure helpers only)
export type CollaborationActorKind = 'human' | 'agent' | 'nhi';

export type CollaborationActivity = {
  scopeRef: string;         // object the activity concerns, opaque host ref
  state: 'viewing' | 'holding' | 'planned' | 'yielded';
  since: string;            // ISO timestamp, host-supplied
};

export type CollaborationActor = {
  actorId: string;          // opaque host identity
  kind: CollaborationActorKind; // host-decided; 'agent' carries I2 scope display (§3.2)
  displayLabel: string;     // host-supplied, rendered as text
  color: string;            // host-supplied; DS validates #RRGGBB else falls back
  activity?: CollaborationActivity; // present iff the host can prove it; DS invents none
};

// Injected capabilities: badge states are derived from snapshots PLUS these
// facts. Snapshots alone carry neither role nor capability (see CB-0).
export type CollaborationCapabilities = {
  currentActorId: string;
  canAcquire: boolean;      // false for viewer/commenter roles
  canRequestUnlock: boolean;
  canForceUnlock: boolean;  // admin only, host-decided
};

export type LockUnitRef = {
  scopeRef: string;         // host object ref (document / diagram / sheet), opaque
  unitRef?: string;         // paragraphId | diagram element ref | cell/range ref, opaque
};

export type LockSnapshot = {
  unit: LockUnitRef;
  holder: CollaborationActor | null;
  expiresAt: string | null; // ISO; null when no lock
  unlockRequestedBy?: CollaborationActor | null;
};

export type PresenceSnapshot = {
  scopeRef: string;
  actors: readonly CollaborationActor[]; // co-viewers, current actor excluded by host or DS per badge rule
  total: number;
};

// Host-injected. Every method is host transport; the DS never opens a socket.
export interface CollaborationProvider {
  acquireLock(unit: LockUnitRef): Promise<{ acquired: boolean; lock: LockSnapshot }>;
  refreshLock(unit: LockUnitRef): Promise<LockSnapshot>;
  releaseLock(unit: LockUnitRef): Promise<void>;
  requestUnlock(unit: LockUnitRef): Promise<LockSnapshot>;
  acceptUnlock(unit: LockUnitRef): Promise<LockSnapshot>;
  forceUnlock(unit: LockUnitRef): Promise<void>;
  recordPresence(scopeRef: string): Promise<PresenceSnapshot>;
  leavePresence(scopeRef: string): Promise<void>;
  subscribeLock(unit: LockUnitRef, onSnapshot: (s: LockSnapshot) => void): () => void;
  subscribePresence(scopeRef: string, onSnapshot: (s: PresenceSnapshot) => void): () => void;
  // L2 only (stage two): present iff the host offers a live session.
  // The Y.Doc / fragment / awareness objects stay behind this boundary;
  // no yjs type appears in the pure entry.
  openLiveSession?(input: {
    scopeRef: string;
    actor: CollaborationActor;
  }): Promise<LiveSessionHandle>;
}

export interface LiveSessionHandle {
  // Opaque to the pure entry and to framework adapters.
  readonly kind: 'live-session';
  readonly sessionId: string; // host session record key (§4.5); opaque to the DS
  dispose(): Promise<void>;
}
```

The pure handle deliberately carries no Yjs object. The binding contract lives only in the `"./editor"` graph, where Yjs types are already reachable:

```ts
// packages/rich-text/src/editor-collaboration.ts ("./editor" graph only;
// may import yjs / y-protocols — never imported from the pure entry)
import type * as Y from 'yjs';
import type { Awareness } from 'y-protocols/awareness';

export interface LiveSessionBinding {
  fragment: Y.XmlFragment;  // the shared fragment for this field's document
  awareness: Awareness;     // presence/caret channel for this session
}

// Implemented by the host alongside CollaborationProvider. The DS binding
// calls resolveBinding once at mount and releases it at unmount; framework
// adapters never receive the fragment, the doc, or the awareness object.
export interface LiveSessionBindingSource {
  resolveBinding(handle: LiveSessionHandle): LiveSessionBinding;
  releaseBinding(handle: LiveSessionHandle): void;
}
```

Host-side session record (not a DS type): the host binds `sessionId` to `(scopeRef, field, baseline hashes, lineage head at open, actor roster)` (§4.5). That link stays opaque in the DS — the editor receives a handle plus, through `resolveBinding`, the fragment/awareness pair for exactly that field — but it must exist host-side before any session opens; a handle that resolves to no binding, or to a binding for a different field, is a host conformance failure (CB-3 witness 8).

Design rules (blocking for RT-1):

- **No transport in the DS.** The provider is injected; DS code calls its methods and renders its snapshots. A test double that resolves synchronously from an in-memory map must be sufficient to run every DS collaboration test — the `CommentStore` in-memory-adapter precedent (§2.3) applied to collaboration. If a DS test needs a server, the port is wrong.
- **Lock state drives existing props only.** The adapter maps `holder === currentActor` → editable, `holder === other` → `editable={false}` with the badge in locked-by-other mode, `holder === null` → host policy (editable with acquire-on-first-gesture, or read-only until acquired — host choice, DS renders both). Badge derivation consumes `LockSnapshot` + `PresenceSnapshot` + injected `CollaborationCapabilities` (§5.1); no badge state is derived from snapshots alone. The editor component gains no lock-specific prop beyond the badge inputs, the capabilities, and the provider reference.
- **Presence is rendering only.** Presence snapshots never change `editable`. A user can be present and read-only (viewer), present and holder, or absent and holder (lock outliving a dropped connection until TTL) — the badge model keeps the three facts separate, as sentropic’s separate lock row and presence map already do (§2.2).
- **Awareness (stage two) renders through injected facts.** Remote caret/selection decorations consume `{ actor, color, label }` plus relative positions computed inside `"./editor"`; the public component surface exposes users as data (the `collaborationCaret.users` shape) and never exposes a `Y.Doc`, an awareness instance, or a provider socket.
- **Offline-first default.** No provider injected ⇒ controlled mode, no badge lock state (or a host-rendered static badge), no network, no CRDT code loaded. This is the `file://` dossier configuration and the default for every current consumer.

### 5.2 What must be designed into RT-1 now so L2 is not blocked later

Three items. Each is cheap now and expensive to retrofit; each is testable in RT-1 without any Yjs dependency.

1. **Identities declared CRDT-stable.** RT-1 already carries `paragraphId` as a node attribute with split/merge/undo/paste rules (§2.6). RT-1 must additionally record, in the FE-2 specification delta and in a DS test, that these rules are the *same* rules a CRDT binding needs: split allocates through the injected allocator (never a position-derived ID), merge retires without reallocation, paste strips incoming identities. The stage-two additions (cross-session collision-freedom, attribute carriage on `Y.XmlElement`) then become binding properties to verify, not identity redesigns. Concretely: RT-1’s allocator injection point is the single identity source in both modes; no code path may mint an identity from `crypto.randomUUID()` inside a Focus session (the factory default remains for non-Focus hosts only, FE-2 §5.2).
2. **Capture stays mode-neutral; notification does not — yet.** Two surfaces must not be conflated. *Capture* (`captureDocument()` → `{ document, representability }`, no gesture) is already the freeze bridge’s input and is mode-neutral by construction: RT-1 must not add any controlled-mode-only assumption to it — in particular no assumption that consecutive captures differ by one local gesture, and no consumer-visible ordering guarantee stronger than document order. A stage-one test with a simulated external document replacement between two captures verifies exactly this, and nothing more; it does not verify anything about notifications. *Notification* (`RichTextChangeEvent { document, gesture, representability }`) is not neutral today: FE-2 defines `gesture` as the provenance of a single completed **local** gesture, from a closed list (`type` / `split` / `merge` / `paste` / `delete` / `undo` / `redo` / `composition-commit` — `feat/rich-text-core:spec/SPEC_EVOL_DS_RICH_TEXT_EDITOR.md` §5.3), emitted once per user-perceived gesture. A remote Yjs transaction is not a local gesture: it has no single author gesture, may interleave several authors, and may arrive while the local user is idle or composing. Saying it “must be indistinguishable from a local gesture” therefore defines neither its emission nor its provenance and is withdrawn. The stage-two contract, to be settled as an FE-2 amendment inside CB-3 before any bound-mode notification is claimed (the h2a return itself does not change): remote-origin document changes in bound mode are surfaced only through capture/readiness — the bound document is the document, the host learns it changed via the binding’s session signal and reads it with `captureDocument()` at freeze or on demand — and the DS either (a) emits no `RichTextChangeEvent` for purely remote transactions (local gestures in bound mode keep the existing closed gesture list, with undo/redo driven by the Yjs manager), or (b) if a notification is required, FE-2 is amended first with an explicit remote-origin provenance (a new gesture kind or a separate `onRemoteDocument` signal, with its own emission rules: coalescing, composition interaction, no baseline implication). Until that amendment is chosen and witnessed, RT-1 claims capture neutrality only and bound-mode notification is `unknown` by design, not by omission.
3. **The provider slot exists, empty.** `"./editor"` accepts an optional collaboration binding at construction (absent in RT-1 deliveries) and the extension composition is factored so the collaboration pair can replace `UndoRedo` in exactly one place. RT-1 ships with the slot unimplemented (controlled binding only) but with the packaging proof that the collaboration graph, when it lands, loads only through `"./editor"` and only with a provider present. Shipping RT-1 without the slot forces a breaking factory change at stage two; shipping it with a half-enabled Yjs binding violates the undo rule of §4.4. The slot is an interface and a wiring point, not a feature flag users can turn on.

Explicitly **not** designed into RT-1: no `yjs` dependency, no awareness UI of any kind (no carets, no selections — those are stage two only; §4 Option C now states the same), no block locks, no session persistence, no Hocuspocus anything. If stage two never starts, nothing in RT-1 is dead weight beyond one optional constructor field and the identity discipline FE-2 already requires.

### 5.3 Announcement discipline

Stage one is announced exactly as: “presence and object locking available in the DS editor (Svelte); concurrent editing not included.” Stage two announces in two steps (§4.5): after the CB-3 DS gate, “concurrent editing client qualified where the host provides a collaboration session; offline dossiers unchanged”; only after the FE-6 host gate, “connected publication delivered” for that host. Any wording that lets a reader believe L0 presence is co-editing, that the DS provides the server, or that client qualification is connected publication, is a scope breach of this study.

1. **Real concurrent editing before CB-3’s gate.** No CRDT, no merged typing, no simultaneous carets are delivered by CB-0/CB-1/CB-2, and no stage-one wording may imply them (§5.3).
2. **Any server in the DS.** No Hocuspocus, WebSocket, SSE, or persistence code in any DS package; no DS-hosted document service; no Tiptap Cloud or Pro dependency (§4.7).
3. **Block-level text locks (L1) unless Q2 directs them.** Not built by default (§7 sequencing summary).
4. **Merged concurrent diagram editing.** No concurrent dragging/geometry merge; diagrams get arbitration and presence only (§3.3).
5. **Spreadsheet design and delivery.** Owned by B3; this study supplies only the shared lock/presence contract (§6.2) and the conditional CB-4S surface, which delivers nothing until Q8 and a B3 grid lot (§7).
6. **The h2a contract.** No change to the return envelope, manifest, diff, reconciler, digests, lineage, or schemas; no new Track event kind; per-paragraph authorship only via Q5’s separate provenance mechanism plus Focus evolution.
7. **`LiveDocumentStore` implementation.** The stub is untouched (§2.1, §6.3); a future implementation is a sentropic lot that may consume the DS port.
8. **The full SPEC_VOL_INTERACTIVE_CANVAS programme.** Kanban-as-canvas (I4), dossier-as-canvas beyond the FE-2 editor (I5), CLI surfacing (I3), and the reusable sentropic canvas module (I6) are separate promotions; B2 covers only the editor collaboration layer they would share.
9. **Comment model changes.** Anchors, threads, and the annotations resolver are consumed as-is (§2.3, §3.5).
10. **Identity, authentication, and membership.** Host-owned in every option; the DS stores and renders opaque actor facts only (§4.7, §5.1).
11. **Offline multi-writer merge.** Yjs offline editing inside a connected host is CB-3 scope; merging two independently produced offline *returns* remains the reconciler’s job (rebase/conflict), not a CRDT merge, and the `file://` dossier stays single-user.
12. **Performance budgets for collaboration.** No caret-latency, merge-throughput, or presence-scale numbers are proposed; they are measured at CB-3 lot start like FE-8’s phase-A measurements, and no stage-one claim depends on them.
13. **Residual unknowns carried, not resolved:** the `y-protocols` source tree is not vendored (`source-gap`, §2.7) and must be pinned by CB-3; `y-websocket`/`y-indexeddb`-class provider/persistence packages are `unknown` until a lot pins them; whether preserved-bearing fields can ever enter bound mode depends on CB-3 witness 3 and may permanently remain “controlled mode only” (§4.4); bound-mode change notification (capture-only vs amended remote-origin provenance) is unsettled pending the FE-2 amendment in CB-3 (§5.2); per-paragraph authorship persistence is `unknown` pending Q5.
