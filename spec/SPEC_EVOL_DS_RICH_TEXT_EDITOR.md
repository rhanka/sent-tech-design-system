## 1. Goal, scope, non-goals

### 1.1 Goal

Deliver the reusable controlled Tiptap editor that lot FE-2 of the h2a specification requires, so that two Svelte consumers can mount the same editor surface:

1. h2a `focus-kit`, the offline portable dossier host (first witness, lot FE-3);
2. the sentropic app, which today carries the Tiptap precedent (lot FE-7).

The editor edits source text in place, preserves opaque paragraph identities through split, merge, undo and paste, emits no change for an unchanged field, respects IME composition, carries no built-in natural language, performs no network access, and embeds into h2a's offline single-file artefact with no CDN.

### 1.2 In scope (this specification)

Section map: §4 package placement; §5 component surface (making h2a specification §5.7 concrete as an API);
§6 content profile P0 (Markdown round-trip path and its qualification, preserved non-editable blocks, and the
list-item paragraph gate); §7 security and CSP; §8 offline packaging (what the DS ships, what the host bundles);
§9 dependencies and licensing; §10 provenance; §11 tests (the FE-2 RED list made concrete); §12 lots inside
the DS; §13 interfaces with h2a lots FE-3, FE-7, FE-8 and the D23 fallback; §14 open questions to the owner;
§15 NOT covered; §16 residual factual uncertainties. No Python is used anywhere in the lots this specification
defines (implementation, tests, jobs, one-off scripts): the DS stack is Node/TypeScript and native tooling
already present.

### 1.3 Out of scope

See §15 for the exhaustive NOT-covered list. In particular: the Focus return, manifest, diff and reconciler (h2a FE-0/FE-1/FE-5); any toolbar product decision beyond keyboard and Markdown input rules in P0; React/Vue/Angular adapters claimed as delivered before their stage gate (§4.3); table/diagram/code editing; collaborative editing.

### 4.2 Decision and reasoning

**Decision (`ds-proposition`):** create `packages/rich-text` as `@sentropic/design-system-rich-text`, a framework-neutral package with exactly two entries. The split below is the RT-0 resolution of the contradiction between this decision (the core wraps `@tiptap/core`, §6.5 path through a ProseMirror document) and the RED-P core half (importing the core entry loads no Svelte or Tiptap module, §11): both hold at once only when "the core" names two different entries, so the specification now names them.

- **Entry `"."` — pure, no editor runtime.** `src/index.ts` (built to `dist/index.js`) exports only pure logic: the controlled-document model and gesture/readiness types (§5.1, §5.3, §5.5), the injected-message catalogue and `untranslated` marker helpers (§5.7), the P0 profile descriptors as data (profile identifier, extension package names in composition order, Markdown serialisation configuration; §6.1, §6.5), the identity attribute contract as data (`paragraphId` / `data-paragraph-id` / `data-preserved-block` names and the plugin descriptor; §5.2), the DS-token theme mapping (§5.8), document equality, the §5.6 external-update decision rules, and capture/readiness state (§5.6). Importing `"."` loads no `@tiptap/*`, no `prosemirror-*`, no Svelte/framework module and no DOM global; every module in its transitive import graph is relative or `node:`-free pure TypeScript. RED-P's core half (§11) asserts on this entry only.
- **Entry `"./editor"` — Tiptap-bound, the engine.** `src/editor.ts` (built to `dist/editor.js`, exported as `"./editor"`) is the only RT-0 entry that imports `@tiptap/core`, `@tiptap/pm`, the granular P0 extensions, `UndoRedo` and `@tiptap/markdown`. It exports the editor factory (`createRichTextEditor`): it builds the Tiptap editor from the P0 extensions, defines the `preservedBlock` node, installs the live paragraph-identity ProseMirror plugin, maps `RichTextDocument` to and from the ProseMirror document with the `paragraphId` attribute, and converts editable paragraph Markdown through `@tiptap/markdown`. Split, merge, undo/redo, paste parsing and Markdown conversion are ProseMirror/Tiptap behaviour reached through this entry, never re-implemented in the DS. The Svelte adapter (RT-1) imports this entry; no framework adapter imports the editor runtime through `"."`.
- Tiptap/ProseMirror are `peerDependencies` of the package (mirroring `packages/codemirror/package.json`: peer range on the major line, exact pins only in `devDependencies` for its own build/tests); `@tiptap/markdown` is a runtime dependency reachable only from `"./editor"` (§9.1). Peers are declared at package level because `package.json` has one peer set; the entry split is enforced by the import graph (RED-P), not by the peer declaration.
- The package ships `sideEffects: false`, `files: ["dist"]`, ESM + types for both entries, build `tsc -p tsconfig.json`, test `vitest run src` (the `packages/codemirror` script shape).
- The package is consumed by thin framework adapters that own only mounting, prop/event idioms and lifecycle, importing `"./editor"` for the runtime and `"."` for types and pure helpers.

Reasoning, against the three constraints in the commission:

1. **A plain Button/Card import never loads Tiptap (`h2a-spec` §5.7/FE-2: explicit subpath export).** The neutral package is a separate workspace, so no `components-*` barrel can pull it transitively unless an adapter does. Inside `packages/components-svelte`, the adapter is exposed only through the explicit subpath export `@sentropic/design-system-svelte/rich-text-editor` (added to `packages/components-svelte/package.json` `exports` alongside the existing `"."`; the barrel `src/lib/index.ts` gains no rich-text export). A consumer importing `@sentropic/design-system-svelte` (Button, Card) resolves `"."` and never resolves the subpath module graph. This is witnessed by the packaging test of §11 (RED-P).
2. **DS framework parity rule.** The DS delivers components across Svelte/React/Vue/Angular and guards parity by measurement, not by type similarity (`spec/SPEC_EVOL_DS_JSON_RENDER_STANDARD.md` §5.1/AC-L1: parity recorded per component, never claimed from types alone; `docs/graph-dataviz-migration-plan.md` lot A4: adapters are declared equivalent only after a real vertical scenario). A neutral package with staged thin adapters is the only placement under which a later React/Vue/Angular adapter reuses the qualified profile and editor entry instead of re-qualifying them. Parity is claimed per stage, never in advance (§4.3).
3. **Consumers that exist now.** Both current consumers are Svelte: h2a `focus-kit` (`packages/h2a/focus-kit/src/App.svelte` at `98060bd0a`, Svelte) and the sentropic app (`ui/src/lib/components/TipTap.svelte`, Svelte). No React, Vue or Angular consumer of a rich editor exists in the sources read. Delivering the neutral package plus the Svelte adapter first serves both real consumers and keeps the other three adapters as a staged, gated extension rather than speculative work.

## 5. Component surface (RT-D2)

This section makes h2a specification §5.7 precise as an API. Names below are the DS API (`ds-proposition` concretisation); semantics tagged `h2a-spec` are binding from §5.7/D14.

### 5.1 Controlled document model (framework-neutral, in `packages/rich-text`)

The component is controlled: the host owns the value; the component never owns a durable copy.

```ts
// packages/rich-text/src/model.ts (RT-0, [N])
export type RichTextFormat = "focus.markdown.p0@1" | "text/plain";

export interface RichTextBlock {
  /** Opaque per-block identity, host-supplied. See §5.2. */
  paragraphId: string;
  kind: "paragraph" | "preserved";
  /** Editable paragraph text (Markdown inline source for
      `focus.markdown.p0@1`, literal text for `text/plain`).
      Present iff kind === "paragraph". */
  text?: string;
  /** Verbatim source slice of a preserved block. Present iff
      kind === "preserved". Never edited, never reserialised. */
  raw?: string;
  /** Preserved block kind as segmented host-side (e.g. "heading",
      "list", "table", "codeBlock", "diagram"). Display only. */
  preservedKind?: string;
}

export interface RichTextDocument {
  format: RichTextFormat;
  blocks: readonly RichTextBlock[];
}
```

- The wire shape between DS and host is `RichTextDocument`, not Tiptap JSON and not ProseMirror positions (`h2a-spec` §5.7: ProseMirror positions and Tiptap JSON never leak into the wire contract). The `"./editor"` entry converts `RichTextDocument` ↔ ProseMirror document internally (§4.2); the `"."` entry carries the model only and converts nothing.
- **No separator storage (blocking).** `RichTextDocument` stores no separator: no blank-line count, no line-ending form (LF vs CRLF vs CR), no trailing whitespace and no final-newline flag exists in the model, and none may be added as a hidden field, an extra block or a paragraph-text suffix. A paragraph `text` is the bare block slice the Focus codec produces (`packages/focus/src/editing/codec.ts` at `98060bd0a`: top-level block slices with gaps excluded, `assertParagraphText` refusing any paragraph text that does not segment back to exactly itself), so a `text` carrying a trailing line break would be refused host-side on every paragraph. Separators are structural gaps owned host-side (§6.5, §13.1); §11 RED 2 and §6.5 define the DS-level identity rule that follows from this.
- For `text/plain` fields the document holds exactly the plain-field segmentation the host adapter derived from the Focus manifest (one block per plain paragraph; an emptied plain field is one block with `text: ""`, §2.2 M6). The component does not re-segment plain text.
- **Interior newline in a `text/plain` paragraph (P0 decision, blocking).** A `text/plain` paragraph MAY contain an interior newline: a `"\n"` strictly inside the paragraph text, with non-blank content on both sides, is content of that paragraph, not a paragraph separator. The host segmentation already produces it: `segmentText` (`codec.ts:35–56` at `98060bd0a`) groups consecutive non-blank lines into one segment, so the source `"A\nB"` is one paragraph (`[0, 3]`), and `assertParagraphText("A\nB", 'text/plain')` passes (exactly one segment covering the whole text, `codec.ts:60–63`). In the `"./editor"` conversion that interior `"\n"` is a `hardBreak` node inside the same `paragraph` (§6.1, §6.2): Shift+Enter inserts it without splitting the paragraph, Enter splits the paragraph, and disabling marks for `text/plain` (§6.1) disables marks only, never the `hardBreak` node. A leading or trailing `"\n"` is never part of a host-segmented slice; a draft paragraph may acquire one only through a split (for example Enter immediately after an interior newline yields the head `"A\n"`), and that head is then refused at export under the §5.10 general rule until the §5.10 condition passes. Forbidding the interior newline instead was rejected: it would make the valid host segment `"A\nB"` unrepresentable as the single block the manifest carries and would break conversion equivalence (§6.5). The allowance is tested, not assumed: the §11.3 vectors include the `text/plain` source `"A\nB"` as one editable segment and RED 3 starts from it as one block (§11).
- For `focus.markdown.p0@1` the host adapter derives blocks from the Focus source codec segmentation (editable paragraphs vs opaque slices, §2.2 M5/M6); the DS ships no source segmentation (§6.5). Preserved slices travel as `raw` and return byte-identical at block level (§6.5).
- **Representable paragraph form (§6.6, blocking).** A paragraph `text` is not arbitrary ProseMirror content serialised by a DS-invented encoding. An untouched paragraph keeps its exact source bytes; for `text/plain` an edited paragraph is literal text (`hardBreak` ⇔ `"\n"`, exact whitespace, no marker of any kind); for `focus.markdown.p0@1` an edited paragraph is the `@tiptap/markdown` bridge serialisation without post-processing, as defined in §6.6. Representability — the bridge re-parse equalling the live content and the wire passing the pinned `assertParagraphText` — is a reported property (§6.6, surfaced by `RichTextRepresentability` in §5.3/§5.5), never a transformation: capture never mutates the live document, and the live ⇔ capture ⇔ remount equality of §6.6 is guaranteed for representable paragraphs only. No hidden encoding of whitespace or hard breaks is allowed in the wire text. The mandatory edited round-trip table is §11.4.

### 5.2 Opaque per-block identity attribute

- **Name.** The identity is the ProseMirror node attribute `paragraphId` on `paragraph` and `preservedBlock` nodes, rendered to the DOM as `data-paragraph-id` (and `data-preserved-block` on preserved blocks). It is a single opaque string, unique within the document, allocated by the host. The component treats it as opaque: it never parses, derives, sorts by or displays it as content.
- **Supply.** The host adapter supplies identities through the initial `RichTextDocument` (one `paragraphId` per block). New identities created inside the editor (split tail, pasted blocks, inserted paragraphs) are allocated through the injected allocator (§5.5, `allocateId`); the component has no identity policy of its own. If the host supplies no allocator, the `"./editor"` factory default is `crypto.randomUUID()` — acceptable only for non-Focus hosts, because Focus allocation policy (deterministic seeding, retired-ID non-reuse) belongs to the producer/host (`h2a-spec` D13, merged `anchors.ts`), never to the component.
- **Carriage (D14, `h2a-spec`).**
  - *Split (Enter):* the leading paragraph keeps the original `paragraphId`; every following paragraph receives a fresh allocated identity.
  - *Merge (Backspace at paragraph start / Delete at end):* the leading paragraph's identity survives; consumed identities are retired inside the editor session and are never reallocated by the component.
  - *Clear the whole field:* clearing every paragraph of a field leaves the single controlled empty block (§5.1) keeping the first block's `paragraphId`; every other block identity is consumed and retired as in a merge, and no fresh identity is allocated for the emptied block. This rule is fixed: the clear-a-field witness of §11/§13.1 depends on it, because keeping the first identity places the spliced empty paragraph at `[0,0]` in the retained-gap source, while a fresh identity would place it after the retained gaps.
  - *Undo/redo:* undo of a removal restores the same logical paragraph's identity (the identity is part of the ProseMirror node, so history restores it by construction; the RED list asserts it, §11 RED 3).
  - *Internal copy/paste:* pasted copies receive fresh allocated identities; a paste never duplicates a live identity inside the document.
  - *External paste:* pasted markup never supplies a trusted identity. The paste pipeline strips any `data-paragraph-id` (and any `paragraphId` attribute) from incoming content before it enters the document, then allocates fresh identities (§7). This rule has no exception, including paste of content copied from the same editor in another window.
- **Non-identity.** Display order, array index, DOM path, translated label, content hash and character offset are never used as identity anywhere in the component (`h2a-spec` D13). Selection and caret are ProseMirror positions internally and are never emitted as identity.

### 5.3 Document and gesture information out — no diff in the DS

```ts
// packages/rich-text/src/model.ts (RT-0, [N])
export type RichTextGestureKind =
  | "type"
  | "split"
  | "merge"
  | "paste"
  | "delete"
  | "undo"
  | "redo"
  | "composition-commit";

/** Gesture provenance. Exactly what the host adapter needs to follow
    block identities across the gesture; no text diff is carried. */
export interface RichTextGesture {
  /** Opaque identifier of this completed gesture, allocated by the component. */
  gestureId: string;
  kind: RichTextGestureKind;
  /** Ordered `paragraphId` values of the blocks the gesture touched,
      in resulting document order. */
  affectedParagraphIds: readonly string[];
  /** Present iff kind === "split": the block that was split and the fresh
      identities allocated for the tail blocks, in document order. */
  split?: {
    sourceParagraphId: string;
    newParagraphIds: readonly string[];
  };
  /** Present iff kind === "merge": the surviving identity and the identities
      consumed by the merge, which the component never reallocates. */
  merge?: {
    survivingParagraphId: string;
    retiredParagraphIds: readonly string[];
  };
  /** Present iff kind === "paste": the freshly allocated identities of the
      inserted blocks and whether the paste entered from inside this editor
      session or from outside it. */
  paste?: {
    insertedParagraphIds: readonly string[];
    origin: "internal" | "external";
  };
}

/** Representability of the emitted wires (§6.6). Identities only: no text,
    no diff, no Focus type. Empty when every paragraph is representable. */
export interface RichTextRepresentability {
  nonRepresentableParagraphIds: readonly string[];
}

export interface RichTextChangeEvent {
  /** The complete new controlled value. The only content the component emits. */
  document: RichTextDocument;
  /** Provenance of the single completed gesture that produced `document`. */
  gesture: RichTextGesture;
  /** Paragraphs of `document` whose wire is non-representable (§6.6). */
  representability: RichTextRepresentability;
}
```

- **No-diff rule (blocking).** The component emits the complete document and the gesture information above, and nothing else about what changed. It MUST NOT compute, store, emit or compare a per-paragraph `before`/`after` pair, a `RichTextChange`/`RichTextTransaction` shape, anchors derived from a diff, or a delta against any baseline, and it MUST NOT retain the last host-supplied or host-acknowledged value as a diff baseline. Removing every DS-side `before`/`after` computation from the surface is normative: no type in `packages/rich-text` carries `before`, `after`, `beforeAnchors` or `anchors`, and no callback translates directly to a Focus `ParagraphChange`. The shapes `RichTextAnchors`, `RichTextChange` and `RichTextTransaction` do not exist.
- **What the adapter needs, named precisely.** The host adapter needs exactly four things, all present above and nothing more: (1) block identities — the ordered `paragraphId` values and texts in `document.blocks`; (2) split/merge/paste gesture provenance — `RichTextGesture.split` / `.merge` / `.paste` together with `affectedParagraphIds`, so the adapter can follow a split tail, a merge survivor and fresh paste identities without guessing from text; (3) composition state — the neutral readiness signal of §5.6, so the adapter never captures mid-composition; (4) representability — `RichTextRepresentability.nonRepresentableParagraphIds` (§6.6), the flagged identities in document order, so the adapter can report an unsupported export under §5.10 without guessing from text. The flag is not a diff and does not weaken the no-diff rule above: it carries no `before`/`after` text, no anchors and no Focus type, and the key inspection of §11 RED 3 asserts `document`, `gesture` and `representability` as the only top-level keys, with no forbidden key at any level. No position, offset or text comparison crosses the DS boundary.
- **Host-side diff (the only diff).** The host adapter maps `document.blocks` to Focus `ParagraphValue[]` through the manifest identities it owns, and computes the per-paragraph diff with `@sentropic/focus/editing` (`diffParagraphs` in merged `packages/focus/src/editing/diff.ts`), against the retained Focus baseline (`ParagraphValue[]` derived from the manifest it holds). The adapter MUST NOT translate a DS gesture into `ParagraphChange` records by hand and MUST NOT implement a second diff algorithm; `gesture` is provenance for logging and caret handling only.
- **Baseline advancement (blocking).** A freeze or an export never advances the baseline. At the pin (`98060bd0a`), `freezeReturn` (`packages/focus/src/editing/contract.ts`) preserves the supplied `document` and `manifest` unchanged: it validates any `previous` return against that same manifest and base, filters empty transactions, chains `supersededReturnIds`, and returns the `previous` clone unchanged when answers, notes, transactions, production and scope are identical; it recomputes no manifest and moves no base. `carryManifest` (`packages/focus/src/editing/anchors.ts`) accompanies a producer revision: it takes a new authoritative `DecisionDossierDocument`, the previous manifest and an explicit paragraph correspondence, and seals a new manifest whose `baseHash` is `baseDigest(newDocument)` with `manifestId` preserved and retired identities accumulated; it is not an export step. The baseline therefore advances only when a new authoritative version, once acknowledged by the host, is carried through `carryManifest` (or seeded once for a first version); neither `freezeReturn`, nor an export, nor a component echo, nor a local edit advances it. Worked consequence: starting from retained baseline text `A`, typing to `B` and then undoing to `A` emits two events (documents `B`, then `A`) whose host-side diffs against the retained baseline `A` are `A → B` and then the empty cumulative diff; no `B → A` change is ever produced, because no DS-side `B`-relative delta exists. Advancing the baseline to `B` after exporting `A → B` would make the next undo produce a `B → A` change instead of the empty cumulative result and is therefore prohibited. Mandatory witness (host adapter in h2a lot FE-3, plus the FE-3 host-side freeze check of §13.1): (1) baseline `A` retained, draft at `A`; (2) type to `B`, host echoes `B` back as the controlled `value` (echo recorded as acknowledgement, §5.6 rule 1, baseline unchanged); (3) freeze export `R1` via `freezeReturn` with the `A → B` cumulative transaction — assert `R1.source.baseHash` and `R1.manifest.manifestBaseHash` equal the baseline `A` hashes; (4) undo to `A`; (5) freeze export `R2` — assert `R2.editReturn.transactions` is `[]` (empty cumulative diff against the still-retained baseline `A`), `R2.source.baseHash` and `R2.manifest.manifestBaseHash` are identical to `R1`'s, `R2.editReturn.supersedesReturnId` equals `R1.returnId`, and `R2.editReturn.supersededReturnIds` is `[R1.returnId]`. Any advance of the retained baseline at step (2), (3) or (4) fails this witness.
- **Emission granularity.** One user-perceived gesture (a run of typing coalesced by the editor, a split, a merge, a paste, a committed IME composition) emits exactly one `RichTextChangeEvent` carrying the complete resulting document. No event is emitted for opening, focusing, rendering, locale/theme change, or leaving an unchanged editor (`h2a-spec` D12, FE-2 RED 2): unchanged means the resulting `RichTextDocument` equals the current controlled value under the document equality of §5.6 (all significant fields: `format`, ordered `paragraphId`, `kind`, `text`, `raw`, `preservedKind`), checked by value equality on the document, never by a diff. No event is emitted mid-IME-composition (§5.6). An undo that restores the prior document emits an event with that document; whether it nets to zero is decided host-side by the Focus diff, never by the component.

### 5.4 `editable` / `disabled` / read-only states

Framework adapters expose the same three-state semantics in their framework idiom; the Svelte adapter (RT-1) exposes:

| Prop | Default | Meaning |
| --- | --- | --- |
| `editable` | `true` | The field may be edited when `true`. `false` is the read-only state: text stays selectable and copyable, the caret may be placed, no mutation is possible. |
| `disabled` | `false` | The form-disabled state: not focusable, `aria-disabled`, no selection interaction. `disabled: true` wins over `editable`. |

- Effective editing is `editable && !disabled`. Both props take effect immediately on the live editor (`editor.setEditable(...)`), without remounting.
- In a non-editable state, typing, paste, drop, cut and every mutation shortcut are inert: no document mutation, no `onChange`, no save-like callback (`h2a-spec` §5.7; viewer/locked rule §2.3). This includes the viewer case: a host rendering for a viewer passes `editable={false}` (or `disabled`) and the RED list asserts the lock through paste and keyboard paths, not only typing (FE-2 RED 1).
- State changes never emit a change event and never alter the document.

### 5.6 External controlled updates during typing; IME composition

**External updates (`h2a-spec` §5.7) — composition and local divergence take precedence over focus state (blocking).** The decision half of this rule is pure and lives in the `"."` entry (`packages/rich-text/src/document.ts`, §12): document equality and a decision function that, given the displayed document, the last acknowledged document, the incoming document, the composing flag and the unacknowledged-local-revision flag defined below, returns exactly one of echo / defer / conflict / apply, with no Tiptap, ProseMirror or DOM reference. The `"./editor"` factory and the framework adapters apply the returned decision to the live ProseMirror instance (suppress replacement, defer, emit `onExternalConflict`, or replace content with selection re-anchoring); they do not restate the rule order. When the `value` prop changes after mount, the component evaluates the following rules in this exact order; focus state never appears as a condition. Three internal values are distinguished throughout: the *displayed document* (the ProseMirror document currently shown), the *last acknowledged document* (the last host-supplied `value` recorded under rule 1 or rule 4, initialised to the mount `value`), and the *unacknowledged local revision* flag — a boolean, initially false, set to true by any user transaction that modifies the live ProseMirror content (any completed gesture, typing run, split, merge, paste, deletion, undo/redo step or composition commit, including a transaction whose serialised wire is byte-identical to the acknowledged wire) and cleared only when an acknowledgement is recorded under rule 1 or a rule-4 application completes. Divergence is therefore a property of the local revision, not of wire equality: wire equality between the displayed and acknowledged documents never clears this flag, the §6.6 representability flag never sets or clears it, and capture (§5.6 deferred capture, §6.6) never sets or clears it. Document equality, used by every rule below and by the unchanged check of §5.3, is value equality over all significant fields and never a diff: two `RichTextDocument` values are equal iff `format` is strictly equal, the `blocks` arrays have the same length in the same order, and for each index the blocks have strictly equal `paragraphId`, strictly equal `kind`, strictly equal `text` (absent equals absent; present values compared by string equality), strictly equal `raw` (same absent/present rule), and strictly equal `preservedKind` (same absent/present rule). A difference in `format` alone, in `kind` alone, or in the `raw` of a preserved block alone is therefore a real difference, never an echo.

1. *Echo — suppression of replacement, recording of acknowledgement.* If the incoming document equals the displayed document under the equality above, the component performs two distinct effects and no third: (a) *replacement is suppressed* — the editor content is not replaced, the ProseMirror instance is not recreated, and focus, caret, selection and scroll are not reset (this is the `lastValue` guard capital of §2.3, checked by the value equality above, never by a diff); and (b) *acknowledgement is recorded* — the last acknowledged document is set to the incoming document (a value copy) and the unacknowledged-local-revision flag is cleared. Recording the acknowledgement does not advance the Focus baseline (§5.3 baseline rule); it only moves the component-internal reference that rule 3 compares against, so that edits the host has echoed back are no longer treated as locally divergent. An incoming document that differs from the displayed document in any significant field — including a change confined to the `raw` of one preserved block — is not an echo and falls through to rules 2–4.
2. *Composition.* Else if a composition is in progress (`readiness().composing === true`), the update is deferred: it is neither applied nor treated as a conflict yet. It is re-evaluated once, immediately after the composition commit and its single `onChange`, under rules 1, 3 and 4, using the equality, acknowledged reference and unacknowledged-local-revision flag defined above (the commit itself sets that flag, like any other user transaction). No overwrite and no conflict signal occur mid-composition.
3. *Local divergence.* Else if the displayed document differs from the last acknowledged document under the equality above **or** the unacknowledged-local-revision flag is set — that is, the user holds a local revision that no acknowledgement has covered, whether or not its serialisation still equals the acknowledged wire, and regardless of whether the editor is focused, blurred, or has lost focus since typing — the incoming value **never overwrites** local work. The component keeps the local document and caret untouched and emits exactly one `onExternalConflict` carrying the incoming document and the local document. Blur never cleans local work: typing, then blurring, then receiving an external update before acknowledgement leaves the local text intact and signals one conflict (§11 RED 4). The host decides (keep local, accept external by remounting with a new key, or reconcile); the component applies no silent winner. A parent clearing the value to empty is an external update under the same rule — the sentropic precedent's focused-clear exception is not carried over, because §5.7 requires surfacing, never overwriting; hosts that need a forced reset remount explicitly.
4. *No conflict.* Else (no composition, no local divergence: the displayed document equals the last acknowledged document **and** the unacknowledged-local-revision flag is clear) the update is applied automatically, whatever the focus state: content is replaced, the selection is restored when the saved ProseMirror positions remain valid in the new document, otherwise clamped to the nearest valid position (the selection-preservation capital of §2.3, generalised from offsets to block identities: selection is re-anchored by `paragraphId` plus intra-paragraph offset where the block survives), and the last acknowledged document is then set to the incoming document (the revision flag stays clear). A rule-4 update that changes only the `raw` (and, where present, the `preservedKind`) of one preserved block, with every paragraph text unchanged, is applied by this rule exactly like any other no-conflict update: the preserved block renders the new `raw`, no conflict is emitted, and no paragraph is recreated.

Only a rule-4 update is automatic. Every other case either defers, records an echo acknowledgement without replacing content, or surfaces a conflict; no path silently overwrites dirty local work, and the former "clean **or not focused**" condition does not exist. Mandatory echo witness (named in §11 RED 4): mount at `A` (acknowledged `A`), type to `B` (displayed `B`, acknowledged still `A`), host echoes `B` as the new `value` (rule 1: no replacement, no remount, acknowledgement becomes `B`), then host supplies external update `C` with no intervening local edit (rule 4: `C` is applied with zero `onExternalConflict`); separately, from an acknowledged document containing a preserved block, host supplies an update identical except for that block's `raw` (not an echo under the equality above; rule 4 applies it with zero conflict and the new `raw` rendered). Treating the echo as a pure no-op without recording the acknowledgement fails the `C` step by construction, because `B` would still count as divergent when `C` arrives.

**Serialisation-equal divergence witness (mandatory, named in §11 RED 4).** Mount a `text/markdown` field as one empty paragraph (wire `""`, acknowledged `""`), then type three spaces with no host echo in between: the live content is `[text("   ")]` while the bridge serialises it to `""` (§6.6, §11.4 whitespace-only row), so the displayed document still equals the last acknowledged document under the wire equality above and the paragraph is flagged — yet the typing transaction has set the unacknowledged-local-revision flag. An external update `"C"` arriving now is evaluated under rule 3, not rule 4: the component keeps the three spaces live, emits exactly one `onExternalConflict`, and does not apply `"C"`. An implementation that decides divergence by wire equality alone applies `"C"` and silently overwrites the unacknowledged draft; the §6.6 flag alone does not protect it either, because the flag never enters this decision — the revision flag does. Only a rule-1 echo or a rule-4 application clears the flag; a subsequent external update after such an acknowledgement is then evaluated on the cleared state.

**IME composition and deferred capture (`h2a-spec` §5.7) — neutral signal, no stale snapshot (blocking).** The editor respects ProseMirror composition state and exposes it through the neutral signal of §5.5:

- `onReadinessChange` fires with `{ composing: true, ready: false }` at `compositionstart` and with `{ composing: false, ready: true }` after `compositionend` and the resulting single `onChange`, in that order. `readiness()` returns the same current value synchronously. The signal carries no text, no language and no Focus type.
- During `compositionstart`–`compositionend`, no `onChange` is emitted and no external update is applied (rule 2 above). Accents, composed characters and emoji are ordinary text once committed; the committed composition emits exactly one `onChange` whose `gesture.kind` is `"composition-commit"`.
- **Deferred capture.** `captureDocument()` is the only export-relevant read. Called while `ready` is true, it resolves immediately with the capture result (`RichTextCaptureResult`, §5.5) for the currently displayed document. Called during composition, it MUST NOT resolve with the pre-composition document and MUST NOT resolve mid-composition: it waits until `compositionend`, the single commit `onChange` has been emitted, and readiness is true again, then resolves exactly once with the capture result for the committed document, which contains the composed text exactly once. The result pairs the document with the `representability` of that same revision (§6.6), so the host freeze reads the flag atomically with the document it qualifies. Capture is a pure read (§6.6 *No mutation at capture*): it emits no event, records no acknowledgement under the rules above (a later host echo of the captured document is evaluated under rules 1–4 like any other incoming value), and leaves history, selection and composition state untouched. The host freeze (§13.1) therefore always awaits `captureDocument()` (or waits for `ready`) and never snapshots the last `onChange` on its own. This satisfies the h2a §5.7 rule that no capture occurs during composition, without substituting a stale revision for the export.
- **Capture termination at unmount (blocking).** A `captureDocument()` promise still pending when the component unmounts (or the editor is otherwise destroyed, §5.9) does not stay pending, does not resolve with any document, and does not fire a late callback: it rejects exactly once during unmount teardown with the neutral capture error, an `Error` whose `name` is `"RichTextCaptureUnavailable"` and whose `message` is exactly `"rich-text.capture-unavailable"` (a neutral key, not a sentence in any language; it carries no document text and no Focus type). After that rejection the component emits no further `onChange`, no further `onReadinessChange`, and no deferred task callback for the destroyed editor. A `captureDocument()` call made after destruction, through a stale handle, returns an already-rejected promise with that same error: it does not throw synchronously, does not recreate the editor, does not resolve and does not hang; `readiness()` called after destruction returns `{ composing: false, ready: false }` and does not throw. Mandatory witness (named in §11 RED 5): start a real composition, call `captureDocument()` so a capture is pending, unmount before any commit, and observe the rejection with that exact `name`/`message`, exactly one settlement, and zero post-unmount callbacks.
- This behaviour requires a real browser for its witness (§11 RED 5); jsdom does not implement composition, and synthetic `CompositionEvent` dispatch alone does not establish a real composition (§11).

### 5.9 Mount on demand, unmount, no network

- The editor is created on mount (`onMount`) and only then: hosts mount it on demand for the active field/block (`h2a-spec` D6/C13). The subpath export is dynamically importable so a host can `await import("@sentropic/design-system-svelte/rich-text-editor")` at first edit activation; the DS does not require eager loading.
- Unmount destroys the Tiptap editor (`editor.destroy()`), removes every listener the component registered on any target (editor root, `document`, `window`), disconnects every `MutationObserver`/`ResizeObserver`/`IntersectionObserver` it created, and cancels every pending animation frame, timer and deferred task it scheduled. No listener, observer or task survives unmount on any target (FE-2 RED 8 asserts this by instrumenting registrations per target/listener/capture triple, observers and scheduled tasks created during the mount, §11). Every `captureDocument()` promise still pending at unmount is settled by the neutral rejection of §5.6 during the same teardown, before teardown completes; no pending capture is left unsettled and none resolves after unmount.
- The component performs no network access of any kind: no `fetch`, no `XMLHttpRequest`, no remote image, font or stylesheet, no beacon. This is observed at runtime for the whole scenario (browser request interception plus a `fetch`/`XMLHttpRequest` sentinel, §11 RED 8), not inferred from an import scan alone: a global `fetch` call needs no import for the scan to miss, so the scan is necessary but never sufficient.

### 5.10 Draft paragraphs refused by the pinned contract (general limit, blocking)

This subsection fixes DS behaviour wherever the pinned contract (§2.2 M8, pin `98060bd0a`) cannot carry what the editor produces. One general rule governs every such case; the examples below illustrate it and no list in this specification enumerates the refused shapes.

- **General rule (blocking).** Under the pin, any draft paragraph in any of the three refusal classes of the *Precedence* bullet below is reported unsupported at export: a paragraph the pinned `assertParagraphText` (`packages/focus/src/editing/codec.ts:58–66`, invoked at `packages/focus/src/editing/diff.ts:66`) refuses, a paragraph the pinned range checks (`validateManifest`, `packages/focus/src/editing/anchors.ts:56`, thrown by `readParagraphs` at `anchors.ts:74–75`) refuse, or — for `text/markdown` — a paragraph flagged by the §6.6 bridge fixed-point test. Examples include an empty `text/plain` paragraph (passes `assertParagraphText` at `codec.ts:59`, then refused by the range checks) and a paragraph with a leading or trailing newline such as `"A\n"` (refused by `assertParagraphText` as `unsupported-paragraph-format`, because `segmentText("A\n")` does not cover the whole text). The rule is stated over the checks and the bridge flag, not over gestures: a future draft shape refused by either h2a check or flagged by the bridge falls under this subsection without any amendment here, and only a shape accepted by both h2a checks **and** unflagged by the bridge never does — a shape accepted by both h2a checks but flagged by the bridge (the `"A  \nB"` witness below) is unsupported under this rule, under its own cause `bridge-non-representable`, defined in the *Precedence* bullet.
- **Precedence and Markdown generalisation (blocking).** This subsection governs every residual refusal in both formats, and §6.6 is subordinate to it. The refusal set is: (a) a wire failing the pinned `assertParagraphText` in either format (`text/plain` or `text/markdown`), reported under the h2a cause that check actually raises (`unsupported-paragraph-format`), (b) a spliced range failing the pinned range checks, reported under the h2a cause `unsupported-range`, and (c) for `text/markdown`, a paragraph whose bridge wire fails the §6.6 fixed-point condition (`bridgeParse(W)` undefined or different from the live content — multi-block parse, lost breaks or spaces, or a structure change such as `# titre`), reported under the bridge's own export cause **`bridge-non-representable`** — a DS/bridge cause, distinct from both h2a errors above: a paragraph in class (c) alone raises neither `unsupported-paragraph-format` nor `unsupported-range` at the pin (its wire can pass `assertParagraphText`, the splice, `validateManifest` and `readParagraphs`, as the `"A  \nB"` witness below shows), and the host MUST NOT surface it under either h2a name. A paragraph in any of these classes is flagged through `RichTextRepresentability` (§5.3/§5.5/§6.6) where the DS can evaluate it, reported unsupported at export under this subsection, and preserved exactly as typed; §6.6 never transforms it, at capture or at any other time. In any apparent conflict between §6.6 and this subsection, this subsection prevails, with one exception this subsection itself authorises: the narrow Shift+Enter no-op of §6.6 (inserted `hardBreak` would become the first child, in `text/markdown` only), which creates no draft content and is not a refusal of an existing draft. Every other gesture remains governed by the *Local gesture allowed* bullet below, in Markdown exactly as in plain text.
- **Bridge witness `"A  \nB"` (blocking).** Mount the `text/markdown` source `"A\nB"` (one host-segmented paragraph), then type two spaces immediately before the soft return: the live content carries those two spaces ahead of the `hardBreak` (native content `[text("A  "), hardBreak, text("B")]`, written `[text("A  \nB")]` in wire-shaped shorthand) and its bridge wire is exactly `"A  \nB"`. At the pin that wire passes every h2a control — `assertParagraphText("A  \nB", 'focus.markdown.p0@1')` accepts it (one editable segment covering the whole text, `codec.ts:58–66`), and the splice, `validateManifest` (`anchors.ts:56`) and `readParagraphs` accept it, so neither `unsupported-paragraph-format` nor `unsupported-range` occurs — yet the bridge re-parses `"A  \nB"` to `[text("A"), hardBreak, text("B")]`, which does not deep-equal the live content, so §6.6 flags the paragraph. Consequence, on the same terms as §13.1: the paragraph is excluded from the FE-3 agreement scope, its export is reported unsupported under the cause `bridge-non-representable` (never under an h2a error name), no agreeing return is frozen for it, and the live draft is preserved exactly as typed. Any reading under which passing both h2a checks alone keeps this paragraph inside the agreement scope fails this witness.
- **Local gesture allowed (blocking).** The component MUST allow locally, exactly as it allows any other gesture, every editing gesture whose result the pinned contract refuses, including splits and clears that produce a refused paragraph. The single authorised exception is the §6.6 Shift+Enter no-op (a `hardBreak` that would become the first child of a Markdown paragraph), which prevents a flagged state that the keystroke alone would create and discards no typed content. In particular: Enter at the end of a `text/plain` paragraph splits under §5.2 (leading block keeps its `paragraphId`, the empty tail block receives a fresh allocator-supplied identity) and emits one `RichTextChangeEvent` whose document holds the empty tail (`text: ""`); clearing the whole content of a `text/plain` field whose source contains paragraph separators (for example `"A\n\nB"`) leaves the controlled single empty block (`text: ""`, §5.1) keeping the first block's `paragraphId` (§5.2) and emits its document; Enter immediately after an interior newline (§5.1) in `"A\nB"` splits into `["A\n", "B"]` (head keeps the original identity, tail receives a fresh identity) and emits its document. The component MUST NOT block, swallow or rewrite any such gesture: it does not refuse the Enter or the clear, does not suppress the resulting block, does not trim a trailing newline to make the draft pass, does not collapse the draft to the pre-gesture document, and does not invent a separator or a non-empty placeholder text. Blocking was rejected for the reasons in RT-D13 (D14 split carriage has no exception for the shape of the resulting paragraphs, D12/§5.3 require the completed gesture to emit, and the §5.7 surface requires the plain-field editor to stay usable); an editor that refused these Enters or clears would fail its primary gestures.
- **No agreement claimed under the pin (blocking).** The FE-3 agreement witness of §13.1 claims agreement under the pin only for drafts whose every paragraph passes `assertParagraphText`, whose spliced ranges validate, **and** no paragraph of which is flagged by the §6.6 bridge test (`RichTextRepresentability`, §5.3/§6.6): for any draft containing a refused or flagged paragraph the host-side splice/read-back equality (`readParagraphs(splicedDocument, splicedManifest)` deep-equals the captured draft) is not asserted and must not be reported as passing — because at the pin the export path throws `unsupported-paragraph-format` (at `diff.ts:66`) or `unsupported-range` (at `anchors.ts:56` via `anchors.ts:74–75`) for the h2a-refused classes (§2.2 M8), and because a bridge-flagged paragraph (class (c) above, the `"A  \nB"` witness) is reported unsupported under `bridge-non-representable` before or without any spliced read-back, with no h2a error raised at all. Flagged paragraphs are therefore excluded from the FE-3 agreement scope everywhere in this subsection, on the same terms as in §13.1. Every draft inside that scope keeps its §13.1 witness under this pin; the scope is tested by the checks and the bridge flag themselves, never by matching the draft against a list of gestures.
- **Export reports unsupported; draft preserved (blocking).** When the host adapter exports a draft containing a refused paragraph, the pinned `diffParagraphs`/`applyParagraphChanges`/`readParagraphs` path raises the refusal (`unsupported-paragraph-format` or `unsupported-range`, §2.2 M8); a Markdown paragraph flagged only by the §6.6 fixed-point condition is reported unsupported on the same terms, before or without a spliced read-back, because no spliced document can agree with a wire that does not re-parse to the live content, and it is surfaced under the bridge's own cause `bridge-non-representable` — not under `unsupported-paragraph-format` or `unsupported-range`, neither of which that paragraph raises at the pin (the `"A  \nB"` witness above). The host MUST surface that outcome as an unsupported export for that field (carrying the actual cause — the h2a error name for classes (a)/(b), `bridge-non-representable` for class (c) — to its own notice surface), MUST NOT freeze or emit a return claiming the spliced document agrees with the draft, MUST NOT advance the retained baseline (§5.3), and MUST preserve the user's local draft unchanged — the displayed DS document, its block identities and its texts stay exactly as the gesture left them, ready to edit further or to export again after the condition below passes. Discarding the draft, reverting the field to the baseline, trimming the offending paragraph, or silently dropping a refused block at export each fail this rule. At DS level the flagged identities reach the host through `RichTextRepresentability` on every `onChange` and on the capture result (§5.3/§5.5/§6.6); the DS component itself computes no diff and raises no Focus error (§5.3), and the pinned refusal cause is observed host-side at export.
- **Condition for full support (blocking).** Full support — the agreement guarantee extended to drafts containing a previously refused paragraph — becomes claimable only when both parts of this condition hold, in order: (1) an h2a evolution covering the refused shapes — the Focus codec/anchors are extended so each such paragraph (for example an empty `text/plain` range `[3,3]` in `"A\n\n"` or `[0,0]` in `"\n\n"`, and a head paragraph `"A\n"` that `assertParagraphText` currently refuses) is a paragraph unit that `readParagraphs` returns and `applyParagraphChanges` round-trips, published as a new `@sentropic/focus` contract; and (2) a new pin — that contract is pinned by exact commit/version in Appendix B and in `spec/SPEC_EVOL_DS_JSON_RENDER_STANDARD.md` §11.2.1 in the same delivery that claims the guarantee. The expected source for the empty-paragraph part is the h2a branch `fix/focus-empty-paragraphs`, still `unverified`: that branch was not read at this pin, this specification asserts no behaviour for it, and it is not assumed to cover the leading/trailing-newline shapes. Until both parts hold, §13.1 asserts only the unsupported-at-export behaviour above for any refused draft; afterwards, the named witnesses of §11 (DS block level) and §13.1 (FE-3) must pass as agreement witnesses on the new pin before the guarantee is stated for the shapes they cover. No DS-side change, DS-only test pass or host-side workaround substitutes for either part.

## 6. Content profile P0 (RT-D3)

### 6.1 Enabled nodes and marks

Profile identifier: `focus.markdown.p0@1` (merged contract, §2.2 M3). The `"."` entry describes this profile as data (`profile.ts`); the `"./editor"` entry enables exactly:

| Kind | Tiptap/ProseMirror element | Editable | Notes |
| --- | --- | --- | --- |
| Node | `doc` | — | Root. |
| Node | `paragraph` (attr `paragraphId`) | Yes | The only editable block in P0. |
| Node | `text` | Yes | Inline text. |
| Node | `hardBreak` | Yes | Inside a paragraph. In `text/plain` it is the interior newline of §5.1 (Shift+Enter; Enter splits instead). |
| Mark | `bold` (strong) | Yes | Keyboard + Markdown input. |
| Mark | `italic` (emphasis) | Yes | Keyboard + Markdown input. |
| Mark | `code` (inline code) | Yes | No code block follows from this mark. |
| Node | `preservedBlock` (attrs `paragraphId`, `raw`, `preservedKind`; `contenteditable=false`, atom) | No | Carries every unsupported block verbatim (§6.3). DS-internal node; never a Focus type. |

Everything else is absent from the schema. In particular there is no `heading`, `bulletList`, `orderedList`, `listItem`, `blockquote`, `codeBlock`, `table`, `image`, `link` mark or `horizontalRule` in the P0 schema. `StarterKit` is not enabled wholesale: `"./editor"` composes the granular extensions (`@tiptap/extension-document`, `-paragraph`, `-text`, `-bold`, `-italic`, `-code`, `-hard-break`, `-placeholder`, plus `UndoRedo` from `@tiptap/extensions`, as resolved at lot start) so that an upstream default can never silently widen the profile (`h2a-spec` §5.3: activating StarterKit defaults is not a fidelity policy). Undo/redo history is enabled; placeholder display is enabled and reads `messages.placeholder`.

`text/plain` fields use the same document model with marks disabled by the adapter (a plain paragraph's text is literal; Markdown input rules do not fire). Disabling marks never disables the `hardBreak` node: the interior-newline decision of §5.1 applies, so a plain paragraph may hold `hardBreak` content and Shift+Enter inserts it while Enter splits the paragraph.

### 6.2 What a paragraph may contain

An editable paragraph is a top-level paragraph whose inline content uses only text, `bold`, `italic`, `code` and `hardBreak` — the same editable set the merged Focus source codec accepts (§2.2 M6). For `text/plain` the marks are absent and the paragraph holds literal text plus any `hardBreak` interior newlines (§5.1): the plain source `"A\nB"` is therefore one editable paragraph, never two, and its `hardBreak` round-trips as the interior `"\n"` of its `ParagraphValue` text. A source paragraph containing a link, an image or raw HTML is not an editable paragraph: the host adapter segments it as a preserved block (§6.3), and the component renders it non-editable. The component never strips a link to make a paragraph editable.

### 6.3 Unsupported blocks: preserved and non-editable, never destroyed

- Tables, code blocks/fences, diagrams (including Mermaid sources), headings, lists (preserved until the §6.4 three-condition gate passes), blockquotes, images, raw HTML blocks and any other construct outside §6.1 are `preservedBlock` nodes when, and only when, they already exist in the source document the host segmented. They render as visibly non-editable regions (`data-preserved-block`, `contenteditable=false`, accessible name from `messages.preservedBlockLabel`) and no editor gesture can place the caret inside them or transform them.
- A preserved block's `raw` is carried byte-identical through mount, editing elsewhere, and unmount, and is emitted unchanged in every `RichTextDocument`. Serialisation never regenerates a preserved block from an AST. This carries h2a capital C11/K11-adjacent preservation: a global Markdown → Tiptap → Markdown round trip must never silently normalise unsupported content away. Preservation applies only to blocks that already exist in the source; it is not a paste-creation path (see the paste rule below and §7).
- **Paste never creates a preserved block (blocking, pinned contract).** Under the pin at `98060bd0a`, the Focus return transports only `ParagraphValue[]` with `blockKind: 'paragraph'` (merged `contract.ts`) through `diffParagraphs` (`diff.ts`), and `assertParagraphText` (`codec.ts`) refuses any text that segments to a non-paragraph or multi-block result (`unsupported-paragraph-format`). A paste that would create a table, a code fence/block, or any other non-paragraph block therefore cannot be carried by the return: creating a new `preservedBlock` would make visible content disappear from the return, and flattening it into paragraphs would be refused by `assertParagraphText`. The component refuses such a paste as a whole, reports it exactly once through `onUnsupportedPaste` (§5.5), and leaves the document, the selection and the host-side return unchanged: no `onChange` is emitted, no block is inserted, no existing block is altered. Creating preserved blocks from paste requires an explicit h2a evolution (a return that can transport non-paragraph blocks), a new pin recorded in Appendix B and in `spec/SPEC_EVOL_DS_JSON_RENDER_STANDARD.md` §11.2.1, and a joint witness; it is not available under the current pin.
- If a user gesture would span an existing preserved block (select-all delete, paste replacing a selection covering one), the component refuses the destructive span and reports it through `onUnsupportedPaste`/a no-op with the preserved blocks intact; it never deletes a preserved block as a side effect of a text gesture. Explicit host-driven removal (the host supplies a new `value` without the block) is the only removal path.

### 6.4 List-item paragraph question (h2a V7): preserved until the contract evolves (blocking)

- **Rule.** Lists stay preserved and non-editable under §6.3. At the pinned contract (`98060bd0a`), `packages/focus/src/editing/codec.ts` segments only top-level `Paragraph` nodes as editable and `packages/focus/src/editing/anchors.ts` creates paragraph units only from editable segments, so no list item is an ordinary editable paragraph unit, and §6.1 contains no `bulletList`, `orderedList` or `listItem` node. The DS alone never widens P0.
- **Three-condition gate.** List items join the editable profile only when all three conditions have passed, in this order, and the widening is then made by amending §6.1 in a follow-up delivery: (1) a compatible h2a evolution — the Focus codec and anchors are extended so list-item paragraphs are accepted as editable units with stable identities, published as a new `@sentropic/focus` contract; (2) a new pin — that contract is pinned by exact version in Appendix B and in `spec/SPEC_EVOL_DS_JSON_RENDER_STANDARD.md` §11.2.1 in the same delivery; (3) the joint FE-1/FE-2 witnesses — the h2a FE-1 source-codec witness and the DS FE-2 round-trip witness pass on the same list corpus, proving on the final bundled codec that bullet and ordered list items keep a stable `paragraphId` on the list item's paragraph through open/edit/close, split, merge and Markdown serialisation, with block identity at DS level and full-source byte-identical output for unchanged lists at the host splice (§6.5, §13.1).
- **DS-only evidence.** The RT-2 list round-trip run (§11, §12) is recorded as DS block-level evidence only (lists mount as preserved blocks, block-level identity per §6.5; full-source output identity for unchanged lists is witnessed host-side, §13.1). A passing DS-only result changes nothing: lists remain preserved, the delivery is announced exactly as "P0 fields editable, lists preserved" (`h2a-spec` D20), and no adapter enables a list extension. A failing or unrun list test likewise keeps lists preserved; it never blocks the P0 delivery and never gets announced as list editing.

### 6.5 Markdown round-trip path and its qualification

- Path: source Markdown field → host segmentation (merged Focus codec, `segmentMarkdown`/`segmentText` at `98060bd0a`; the DS ships no source segmentation) → `RichTextDocument` → ProseMirror document (the `"./editor"` entry, §4.2) → editing (ProseMirror transactions and history) → `RichTextDocument` → per-paragraph Markdown via `@tiptap/markdown` in `"./editor"` for editable paragraphs only, with preserved `raw` slices spliced back at their block positions by the host adapter into the retained source (§13.1). Plain fields bypass Markdown entirely. The DS never assembles a full source string: it has no separator to write (§5.1), so any DS-side full-source serialiser would have to invent separators the model does not carry.
- The Markdown bridge is `@tiptap/markdown ^3.32.0` over the §6.1 extension set, reached only from `"./editor"`, configured with the profile's serialisation options whose data form is fixed in `packages/rich-text/src/profile.ts` (RT-0, `"."` entry) and whose live wiring lives in `"./editor"` (§12). Reason for the change from the observed sentropic `tiptap-markdown ^0.9.0` (§2.3): `@tiptap/markdown` is the official bridge from the Tiptap monorepo on the same v3 major as the core (`@tiptap/core 3.32.0`), with a v3-native storage API, where the community `tiptap-markdown` line targets the v2 API surface. Transitive dependency `marked` (MIT, see §9.2). The exact `@tiptap/markdown` and `@tiptap/*` versions are pinned in the DS lockfile at lot start (`@tiptap/markdown 3.32.0`, `marked 17.0.6`) and recorded in the lot report.
- **Two identity levels (blocking; RT-0 resolution of RED 2 against §5.1).** The merged specification previously required the DS core to reproduce the whole source byte-identically (former §11 RED 2) while §5.1 stores no separators and the Focus codec refuses paragraph texts carrying separators (see §5.1). No `RichTextDocument` value can satisfy both, as the RT-0 run measured (a 6-byte residue: two CRLF separators and trailing blank content, with every block value already identical). The rule is now split by ownership, with no DS-side splice helper (justification at the end of this section):
  - **DS level — block identity.** At the DS boundary the round-trip assertion is block-level: for an unedited cycle, mount → focus → blur → unmount emits zero `onChange` (§5.3), block order and every `paragraphId` are unchanged, every unchanged paragraph `text` is byte-identical to the host-segmented slice that entered, and every preserved `raw` is byte-identical. Capture honours the same identity as a pure read (§6.6): it returns the untouched source bytes without re-serialising them, including for a paragraph whose only change is in a neighbour and for a version restored by undo. For a single-paragraph edit, the edited paragraph carries exactly the new text and every other block (neighbouring paragraph texts, preserved `raw` values, order, identities) is unchanged. No DS test compares a reconstructed full source string, and no DS code joins blocks with an invented separator.
  - **Host level — full-source identity.** Reproducing the whole source byte-identically, separators included (blank lines, CRLF/CR forms, trailing whitespace, final newline), is the host splice: FE-3 reuses the pinned `applyParagraphChanges` (`packages/focus/src/editing/diff.ts:40–83` at `98060bd0a`) as that splice — it preserves every gap byte (preserved `raw` slices included, which never leave the gaps) and joins genuinely inserted paragraphs with `"\n\n"` — with the retained baseline kept separately as the `freezeReturn` input. It is witnessed in h2a lot FE-3 (§13.1, including agreement after split, merge, paste and undo, with the §5.10/§2.2 M8 general exception: under this pin the agreement part of that witness covers only drafts whose every paragraph passes `assertParagraphText`, whose spliced ranges validate and no paragraph of which is flagged by the §6.6 bridge test; for any draft containing a paragraph refused by either check or flagged by the bridge §13.1 asserts the unsupported-at-export behaviour and draft preservation of §5.10 instead (cause `bridge-non-representable` for the bridge-flagged class), and agreement for such drafts becomes claimable only under the §5.10 evolution-plus-new-pin condition) and recorded as an interface requirement there. A DS green never substitutes for that witness.
- **Qualification, not declaration (`h2a-spec` §5.3/U1).** A declared `@tiptap/markdown` version is not a round-trip proof. The profile is qualified only when the §11 round-trip witnesses pass on the final bundle: at DS level, open/edit-nothing/close over every P0 construct and every preserved construct of the corpus yields block identity (paragraph above) and the host-side Focus diff of the unedited document against its baseline is empty; at host level, the FE-3 splice witness (§13.1) yields the byte-identical full source. Any marker, spacing or line-break normalisation of unchanged *block content* at DS level is a failure, because it would manufacture false amendments; separator bytes are not the DS's to normalise or to preserve. The component itself computes no delta for this check (§5.3); emptiness is established host-side with `diffParagraphs`.
- **Segmentation stays host-side; DS equivalence is conversion equivalence.** The Focus codec (`@lezer/markdown` slices, §2.2 M5) remains the only segmentation authority: the same source produces the editable/preserved block boundaries and paragraph texts host-side, and the DS neither mirrors nor substitutes that segmentation in production code. What the DS qualifies instead is that its `"./editor"` conversion preserves exactly the host-segmented blocks it is given: `RichTextDocument` (built host-side from a vector's segments) → ProseMirror document → `RichTextDocument` returns the same ordered blocks, the same identities, the same paragraph texts and the same preserved `raw` values, and each editable paragraph's Markdown through `@tiptap/markdown` re-segments host-side to exactly that paragraph (the `assertParagraphText` shape). The qualification oracle stays the DS-side vector set of §11.3/RT-2 (`packages/rich-text/tests/fixtures/focus-segmentation-vectors.json` [N], exercised by `packages/rich-text/src/segmentation-equivalence.test.ts` [N] against `"./editor"`): at the pin `98060bd0a` no h2a-published data artefact delivers the Focus codec's expected boundaries — the fixtures under `packages/focus/tests/` (including `packages/focus/tests/fixtures/editing-vectors.json`) sit outside the `files` field of `packages/focus/package.json` (`["dist", "registry/entries.v1.json", "schemas/", "skills/", "README.md", "LICENSE"]`) and no `exports` entry names them, so they are not importable by pinned package version and this specification invents no such artefact. The DS vectors carry verifiable provenance (§11.3) and are the mandatory RT-2 gate today; a future h2a-published oracle (a dedicated exported fixture artefact at a new pin) is a `source-gap` dependency, recorded as such in §16, and replaces the DS vectors only through a pin bump recorded in Appendix B and in `spec/SPEC_EVOL_DS_JSON_RENDER_STANDARD.md` §11.2.1. The absence of that published oracle never suspends, skips or weakens the RT-2 gate.
- **Why no DS-side splice helper.** A DS helper that rejoined blocks into a full source would need the original separator bytes and block ranges, which are Focus manifest data (D9 ownership, §0.2): the DS would have to receive, store and interpret host segmentation output beyond the `RichTextDocument` wire shape, duplicating the host adapter's splice and creating a second place where separator handling could drift from the Focus codec ranges. The splice therefore stays in the single owner that already retains the source and the ranges — the host adapter — and the DS exposes no `sourceFromDocument`-style full-source serialiser (the RT-0 hand-written codec is disposed of in §12).

### 6.6 Representable paragraph content: the non-mutating rule (blocking)

This subsection states which paragraph contents each format can carry, and what the editor does with the rest. It replaces every DS-invented whitespace/hard-break encoding and the former capture-time canonicalisation (`Canon`): no encoding the DS invents can be both lossless and accepted by the host, because Markdown itself cannot carry a paragraph that is only whitespace or only hard breaks, cannot carry leading hard breaks through a parse, and the pinned Focus `assertParagraphText` (`packages/focus/src/editing/codec.ts:58–66` at `98060bd0a`, see §2.2 M8) refuses, in `text/markdown`, any paragraph that is not exactly one editable Markdown segment covering the whole text (`segmentMarkdown(text)` yielding one `editable` segment at `[0, text.length]`, `""` excepted at line 59). The rule below therefore defines a representable set and a reported behaviour outside it; it does not encode around either limit and it never transforms the draft to fit the limit.

- **Wire principle (blocking).** A paragraph's wire `text` (§5.1) is exactly one of three things, and nothing else: the untouched source bytes of the *Untouched paragraphs* bullet below, for `text/plain` the literal text of the *`text/plain`* bullet below, or for an edited `focus.markdown.p0@1` paragraph the serialisation produced by the Markdown bridge (`@tiptap/markdown`, §6.5) for that paragraph, without post-processing. No synthetic marker of any kind is allowed in the wire text and no post-processing of any kind is applied to a bridge serialisation: no DS-invented escape, sentinel, count encoding, whitespace relocation, break restoration, or private interpretation of a literal sequence as a break count. A literal sequence that merely looks like a former marker (for example the two-spaces-plus-newline sequence `"  \n"`, or its repetitions) is ordinary text, judged by the same representability test below; DS code MUST NOT decode it into `hardBreak` nodes. Syntax the bridge itself emits and parses as Markdown (for example an interior hard break between two visible texts) is bridge syntax, not a DS marker.
- **Untouched paragraphs keep their exact source bytes (blocking).** A paragraph is *untouched* at a read (`onChange` emission or capture) when no completed gesture since mount, since the last rule-4 application (§5.6), or since the undo/redo step that restored its current version has touched its block: its live ProseMirror content is still the content parsed from the wire text that entered for its `paragraphId`, and a version restored by undo carries the source bytes recorded for that version. An untouched paragraph's wire is those exact source bytes, byte-identical, at capture, after neighbouring edits, and after an undo that restores it (§6.5 DS-level block identity, `h2a-spec` D12). Capture and emission therefore never re-serialise an untouched paragraph through the bridge: mounting `_emphasis_` and capturing, with or without an edit in a neighbouring paragraph, yields the wire `"_emphasis_"`, never `"*emphasis*"`. Every other paragraph is *edited* and takes its wire from the two bullets below. Preserved blocks are unchanged by this rule: their `raw` is verbatim (§6.3).
- **`text/plain`, edited paragraphs (blocking).** Literal text, with no canonicalisation, no prevention and no marker: the ProseMirror content of a paragraph (ordered `text` and `hardBreak` children, §6.1) maps to wire by writing each text child verbatim and each `hardBreak` as exactly `"\n"`, in child order (`hardBreak` ⇔ `"\n"`), and maps back by splitting the wire on `"\n"` in order (every `"\n"` becomes one `hardBreak`, empty pieces produce no text child). Whitespace is exact: spaces, tabs and their order and position (leading, interior, trailing, adjacent to a break) are preserved byte-for-byte, and a space typed at the end of a line is never removed from the live editor. The literal mapping itself is lossless for every such content, including whitespace-only, break-only and leading/trailing-break contents; whether the resulting wire then passes the pinned `assertParagraphText` for `text/plain` is the separate representability question of the next bullets (for example a leading or trailing `"\n"` is refused there), and §6.6 neither trims nor encodes a refused wire.
- **Representability is a reported property, never a transformation (blocking).** Let `P` be the live ProseMirror inline content of one paragraph (ordered children: `text` nodes with their exact strings and marks, and `hardBreak` nodes) and let `W` be its candidate wire (the untouched source bytes for an untouched paragraph; the literal mapping above for an edited `text/plain` paragraph; `W = bridgeSerialise(P)`, the `@tiptap/markdown` serialisation of a single-paragraph document holding `P`, for an edited `text/markdown` paragraph). The test below is evaluated for every paragraph on each emission and capture, with that paragraph's candidate wire. Let `bridgeParse(W)` be the inline content of the single paragraph the bridge parses `W` back to (undefined when the bridge yields no paragraph, more than one block, or a non-paragraph block), with exactly one explicit exception: the exactly-empty wire `W === ""` maps to one empty paragraph, so `bridgeParse("")` is defined as `[]` (the inline content of that empty paragraph), even though the pinned bridge itself parses `""` to `{ type: "doc", content: [] }` (measured on `@tiptap/markdown` 3.32.0, §11.4 restoration row). This exactly-empty mapping applies both here, in condition (1) of the representability test, and at remount (§6.6 *Round-trip guarantee* bullet and the `paragraphTextToProseMirror` conversion it governs: remounting a wire `""` yields one empty paragraph with content `[]`, never zero blocks). The exception is narrow and extends no further: it does not make a whitespace-only content representable — an edited `[text("   ")]` serialises to `""`, and `bridgeParse("") === []` does not deep-equal `[text("   ")]`, so condition (1) still fails and the paragraph stays flagged — and it does not extend to any other paragraph-less parse: every other `W` whose bridge parse yields no paragraph (for example a whitespace wire the bridge parses to zero blocks, or a multi-block or non-paragraph result) keeps `bridgeParse(W)` undefined. The paragraph is **representable** if and only if both hold: (1) `bridgeParse(W)` is defined and deep-equals `P` — same ordered children, same node types, same exact text strings, same marks (for `text/plain` this condition is the literal mapping itself and holds by construction) — and (2) `W` passes the pinned `assertParagraphText(W, format)` (`packages/focus/src/editing/codec.ts:58–66`): for `text/markdown`, `segmentMarkdown(W)` is exactly one editable segment covering `[0, W.length]`; for `text/plain`, `segmentText(W)` is exactly one segment covering `[0, W.length]`; the empty wire `W === ""` passes by the line-59 exception in both formats. The two conditions are independent and neither implies the other: at the pinned bridge, `[text(" A")]` serialises to `" A"` and satisfies (1) while failing (2), the anchored mixture `[text("A "), hardBreak, text(" "), hardBreak, text(" B")]` serialises to a wire whose parse yields two paragraphs so (1) is undefined, a paragraph holding literally `# titre` serialises to `"# titre"` whose parse is a heading so (1) is undefined, and `"A "` satisfies both. Representability is decided only by this two-condition test, never by a pattern list, and a paragraph failing either condition is **non-representable**: the failure is reported, the live content is never rewritten to make it pass. Derived consequences at the pinned bridge, stated as properties and not as additional definitions, and restricted to edited `text/markdown` paragraphs whose candidate wire is the bridge serialisation (`W = bridgeSerialise(P)`): a non-empty such paragraph with no visible character, a paragraph whose first child is a `hardBreak`, a paragraph ending in a `hardBreak`, and any interior arrangement the bridge does not round-trip with child order intact each fail (1) or (2); gathering texts ahead of breaks or breaks ahead of texts is a failure of (1), never a permitted normalisation. This consequence does not extend to untouched paragraphs: an untouched source wire `"&#32;"` parses to `[text(" ")]` at the pinned bridge and satisfies both conditions, so a non-empty paragraph with no visible character does not fail as such while it stays untouched — it is judged only once edited and serialised by the bridge. An untouched paragraph whose wire entered as a host-segmented slice satisfies the test by construction (its live content is the parse of that slice and the slice passed the host segmentation), so it is never flagged while it stays untouched; preserved blocks are outside this test.
- **Reporting surface (blocking; §5.3/§5.6 fit).** Non-representability is reported through the existing component surface as data, with no new callback and no text carried: the `"."` entry defines `RichTextRepresentability { nonRepresentableParagraphIds: readonly string[] }` (the flagged `paragraphId` values in document order, `packages/rich-text/src/model.ts`, §5.3/§5.5). Every `RichTextChangeEvent` carries it beside `document` and `gesture`, computed by the same `"./editor"` conversion that produces the emitted wire, and `captureDocument()` resolves with `RichTextCaptureResult { document, representability }` for the captured revision (§5.5/§5.6), so the host learns the flag on the live emission path and again, atomically, on the export-relevant capture path. This fits §5.3 because the flag carries identities only — no `before`/`after` text, no diff, no Focus type or error (§5.3 no-diff rule) — and it fits §5.6 because it rides the deferred capture that the host freeze already awaits, adding no second read. The flag is not part of `RichTextDocument`, never enters the §5.6 document equality, never sets or clears the §5.6 unacknowledged-local-revision flag, never by itself emits an event, and is recomputed on each emission and capture. The `"./editor"` conversion evaluates condition (1) with the bridge and condition (2) by the pinned predicate's single-segment coverage criterion applied to `W`; no `@sentropic/focus` import, type or error string crosses the DS boundary (§5.3), and the manifest range check (`validateManifest`, `anchors.ts:56`) stays host-side, reported under §5.10 exactly as before.
- **Flagged paragraphs: draft preserved, export unsupported (blocking).** When a paragraph is flagged, the draft stays exactly as typed in the live editor: no transaction filter, input rule, per-keystroke serialisation round-trip or capture step removes, trims, reorders or rewrites any part of it, and a space typed at the end of a line or a trailing break the user may still type past stays live while editing. Capture still returns the candidate wire `W` for the flagged paragraph, together with the flag; the wire is not emptied, replaced or otherwise adjusted because the paragraph is flagged — a flagged `# titre` paragraph captures as the wire `"# titre"` with its identity flagged, never as an empty paragraph, so capture can never erase visible text. Export of a flagged paragraph is unsupported: the host reports it under §5.10, generalised to `text/markdown` by the *Precedence* bullet below — under the bridge's own cause `bridge-non-representable` when the paragraph is flagged by the bridge alone, distinct from the h2a errors `unsupported-paragraph-format`/`unsupported-range` — freezes no return claiming agreement for it, and advances no baseline (§5.3). The DS component itself computes no diff and raises no Focus error (§5.3); the unsupported outcome is surfaced by the flag at DS level and by the pinned refusal at host export.
- **Precedence: §5.10 governs every residual refusal (blocking).** §5.10, as rewritten, governs every residual refusal in both formats: a wire failing the pinned `assertParagraphText` in either format, a spliced range failing `validateManifest`, and a Markdown paragraph failing condition (1) above are all reported unsupported at export with the draft preserved, and §6.6 creates no agreement claim for any of them. §6.6 adds no transformation on top of §5.10; its only input-side exception is the narrow prevention of the next bullet, which §5.10 itself authorises. In any apparent conflict between a §6.6 statement and §5.10, §5.10 prevails, except for that single authorised prevention.
- **Prevention stays minimal and harmless (blocking).** In a `text/markdown` field only, Shift+Enter is a no-op when the inserted `hardBreak` would become the first child of its paragraph — Shift+Enter at offset 0 of a paragraph, which includes Shift+Enter in an empty paragraph: the gesture would create only a non-representable leading-break state and has no other effect, so refusing the keystroke loses nothing the user has typed. A no-op means exactly: no ProseMirror transaction is dispatched for the break, no `onChange` is emitted, no history entry is created, and the caret and selection are unchanged. This branch requires a `hardBreak`: a paragraph whose children are only whitespace text, with no `hardBreak`, is never prevented, stripped or flagged at input — it stays live exactly as typed and is judged only by the representability test at emission and capture. No other completed gesture is prevented or repaired under this rule: a paste, split, merge or deletion that leaves a leading `hardBreak`, a break-only paragraph or a whitespace-and-breaks paragraph standing completes normally, and the resulting paragraph is flagged and preserved under the bullets above, never corrected by omitting `hardBreak` nodes in the same transaction. This prevention applies only to `text/markdown`; `text/plain` inserts the break literally at any position (the *`text/plain`* bullet above).
- **No mutation at capture, ever (blocking; capture protocol).** Capture (`captureDocument()`, §5.6) reads the live document and never changes it: it dispatches no ProseMirror transaction, emits no `RichTextChangeEvent` and no other event, creates, consumes or clears no history entry, and leaves the live ProseMirror document, the caret, the selection, the scroll position, the composition state and the last acknowledged document (§5.6) exactly as they were. There is therefore no capture event whose provenance, counting or ordering would need definition: `RichTextGestureKind` (§5.3) gains no capture kind, the echo rules of §5.6 see no capture effect (a host echoing a captured document back as `value` is evaluated under rules 1–4 exactly as any other incoming value), and a capture made during IME composition stays deferred under §5.6 — it waits for the commit and reads the committed document, without cancelling, committing or otherwise touching the composition. A second capture with no intervening gesture resolves with a deep-equal document, byte-identical wires and the same flag. Any implementation whose capture applies a computed form to the live document, emits an event, or alters history or selection fails this rule, whatever it returns.
- **Round-trip guarantee (blocking, testable equality).** Live ⇔ capture ⇔ remount is guaranteed for representable paragraphs only — that is, for every untouched paragraph and for every edited paragraph that is not flagged. For such a paragraph, with `D_cap` the document of the capture result, `D_rem` the ProseMirror document obtained by remounting `D_cap`, and `D_cap2` the capture of `D_rem`: `D_rem` deep-equals the live paragraph content (same ordered children, exact texts, marks; identities and block order preserved) and `D_cap2` byte-equals `D_cap` for that paragraph. Remount applies the same exactly-empty mapping as the representability test: a representable empty paragraph (wire `""`, live content `[]`) remounts to one empty paragraph with content `[]`, and its second capture is again `""` with an empty flag — the mapping that the pinned bridge's paragraph-less parse of `""` does not provide on its own, and that no other paragraph-less wire receives. A flagged paragraph has no remount guarantee: remounting its captured wire may yield different content or no paragraph, and no test or host path may treat that remount as faithful. Its recovery is the live draft, preserved in the mounted editor, plus the host export reporting of §5.10; a host that must keep the text keeps the live editor (or the user's next edit) rather than unmounting and remounting from a flagged capture. Any hidden encoding that would make a flagged content appear to satisfy these equalities (a marker a later parse decodes differently from the bridge, a reordering of children, a break count recovered from literal text) fails this rule by construction.
- **Degenerate-wire removal (blocking, next code run).** The next code run removes `degenerateParagraphWire` (`packages/rich-text/src/editor-conversion.ts`) and every synthetic marker it relied on, including any restore path that synthesises `hardBreak` nodes the bridge parse does not produce (counting trailing `"  \n"` repetitions, rebuilding a break-only or whitespace-plus-breaks wire, or gathering whitespace text ahead of breaks). After that run, a Markdown paragraph's wire is exactly the untouched source bytes or the bridge serialisation without post-processing, its remount is exactly the bridge parse (subject only to the prevention above), its representability is reported through the surface above, and a plain paragraph's wire is exactly the literal mapping above. Tests that expected degenerate-wire preservation are replaced by the §11.4 table; keeping a parallel private parse beside the bridge fails §6.6.

## 7. Security (RT-D4)

- **Parsing boundary.** Mounted content and pasted content enter only through the P0 ProseMirror schema (§6.1). Raw HTML is never assigned to the DOM as markup by the component; there is no `innerHTML` content path. Content already present in the mounted source that the schema cannot represent is a preserved block (§6.3); pasted content that the schema cannot represent as paragraphs is refused, per the paste rules below. The component never reconstructs Markdown source from rendered HTML.
- **Paste.** On paste, the component parses the clipboard payload (`text/html` when present, else `text/plain`) through the schema with these rules, in order:
  1. Strip every `data-paragraph-id`/`paragraphId` and allocate fresh identities (§5.2).
  2. Drop `script`, `iframe`, `object`, `embed`, `form`, event-handler attributes (`on*`), and `style` attributes wholesale; a pasted `</script>` sequence is text or dropped, never an element.
  3. Links: the `link` mark is not in the schema, so pasted links degrade to their text content; `javascript:`, `data:text/html` and other scriptable protocols never survive as attributes because no link node exists to carry them.
  4. Images: the `image` node is not in the schema. Remote images (`http:`, `https:`, protocol-relative) and local/data images alike produce no `<img>`, no request and no placeholder fetch; the alt text, when present, is inserted as plain text and the rejection is reported via `onUnsupportedPaste`.
  5. Non-paragraph blocks (refusal, pinned contract): if the payload, after rules 1–4, would create any block that is not a `paragraph` — a table, a code fence or code block, a heading, a list, a blockquote, an image block, a horizontal rule, a raw HTML block, a diagram source, or any other construct outside §6.1 — the whole paste is refused. The component emits exactly one `onUnsupportedPaste` carrying the `rejectedKinds` that would have been created (§5.5), emits no `onChange`, inserts no block, and leaves the document, the selection and the host-side return byte-identical to their pre-paste state. This rule applies whether the payload carries Markdown source text (`text/plain` with a fence or table syntax) or only rendered HTML (for example a `<table>` element): the component does not turn either form into a preserved block and does not flatten either form into paragraphs. Paragraph-only paste (plain paragraphs with `bold`/`italic`/`code`/`hardBreak`) is the only paste that inserts content, with fresh identities under rule 1. Their insertion as preserved blocks would require the h2a evolution, new pin and joint witness named in §6.3 and is refused until then.
- **No remote fetch.** The component loads no remote image, font, stylesheet or script and issues no request (§5.9). Rendered output contains no `src`/`href` to a remote origin from edited content.
- **CSP.** The component is compatible with the portable host's `connect-src 'none'` posture (`h2a-spec` §5.5/D5) and with the MCP Apps default CSP shape recorded in the JSON render standard (`connect-src 'none'`). It requires no `unsafe-eval`, no inline-script exception beyond the host's own bundle, and no `img-src`/`font-src` remote allowance. Any future need for a CSP exception is a stop signal to record, not a waiver to add silently.

### 11.4 Representable-form round-trip table (blocking, §6.6)

- **Ordered mixture (blocking).** At least these ordered mixtures, in this child order: (i) exactly space, break, space, break, space — children `[text(" "), hardBreak, text(" "), hardBreak, text(" ")]`. In `text/plain`: capture wire exactly `"A \n \n B"`, flagged (two `segmentText` segments), live preserved, literal remount yielding the same children as a mapping result. In `text/markdown`: capture wire exactly `"A   \n   \n B"` (bridge serialisation), flagged (its parse yields two paragraphs), live-after-capture deep-equal to the listed children, and no remount equality asserted.
- **Literal marker-like text (blocking).** At least: a paragraph carrying literally the former marker sequence `"  \n"` (two spaces and a newline as literal characters) and its repetition `"  \n  \n"`, and the collision sequence mount `"  \n "` then delete the last space by a native transaction, leaving the literal sequence `"  \n"`. In `text/plain` each wire is read by the literal mapping of §6.6: the collision sequence leaves live children `[text("  "), hardBreak]`, capture wire exactly `"  \n"`, flagged (`segmentText` refusal), live preserved, and the literal remount yielding the same children as a mapping result; the repetition leaves `[text("  "), hardBreak, text("  "), hardBreak]` with wire `"  \n  \n"` on the same terms. In `text/markdown` the corresponding live content is constructed by typing (two spaces, then Shift+Enter at the end, which is not the §6.6 no-op): live `[text("  "), hardBreak]`, capture wire exactly `""` (bridge serialisation), flagged, and live-after-capture unchanged. In neither format may DS code decode the two-spaces-plus-newline sequence into a `hardBreak` count beyond the format's own mapping, and the ProseMirror child types (text vs `hardBreak`) and the native copy text MUST be asserted before and after capture, so a literal-to-break conversion fails the row.
- **Structure-change row: `# titre` (blocking).** In `text/markdown`, type `# titre` character by character into an empty paragraph: live children exactly `[text("# titre")]`, capture wire exactly `"# titre"` (bridge serialisation), the paragraph flagged (its parse is a heading, not a paragraph), live-after-capture still `[text("# titre")]` — capture never reduces a flagged paragraph to an empty document. In `text/plain`, typing the same characters yields the literal wire `"# titre"`, unflagged (one covering `segmentText` segment), with live ⇔ capture ⇔ remount exact.
- **Untouched-source row: `_emphasis_` (blocking).** Mount a `text/markdown` document of two paragraphs, wires `"_emphasis_"` and `"voisin"` in that order. Edit only the second paragraph (append `"!"` through a native transaction), then capture: the first paragraph's capture wire is exactly `"_emphasis_"` (byte-identical source, never `"*emphasis*"`), its identity is absent from `nonRepresentableParagraphIds`, and the second paragraph's wire is the bridge serialisation of its edited content. Variant: edit the first paragraph, undo that edit, then capture with a further edit in the second paragraph — the restored first paragraph again captures as exactly `"_emphasis_"`. Any re-serialisation of the untouched or undo-restored paragraph fails the row (§6.5, §6.6).
- **Restoration sequence (blocking, exact contents in both formats).** The prescribed sequence is Shift+Enter → capture/remount → type B → capture/remount, in each format, starting from one empty paragraph (wire `""`, identity kept throughout); a row that stops at the first remount without the following edit does not satisfy this bullet. In `text/markdown`: Shift+Enter is the §6.6 no-op (assert no transaction, no `onChange`, no history entry, caret unchanged), live children `[]`; capture resolves with document text `""` and an empty flag; remount yields `[]` — one empty paragraph by the §6.6 exactly-empty mapping (`bridgeParse("") === []`), not the pinned bridge's paragraph-less parse of `""`, and that mapping is asserted here for both the test and the remount while a whitespace-only capture of `""` in the trailing-break row below stays flagged with no remount equality; place the caret in the paragraph and type `B` — live `[text("B")]`, one `onChange` with wire `"B"` and an empty flag; capture yields wire `"B"` with an empty flag and live-after-capture still `[text("B")]`; remount yields `[text("B")]`; second capture yields wire `"B"`. - **Leading/trailing-space rows (blocking).** In `text/markdown`: type a leading space (` ` then `mot`): live `[text(" mot")]`, still present before capture, capture wire exactly `" mot"`, flagged (bridge fixed point holds, pinned `assertParagraphText` refuses), live-after-capture unchanged; type a trailing space (`mot` then ` `): live `[text("mot ")]`, capture wire exactly `"mot "`, unflagged (both §6.6 conditions hold at the pinned bridge), live ⇔ capture ⇔ remount with a byte-identical second capture; type `word`, space, `next` so the space becomes interior, asserting it survives capture unchanged and unflagged. In `text/plain` leading and trailing spaces round-trip exactly by the literal mapping, with the flag decided only by the pinned `assertParagraphText` for `text/plain`.
- **Trailing-break and whitespace-only rows (blocking).** In `text/markdown`: `Alpha` + Shift+Enter at the end stays live as `[text("Alpha"), hardBreak]` before capture, capture wire exactly `"Alpha  \n"` (bridge serialisation), flagged (the re-parse loses the break), live-after-capture unchanged, no remount equality asserted; the variant that types `B` after that break before capture (break now interior) is representable exactly when the §6.6 test passes and then round-trips with child order intact; a whitespace-only paragraph (type three spaces) stays live as `[text("   ")]`, capture wire exactly `""`, flagged, live-after-capture still `[text("   ")]` — the empty wire is the bridge serialisation, never an emptied live paragraph. In `text/plain` each content takes the literal mapping above, with the flag decided only by the pinned `assertParagraphText` for `text/plain`.
- **Capture purity and flag assertion (blocking, §6.6/§5.6 protocol).** Every row asserts the `representability` of the capture result and of the last `onChange` against its expected flagged identities (exact array, document order), and asserts the absence of any capture-time mutation or event: the `onChange` count is identical immediately before and after each capture, the live ProseMirror children deep-equal their pre-capture value, the undo/redo history depths are unchanged, and the selection (anchor `paragraphId` plus intra-paragraph offset) is unchanged. A second capture with no intervening gesture resolves with a deep-equal document, byte-identical wires and the same flag; capture during IME composition stays deferred under §5.6/RED 5 and reads the committed document without touching the composition. Emitting any event from capture, gaining a `RichTextGestureKind` for capture, or changing live content, history or selection at capture fails the table.
- **Guarantee assertion (blocking).** Every representable row asserts the §6.6 equality: remounted ProseMirror deep-equals the edited live content and the second capture byte-equals the first. Every flagged row asserts the exact capture wire, the exact flag, and live-after-capture deep-equal to live-before-capture, and asserts no remount equality. Removing `degenerateParagraphWire` (§6.6) MUST NOT be accompanied by any row that expects a synthetic marker in the wire; a wire containing a DS marker, a remount whose children were reordered or synthesised beyond the bridge parse, or a capture that mutates the live document fails the table.

## 13. Interfaces with h2a lots (RT-D10)

### 13.1 What FE-3 consumes, and when

FE-3 (h2a portable in-place editing) consumes, from the published DS packages at an exact pinned version recorded in `packages/h2a/focus-kit/package.json` host-side:

- `@sentropic/design-system-rich-text` (the pure `"."` entry for types, profile descriptors and document logic, and the `"./editor"` entry for the runtime the adapter mounts) and `@sentropic/design-system-svelte/rich-text-editor` (the component), imported by exact subpath — never the DS barrel.
- The host adapter (`packages/h2a/focus-kit/src/EditableField.svelte` + `editing-session.js`, h2a-side files named by the h2a specification) supplies: the Focus manifest's paragraph identities as `RichTextDocument` block IDs, a Focus-compatible `allocateId`, the resolved `messages` catalogue, the `editable` state from dossier-level amend mode, and the retained Focus baseline (`ParagraphValue[]` from the manifest it holds). On each `RichTextChangeEvent` it maps `document.blocks` to draft `ParagraphValue[]` through those identities and computes the per-paragraph diff with `@sentropic/focus/editing` (`diffParagraphs`, merged `packages/focus/src/editing/diff.ts`) against the retained baseline, then splices host-side by reusing that same pinned module — `applyParagraphChanges` (`packages/focus/src/editing/diff.ts:40–83` at `98060bd0a`) — toward the return that h2a FE-4 machinery freezes. FE-3 implements no second splice and no second diff: `applyParagraphChanges` is the splice implementation FE-3 reuses (host-splice bullet below). The two pairs are kept separate: `applyParagraphChanges(baselineDocument, baselineManifest, transactions)` returns a spliced `{ document, manifest }` whose `baseHash` is `baseDigest(splicedDocument)`, while `freezeReturn` is always called with the retained baseline `(document, manifest)` unchanged; the spliced manifest is never substituted as the freeze baseline. `gesture` is consumed as provenance only (logging, caret handling); it is never translated into `ParagraphChange` records by hand, and no second diff algorithm exists on either side of the boundary. The retained baseline never advances on freeze or export (§5.3): `freezeReturn` preserves the supplied document and manifest and validates any previous return against that same base, and `carryManifest` is reserved for a new authoritative producer version once acknowledged. The FE-3 freeze check therefore runs the §5.3 witness end to end — baseline `A`, type to `B`, controlled echo of `B`, freeze `R1`, undo to `A`, freeze `R2` with `transactions: []`, identical `source.baseHash`/`manifest.manifestBaseHash` on `R1` and `R2`, and `R2` superseding `R1` — and any baseline advance at echo, freeze or undo fails FE-3. For export, the adapter awaits the component's deferred capture (`captureDocument()`, §5.6) so the frozen document is the displayed revision, never a mid-composition or stale snapshot. The DS component supplies no diff, no anchors and no baseline to the wire; the return envelope is built host-side.
- **Host splice: full-source byte identity (interface requirement on FE-3, blocking).** The DS boundary stops at block identity (§6.5); reproducing the source as a whole is the host adapter's splice, and FE-3 must implement and witness it as follows. (a) *Retention:* for each edited field the adapter retains the original source string and the Focus codec segmentation for it (the ordered `[{ start, end, editable }]` ranges from `segmentMarkdown`/`segmentText` at the pin, with the gap bytes between ranges — blank lines, CRLF/CR forms, trailing whitespace, final newline — never normalised, trimmed or re-emitted from a template). (b) *Splice (reuse, no second reconstruction):* on export FE-3 calls the pinned `applyParagraphChanges(baselineDocument, baselineManifest, [diffParagraphs(baselineValues, draftValues)])` and uses its returned `document` as the spliced source. That function is the only splice: at `98060bd0a` (`diff.ts:40–83`) it tokenises each field as gap bytes (`source.slice` between manifest paragraph ranges) interleaved with paragraph slices, replaces or deletes paragraph tokens in place, preserves every gap byte verbatim, and joins a genuinely inserted paragraph to its neighbours with `"\n\n"`. FE-3 writes no separator of its own, creates no range template and re-emits no gap from a template; split/merge/paste identity following (§5.2, §5.3 gesture provenance) decides only how `document.blocks` map to draft `ParagraphValue[]` before the diff, never a second range splice. The baseline pair retained under (a) stays the `freezeReturn` input (see the adapter bullet above); the spliced `{ document, manifest }` returned here is the exported source, not a new freeze baseline. (c) *Witnesses (mandatory, in FE-3, against the Focus codec ranges):* over the same corpus shape as §11 RED 2 (P0 constructs, preserved table/fence/heading/list, CRLF separators, trailing blank lines, final newline). *No-change:* open → edit nothing → the `applyParagraphChanges` output reproduces the original source byte-identically (full string equality, separators included) and `diffParagraphs` against the retained baseline is empty. *Single edit:* edit exactly one middle paragraph → the spliced source equals the original with exactly that paragraph's range replaced by the new text, every other range and every gap byte identical. *Refused paste (the FE-3 half of RED 7):* for each non-paragraph payload of §11 RED 7, after the DS refusal (document unchanged, selection unchanged, zero `onChange`, refusal reported — asserted DS-side in `paste.test.ts`), FE-3 asserts the host consequence with the retained baseline kept separately for `freezeReturn`: `diffParagraphs(baselineValues, draftValuesAfterRefusal)` adds no new transaction or change over the pre-paste draft, `freezeReturn` called with the retained baseline `(document, manifest)` yields a return unchanged from the pre-paste freeze (same transactions, same `source.baseHash`/`manifest.manifestBaseHash`, same supersession), and the whole source from `applyParagraphChanges` is byte-identical to the pre-paste source. *Agreement after split, merge, paste and undo (scope under the pin):* for each gesture — Enter-split in the middle of a paragraph, Backspace-merge, paragraph-only paste, and undo back toward the baseline, in each case where every paragraph of the resulting draft passes `assertParagraphText` (`codec.ts:58–66`), the spliced ranges validate (`anchors.ts:56`), and no paragraph is flagged in the capture result's `representability` (§6.6; a flagged Markdown paragraph is outside this scope on the same terms as a refused one, §5.10) — FE-3 captures the draft via `captureDocument()` (§5.6), maps it to draft `ParagraphValue[]`, computes `diffParagraphs` then `applyParagraphChanges` as in (b), and asserts the two sides agree: `readParagraphs(splicedDocument, splicedManifest)` from the spliced output deep-equals the captured draft `ParagraphValue[]` (same `paragraphId` values, same texts, same order and field addressing), and each spliced field string equals the baseline source with every gap byte preserved and every genuinely inserted paragraph joined by `"\n\n"` exactly as `diff.ts:40–83` writes it (undo to the baseline yields the empty diff and a spliced source byte-identical to the original). Any case in this scope failing fails FE-3; a DS block-identity green (RT-2) never substitutes for these witnesses, and these witnesses never re-open the DS model to store separators (§5.1). This is the single splice implementation; the DS exposes no splice helper (§6.5), so no second separator handling exists to drift from these ranges. *Draft paragraphs refused by the pinned contract — FE-3 halves of the named witnesses (mandatory; §5.10 general rule, §2.2 M8):* any draft containing a refused paragraph is outside the agreement scope above under the pin `98060bd0a`; the three named witnesses below illustrate the rule (they do not enumerate the refused shapes) and are witnessed separately, with no agreement asserted, while any other refused draft follows the same unsupported handling without needing a named witness. *Enter at end of paragraph* (FE-3): baseline `text/plain` `"A"` (manifest paragraph `[0,1]`), DS draft captured via `captureDocument()` is `["A", ""]` (the DS half is §11 RED 3, describe `Enter at end of paragraph`); FE-3 maps it to draft `ParagraphValue[]`, runs `diffParagraphs` then `applyParagraphChanges`, observes spliced source `"A\n\n"` with the second paragraph at range `[3,3]` (`diff.ts:74–79`), then asserts `readParagraphs(splicedDocument, splicedManifest)` throws `unsupported-range` (`anchors.ts:56` via `anchors.ts:74–75`, `segmentText("A\n\n")` holding no segment at `[3,3]` in `codec.ts:35–56`), the host reports the field's export as unsupported carrying that cause (§5.10), no return is frozen claiming agreement for this draft, the retained baseline `(document, manifest)` and its `baseHash`/`manifestBaseHash` are unchanged, and the captured draft `["A", ""]` is preserved unchanged for further editing. *clear a field containing separators* (FE-3): baseline `text/plain` `"A\n\nB"` (paragraphs `[0,1]`, `[3,4]`), DS draft captured via `captureDocument()` is the single empty block `[""]` keeping the first block's `paragraphId` (the DS half is §11 RED 3, describe `clear a field containing separators`; §5.2); FE-3 runs the same splice, observes spliced source `"\n\n"` (retained gap bytes) with its empty paragraph at `[0,0]` — the range that follows from keeping the first identity, a fresh identity would place it at `[2,2]` after the retained gaps — then asserts `readParagraphs` throws `unsupported-range` (`segmentText("\n\n")` is `[]`), the host reports the export as unsupported, no agreeing return is frozen, the retained baseline is unchanged, and the captured draft `[""]` is preserved unchanged. *Enter right after an interior newline* (FE-3): baseline `text/plain` `"A\nB"` (single manifest paragraph `[0,3]`, interior newline, §5.1), DS draft captured via `captureDocument()` is `["A\n", "B"]` (the DS half is §11 RED 3, describe `Enter right after an interior newline`); FE-3 maps it to draft `ParagraphValue[]` (replace of the baseline paragraph by `"A\n"` plus insert of `"B"`), runs `diffParagraphs` then `applyParagraphChanges`, and asserts `applyParagraphChanges` throws `unsupported-paragraph-format` at `diff.ts:66` (`assertParagraphText("A\n", 'text/plain')`, `codec.ts:58–66`: `segmentText("A\n")` is `[{ start: 0, end: 1 }]` and does not cover the whole text) before any spliced document or manifest is produced — no spliced source and no read-back equality are asserted for this witness under the pin — the host reports the field's export as unsupported carrying that cause (§5.10), no return is frozen claiming agreement for this draft, the retained baseline `(document, manifest)` and its `baseHash`/`manifestBaseHash` are unchanged, and the captured draft `["A\n", "B"]` is preserved unchanged for further editing. ### 13.3 What FE-8 needs from the DS

FE-8 (shared language and reactivity qualification, transversal, gating the first increment) receives from the DS:

- **Marker form:** the exact `untranslated` marker of §5.7 — visible text `⟦untranslated:rich-text.<key>⟧` plus `data-untranslated="rich-text.<key>"` — with the `rich-text.` key namespace fixed by RT-0's `messages.ts`. FE-8 renders a locale without a catalogue and lists every marker-only key in its build report; the DS guarantees the marker is never a hard-coded language string and that IDs, host-side diffs and stored values stay bit-identical across locales (§5.7). The component itself holds no diff whose identity could vary (§5.3).
- **Measurable reactivity invariants on the component** (budgets themselves are FE-8's phase-B output, `h2a-spec` D22; the DS supplies the measurable surface, not the numbers). Each invariant is observed directly on the mechanism it names; a proxy never satisfies it:
  1. *No remount per keystroke:* the internal witness (`packages/rich-text/src/reactivity.test.ts`, §11) counts editor-factory constructions and destructions across a typing burst — exactly one construction, zero destructions — and the browser suite additionally checks that the editor DOM root element is the same node before and after the burst. A stable DOM root alone never satisfies this invariant, because it does not prove a stable ProseMirror instance.
  2. *No whole-document reparse per keystroke:* the same internal witness counts calls to the `"./editor"` whole-document conversion / Markdown parsing entry across the burst — zero whole-document calls per keystroke; only the affected block is touched, as a ProseMirror transaction — and checks that preserved blocks' `raw` values are unchanged in every emitted document. A single `onChange` count, or equality of one `raw` string (a value with no observable object identity), never satisfies this invariant; the counters observe the construction and parsing calls directly, inside the package's own tests, and no editor, view or parser object is exposed in the public API to make the observation.
  3. *Caret/selection/scroll preservation:* locale (`messages`) and theme (token) changes preserve the real `Selection` anchor (block ID + offset) and scroll position — asserted in `RichTextEditor.browser.test.mjs`.
  4. *Stale-result safety:* an external update arriving during composition or while locally divergent surfaces via `onExternalConflict` and never overwrites (§5.6); the exported snapshot equals the displayed revision because the host freeze awaits `captureDocument()` (§5.6, §13.1), never a mid-composition state and never a bare re-read of the last `onChange`.
  5. *Zero network per session:* request interception in the browser suite counts zero requests from mount through edit to unmount (RED 8 network half, observed for the whole scenario).
- FE-7 (sentropic adoption) consumes the same subpath through its own facade; the DS surface it depends on is exactly §5, and the viewer lock it must preserve is RED 1's viewer fixture. ## 15. NOT covered

Each item below is explicitly excluded from this specification and from the Stage-1 delivery. Announcing any of them as delivered under this specification is a scope breach.

1. **The Focus return, manifest, diff, reconciler, digests and schemas.** Owned by h2a/Focus (FE-0/FE-1/FE-5). The DS consumes them by pinned reference only (§13.4) and defines no second shape.
2. **Full-document editing:** table-cell editing, diagram source or scene editing, code-block editing, heading editing, blockquote editing, link/image editing, and any Markdown construct outside the §6.1 P0 profile. Those blocks are preservation witnesses, not editing witnesses.
3. **List editing before the §6.4 three-condition gate.** Lists stay preserved and visibly non-editable until a compatible h2a evolution, a new pin recorded in both specifications, and the joint FE-1/FE-2 witnesses have all passed. A DS-only round-trip result never enables list editing.
4. **A formatting toolbar, slash menu, mention/autocomplete system, or any popover UI.** P0 input is keyboard + Markdown input rules (Q-RT-2).
5. **Collaborative or multi-writer editing:** CRDTs, presence, simultaneous cursors, a document server, and any `LiveDocumentStore` implementation.
6. **Persistence, autosave, transport and business logic in the component:** no localStorage draft, no `apiPut`, no store, no Track write, no inbox delivery. Draft recovery and export are host duties (h2a FE-4).
7. **React, Vue and Angular adapters claimed as delivered** before their §4.3 stage gates pass. Stage 1 is Svelte only and is announced as such.
8. **Retro-editing previously rendered HTML files** and any `renderHtml`+runtime host qualification (h2a V13): allowed by the Focus contract, not a DS gate here.
9. **Performance budgets.** Numeric keystroke/paint budgets are FE-8 phase-B outputs derived from measurement (`h2a-spec` D22). This specification supplies measurable invariants (§13.3) and no threshold numbers.
10. **The business substance of any dossier** and the qualification of the real reference case (h2a FE-9). DS fixtures are synthetic and labelled as such (§11.3).
11. **Publication mechanics beyond the DS guard:** npm availability of any h2a package, CDN distribution, and MCP `ui://` hosting of the editor are not asserted here.
12. **A second editor.** Neither a `focus-kit` fallback maintained past its replacement gate (§13.2) nor a per-framework re-implementation of the profile and editor conversion (§4.1 option 3) is covered or permitted under this specification.
13. **Agreement and supported export for draft paragraphs refused by the pinned contract.** Under `98060bd0a` the DS allows locally any gesture whose resulting draft paragraph the pinned `assertParagraphText` or range checks refuse (§5.10 general rule; examples include an empty `text/plain` paragraph and a paragraph with a leading or trailing newline such as `"A\n"`), but no FE-3 agreement and no supported export is covered or claimable for a draft containing such a paragraph: the host reports the export as unsupported (carrying `unsupported-paragraph-format` or `unsupported-range`) and preserves the draft. The same exclusion covers a `text/markdown` paragraph flagged by the §6.6 bridge test alone, reported under the distinct cause `bridge-non-representable` (§5.10 `"A  \nB"` witness). That coverage starts only under the §5.10 evolution-plus-new-pin condition with the named witnesses passing as agreement witnesses on the new pin (§11, §13.1, §16 U-RT-7).
