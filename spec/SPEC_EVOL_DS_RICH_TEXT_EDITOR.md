## 1. Goal, scope, non-goals

### 1.1 Goal

Deliver the reusable controlled Tiptap editor that lot FE-2 of the h2a specification requires, so that two Svelte consumers can mount the same editor surface:

1. h2a `focus-kit`, the offline portable dossier host (first witness, lot FE-3);
2. the sentropic app, which today carries the Tiptap precedent (lot FE-7).

The editor edits source text in place, preserves opaque paragraph identities through split, merge, undo and paste, emits no change for an unchanged field, respects IME composition, carries no built-in natural language, performs no network access, and embeds into h2a's offline single-file artefact with no CDN.

### 1.2 In scope (this specification)

Section map: §4 package placement; §5 component surface (making h2a specification §5.7 concrete as an API);
§6 content profile P0 (Markdown round-trip path and its qualification, preserved non-editable blocks, and the
list-item paragraph gate); §7 security and CSP; §8 offline packaging (what the DS ships, what the host bundles);
§9 dependencies and licensing; §10 provenance; §11 tests (the FE-2 RED list made concrete); §12 lots inside
the DS; §13 interfaces with h2a lots FE-3, FE-7, FE-8 and the D23 fallback; §14 open questions to the owner;
§15 NOT covered; §16 residual factual uncertainties. No Python is used anywhere in the lots this specification
defines (implementation, tests, jobs, one-off scripts): the DS stack is Node/TypeScript and native tooling
already present.

### 1.3 Out of scope

See §15 for the exhaustive NOT-covered list. In particular: the Focus return, manifest, diff and reconciler (h2a FE-0/FE-1/FE-5); any toolbar product decision beyond keyboard and Markdown input rules in P0; React/Vue/Angular adapters claimed as delivered before their stage gate (§4.3); table/diagram/code editing; collaborative editing.

**Decision (`ds-proposition`):** create `packages/rich-text` as `@sentropic/design-system-rich-text`, a framework-neutral package with exactly two entries. - **Entry `"."` — pure, no editor runtime.** `src/index.ts` (built to `dist/index.js`) exports only pure logic: the controlled-document model and gesture/readiness types (§5.1, §5.3, §5.5), the injected-message catalogue and `untranslated` marker helpers (§5.7), the P0 profile descriptors as data (profile identifier, extension package names in composition order, Markdown serialisation configuration; §6.1, §6.5), the identity attribute contract as data (`paragraphId` / `data-paragraph-id` / `data-preserved-block` names and the plugin descriptor; §5.2), the DS-token theme mapping (§5.8), document equality, the §5.6 external-update decision rules, and capture/readiness state (§5.6). Importing `"."` loads no `@tiptap/*`, no `prosemirror-*`, no Svelte/framework module and no DOM global; every module in its transitive import graph is relative or `node:`-free pure TypeScript. RED-P's core half (§11) asserts on this entry only.
- **Entry `"./editor"` — Tiptap-bound, the engine.** `src/editor.ts` (built to `dist/editor.js`, exported as `"./editor"`) is the only RT-0 entry that imports `@tiptap/core`, `@tiptap/pm`, the granular P0 extensions, `UndoRedo` and `@tiptap/markdown`. It exports the editor factory (`createRichTextEditor`): it builds the Tiptap editor from the P0 extensions, defines the `preservedBlock` node, installs the live paragraph-identity ProseMirror plugin, maps `RichTextDocument` to and from the ProseMirror document with the `paragraphId` attribute, and converts editable paragraph Markdown through `@tiptap/markdown`. Split, merge, undo/redo, paste parsing and Markdown conversion are ProseMirror/Tiptap behaviour reached through this entry, never re-implemented in the DS. The Svelte adapter (RT-1) imports this entry; no framework adapter imports the editor runtime through `"."`.
- Tiptap/ProseMirror are `peerDependencies` of the package (mirroring `packages/codemirror/package.json`: peer range on the major line, exact pins only in `devDependencies` for its own build/tests); `@tiptap/markdown` is a runtime dependency reachable only from `"./editor"` (§9.1). Peers are declared at package level because `package.json` has one peer set; the entry split is enforced by the import graph (RED-P), not by the peer declaration.
- The package ships `sideEffects: false`, `files: ["dist"]`, ESM + types for both entries, build `tsc -p tsconfig.json`, test `vitest run src` (the `packages/codemirror` script shape).
- The package is consumed by thin framework adapters that own only mounting, prop/event idioms and lifecycle, importing `"./editor"` for the runtime and `"."` for types and pure helpers.

Reasoning, against the three constraints in the commission:

1. **A plain Button/Card import never loads Tiptap (`h2a-spec` §5.7/FE-2: explicit subpath export).** The neutral package is a separate workspace, so no `components-*` barrel can pull it transitively unless an adapter does. A consumer importing `@sentropic/design-system-svelte` (Button, Card) resolves `"."` and never resolves the subpath module graph. This is witnessed by the packaging test of §11 (RED-P).
2. **DS framework parity rule.** The DS delivers components across Svelte/React/Vue/Angular and guards parity by measurement, not by type similarity (`spec/SPEC_EVOL_DS_JSON_RENDER_STANDARD.md` §5.1/AC-L1: parity recorded per component, never claimed from types alone; `docs/graph-dataviz-migration-plan.md` lot A4: adapters are declared equivalent only after a real vertical scenario). Parity is claimed per stage, never in advance (§4.3).
3. **Consumers that exist now.** Both current consumers are Svelte: h2a `focus-kit` (`packages/h2a/focus-kit/src/App.svelte` at `98060bd0a`, Svelte) and the sentropic app (`ui/src/lib/components/TipTap.svelte`, Svelte). ## 5. Component surface (RT-D2)

This section makes h2a specification §5.7 precise as an API. Names below are the DS API (`ds-proposition` concretisation); semantics tagged `h2a-spec` are binding from §5.7/D14.

### 5.1 Controlled document model (framework-neutral, in `packages/rich-text`)

The component is controlled: the host owns the value; the component never owns a durable copy.

```ts
// packages/rich-text/src/model.ts (RT-0, [N])
export type RichTextFormat = "focus.markdown.p0@1" | "text/plain";

export interface RichTextBlock {
  /** Opaque per-block identity, host-supplied. See §5.2. */
  paragraphId: string;
  kind: "paragraph" | "preserved";
  /** Editable paragraph text (Markdown inline source for
      `focus.markdown.p0@1`, literal text for `text/plain`).
      Present iff kind === "paragraph". */
  text?: string;
  /** Verbatim source slice of a preserved block. Present iff
      kind === "preserved". Never edited, never reserialised. */
  raw?: string;
  /** Preserved block kind as segmented host-side (e.g. "heading",
      "list", "table", "codeBlock", "diagram"). Display only. */
  preservedKind?: string;
}

export interface RichTextDocument {
  format: RichTextFormat;
  blocks: readonly RichTextBlock[];
}
```

- The wire shape between DS and host is `RichTextDocument`, not Tiptap JSON and not ProseMirror positions (`h2a-spec` §5.7: ProseMirror positions and Tiptap JSON never leak into the wire contract). The `"./editor"` entry converts `RichTextDocument` ↔ ProseMirror document internally (§4.2); the `"."` entry carries the model only and converts nothing.
- **No separator storage (blocking).** `RichTextDocument` stores no separator: no blank-line count, no line-ending form (LF vs CRLF vs CR), no trailing whitespace and no final-newline flag exists in the model, and none may be added as a hidden field, an extra block or a paragraph-text suffix. A paragraph `text` is the bare block slice the Focus codec produces (`packages/focus/src/editing/codec.ts` at `98060bd0a`: top-level block slices with gaps excluded, `assertParagraphText` refusing any paragraph text that does not segment back to exactly itself), so a `text` carrying a trailing line break would be refused host-side on every paragraph. Separators are structural gaps owned host-side (§6.5, §13.1); §11 RED 2 and §6.5 define the DS-level identity rule that follows from this.
- For `text/plain` fields the document holds exactly the plain-field segmentation the host adapter derived from the Focus manifest (one block per plain paragraph; an emptied plain field is one block with `text: ""`, §2.2 M6). The component does not re-segment plain text.
- For `focus.markdown.p0@1` the host adapter derives blocks from the Focus source codec segmentation (editable paragraphs vs opaque slices, §2.2 M5/M6); the DS ships no source segmentation (§6.5). Preserved slices travel as `raw` and return byte-identical at block level (§6.5).

### 5.2 Opaque per-block identity attribute

- **Name.** The identity is the ProseMirror node attribute `paragraphId` on `paragraph` and `preservedBlock` nodes, rendered to the DOM as `data-paragraph-id` (and `data-preserved-block` on preserved blocks). It is a single opaque string, unique within the document, allocated by the host. The component treats it as opaque: it never parses, derives, sorts by or displays it as content.
- **Supply.** The host adapter supplies identities through the initial `RichTextDocument` (one `paragraphId` per block). New identities created inside the editor (split tail, pasted blocks, inserted paragraphs) are allocated through the injected allocator (§5.5, `allocateId`); the component has no identity policy of its own. If the host supplies no allocator, the `"./editor"` factory default is `crypto.randomUUID()` — acceptable only for non-Focus hosts, because Focus allocation policy (deterministic seeding, retired-ID non-reuse) belongs to the producer/host (`h2a-spec` D13, merged `anchors.ts`), never to the component.
- **Carriage (D14, `h2a-spec`).**
  - *Split (Enter):* the leading paragraph keeps the original `paragraphId`; every following paragraph receives a fresh allocated identity.
  - *Merge (Backspace at paragraph start / Delete at end):* the leading paragraph's identity survives; consumed identities are retired inside the editor session and are never reallocated by the component.
  - *Undo/redo:* undo of a removal restores the same logical paragraph's identity (the identity is part of the ProseMirror node, so history restores it by construction; the RED list asserts it, §11 RED 3).
  - *Internal copy/paste:* pasted copies receive fresh allocated identities; a paste never duplicates a live identity inside the document.
  - *External paste:* pasted markup never supplies a trusted identity. The paste pipeline strips any `data-paragraph-id` (and any `paragraphId` attribute) from incoming content before it enters the document, then allocates fresh identities (§7). This rule has no exception, including paste of content copied from the same editor in another window.
- **Non-identity.** Display order, array index, DOM path, translated label, content hash and character offset are never used as identity anywhere in the component (`h2a-spec` D13). Selection and caret are ProseMirror positions internally and are never emitted as identity.

### 5.3 Document and gesture information out — no diff in the DS

```ts
// packages/rich-text/src/model.ts (RT-0, [N])
export type RichTextGestureKind =
  | "type"
  | "split"
  | "merge"
  | "paste"
  | "delete"
  | "undo"
  | "redo"
  | "composition-commit";

/** Gesture provenance. Exactly what the host adapter needs to follow
    block identities across the gesture; no text diff is carried. */
export interface RichTextGesture {
  /** Opaque identifier of this completed gesture, allocated by the component. */
  gestureId: string;
  kind: RichTextGestureKind;
  /** Ordered `paragraphId` values of the blocks the gesture touched,
      in resulting document order. */
  affectedParagraphIds: readonly string[];
  /** Present iff kind === "split": the block that was split and the fresh
      identities allocated for the tail blocks, in document order. */
  split?: {
    sourceParagraphId: string;
    newParagraphIds: readonly string[];
  };
  /** Present iff kind === "merge": the surviving identity and the identities
      consumed by the merge, which the component never reallocates. */
  merge?: {
    survivingParagraphId: string;
    retiredParagraphIds: readonly string[];
  };
  /** Present iff kind === "paste": the freshly allocated identities of the
      inserted blocks and whether the paste entered from inside this editor
      session or from outside it. */
  paste?: {
    insertedParagraphIds: readonly string[];
    origin: "internal" | "external";
  };
}

export interface RichTextChangeEvent {
  /** The complete new controlled value. The only content the component emits. */
  document: RichTextDocument;
  /** Provenance of the single completed gesture that produced `document`. */
  gesture: RichTextGesture;
}
```

- **No-diff rule (blocking).** The component emits the complete document and the gesture information above, and nothing else about what changed. It MUST NOT compute, store, emit or compare a per-paragraph `before`/`after` pair, a `RichTextChange`/`RichTextTransaction` shape, anchors derived from a diff, or a delta against any baseline, and it MUST NOT retain the last host-supplied or host-acknowledged value as a diff baseline. Removing every DS-side `before`/`after` computation from the surface is normative: no type in `packages/rich-text` carries `before`, `after`, `beforeAnchors` or `anchors`, and no callback translates directly to a Focus `ParagraphChange`. The shapes `RichTextAnchors`, `RichTextChange` and `RichTextTransaction` do not exist.
- **What the adapter needs, named precisely.** The host adapter needs exactly three things, all present above and nothing more: (1) block identities — the ordered `paragraphId` values and texts in `document.blocks`; (2) split/merge/paste gesture provenance — `RichTextGesture.split` / `.merge` / `.paste` together with `affectedParagraphIds`, so the adapter can follow a split tail, a merge survivor and fresh paste identities without guessing from text; (3) composition state — the neutral readiness signal of §5.6, so the adapter never captures mid-composition. No position, offset or text comparison crosses the DS boundary.
- **Host-side diff (the only diff).** The host adapter maps `document.blocks` to Focus `ParagraphValue[]` through the manifest identities it owns, and computes the per-paragraph diff with `@sentropic/focus/editing` (`diffParagraphs` in merged `packages/focus/src/editing/diff.ts`), against the retained Focus baseline (`ParagraphValue[]` derived from the manifest it holds). The adapter MUST NOT translate a DS gesture into `ParagraphChange` records by hand and MUST NOT implement a second diff algorithm; `gesture` is provenance for logging and caret handling only.
- **Baseline advancement (blocking).** A freeze or an export never advances the baseline. At the pin (`98060bd0a`), `freezeReturn` (`packages/focus/src/editing/contract.ts`) preserves the supplied `document` and `manifest` unchanged: it validates any `previous` return against that same manifest and base, filters empty transactions, chains `supersededReturnIds`, and returns the `previous` clone unchanged when answers, notes, transactions, production and scope are identical; it recomputes no manifest and moves no base. `carryManifest` (`packages/focus/src/editing/anchors.ts`) accompanies a producer revision: it takes a new authoritative `DecisionDossierDocument`, the previous manifest and an explicit paragraph correspondence, and seals a new manifest whose `baseHash` is `baseDigest(newDocument)` with `manifestId` preserved and retired identities accumulated; it is not an export step. The baseline therefore advances only when a new authoritative version, once acknowledged by the host, is carried through `carryManifest` (or seeded once for a first version); neither `freezeReturn`, nor an export, nor a component echo, nor a local edit advances it. Worked consequence: starting from retained baseline text `A`, typing to `B` and then undoing to `A` emits two events (documents `B`, then `A`) whose host-side diffs against the retained baseline `A` are `A → B` and then the empty cumulative diff; no `B → A` change is ever produced, because no DS-side `B`-relative delta exists. Advancing the baseline to `B` after exporting `A → B` would make the next undo produce a `B → A` change instead of the empty cumulative result and is therefore prohibited. Mandatory witness (host adapter in h2a lot FE-3, plus the FE-3 host-side freeze check of §13.1): (1) baseline `A` retained, draft at `A`; (2) type to `B`, host echoes `B` back as the controlled `value` (echo recorded as acknowledgement, §5.6 rule 1, baseline unchanged); (3) freeze export `R1` via `freezeReturn` with the `A → B` cumulative transaction — assert `R1.source.baseHash` and `R1.manifest.manifestBaseHash` equal the baseline `A` hashes; (4) undo to `A`; (5) freeze export `R2` — assert `R2.editReturn.transactions` is `[]` (empty cumulative diff against the still-retained baseline `A`), `R2.source.baseHash` and `R2.manifest.manifestBaseHash` are identical to `R1`'s, `R2.editReturn.supersedesReturnId` equals `R1.returnId`, and `R2.editReturn.supersededReturnIds` is `[R1.returnId]`. Any advance of the retained baseline at step (2), (3) or (4) fails this witness.
- **Emission granularity.** One user-perceived gesture (a run of typing coalesced by the editor, a split, a merge, a paste, a committed IME composition) emits exactly one `RichTextChangeEvent` carrying the complete resulting document. No event is emitted for opening, focusing, rendering, locale/theme change, or leaving an unchanged editor (`h2a-spec` D12, FE-2 RED 2): unchanged means the resulting `RichTextDocument` equals the current controlled value under the document equality of §5.6 (all significant fields: `format`, ordered `paragraphId`, `kind`, `text`, `raw`, `preservedKind`), checked by value equality on the document, never by a diff. No event is emitted mid-IME-composition (§5.6). An undo that restores the prior document emits an event with that document; whether it nets to zero is decided host-side by the Focus diff, never by the component.

### 5.4 `editable` / `disabled` / read-only states

Framework adapters expose the same three-state semantics in their framework idiom; the Svelte adapter (RT-1) exposes:

| Prop | Default | Meaning |
| --- | --- | --- |
| `editable` | `true` | The field may be edited when `true`. `false` is the read-only state: text stays selectable and copyable, the caret may be placed, no mutation is possible. |
| `disabled` | `false` | The form-disabled state: not focusable, `aria-disabled`, no selection interaction. `disabled: true` wins over `editable`. |

- Effective editing is `editable && !disabled`. Both props take effect immediately on the live editor (`editor.setEditable(...)`), without remounting.
- In a non-editable state, typing, paste, drop, cut and every mutation shortcut are inert: no document mutation, no `onChange`, no save-like callback (`h2a-spec` §5.7; viewer/locked rule §2.3). This includes the viewer case: a host rendering for a viewer passes `editable={false}` (or `disabled`) and the RED list asserts the lock through paste and keyboard paths, not only typing (FE-2 RED 1).
- State changes never emit a change event and never alter the document.

- `value` is controlled. The component keeps an internal editor document initialised from `value` and emits `onChange`; it does not mutate the prop.
- `onExternalConflict` is the surfacing channel of §5.6. `onUnsupportedPaste` reports a paste that the profile refused (§7) so the host can show its own notice through injected messages; the component shows no built-in notice text. The event is defined in the `"."` entry as `RichTextUnsupportedPasteEvent { rejectedKinds: readonly string[]; clipboardFormats: readonly ("text/html" | "text/plain")[] }`, where `rejectedKinds` lists the non-paragraph block kinds the paste would have created (for example `"table"`, `"codeBlock"`, `"heading"`, `"list"`, `"blockquote"`, `"image"`, `"horizontalRule"`, `"rawHtml"`) in clipboard order, deduplicated; it carries no pasted text, no HTML and no Focus type.
- `onReadinessChange` is the neutral composition/readiness signal. It is the only way the host learns that a capture must wait; re-reading the last `onChange` during composition is never sufficient, because that document predates the visible composed text. The imperative handle (`captureDocument`/`readiness`, exposed by the framework adapter in its idiom — a component reference in Svelte) is the deferred-capture surface of §5.6.
- No prop carries a Focus type, a Track type, a URL, a transport, a store or a business callback. There is no `onSave`, no autosave, no debounce-to-network semantics in the component; a host may debounce its own reaction to `onChange` (the sentropic debounce capital stays host-side, §10).

### 5.6 External controlled updates during typing; IME composition

**External updates (`h2a-spec` §5.7) — composition and local divergence take precedence over focus state (blocking).** The decision half of this rule is pure and lives in the `"."` entry (`packages/rich-text/src/document.ts`, §12): document equality and a decision function that, given the displayed document, the last acknowledged document, the incoming document and the composing flag, returns exactly one of echo / defer / conflict / apply, with no Tiptap, ProseMirror or DOM reference. The `"./editor"` factory and the framework adapters apply the returned decision to the live ProseMirror instance (suppress replacement, defer, emit `onExternalConflict`, or replace content with selection re-anchoring); they do not restate the rule order. When the `value` prop changes after mount, the component evaluates the following rules in this exact order; focus state never appears as a condition. Two internal values are distinguished throughout: the *displayed document* (the ProseMirror document currently shown) and the *last acknowledged document* (the last host-supplied `value` recorded under rule 1 or rule 4, initialised to the mount `value`). Document equality, used by every rule below and by the unchanged check of §5.3, is value equality over all significant fields and never a diff: two `RichTextDocument` values are equal iff `format` is strictly equal, the `blocks` arrays have the same length in the same order, and for each index the blocks have strictly equal `paragraphId`, strictly equal `kind`, strictly equal `text` (absent equals absent; present values compared by string equality), strictly equal `raw` (same absent/present rule), and strictly equal `preservedKind` (same absent/present rule). A difference in `format` alone, in `kind` alone, or in the `raw` of a preserved block alone is therefore a real difference, never an echo.

1. *Echo — suppression of replacement, recording of acknowledgement.* If the incoming document equals the displayed document under the equality above, the component performs two distinct effects and no third: (a) *replacement is suppressed* — the editor content is not replaced, the ProseMirror instance is not recreated, and focus, caret, selection and scroll are not reset (this is the `lastValue` guard capital of §2.3, checked by the value equality above, never by a diff); and (b) *acknowledgement is recorded* — the last acknowledged document is set to the incoming document (a value copy). Recording the acknowledgement does not advance the Focus baseline (§5.3 baseline rule); it only moves the component-internal reference that rule 3 compares against, so that edits the host has echoed back are no longer treated as locally divergent. An incoming document that differs from the displayed document in any significant field — including a change confined to the `raw` of one preserved block — is not an echo and falls through to rules 2–4.
2. *Composition.* Else if a composition is in progress (`readiness().composing === true`), the update is deferred: it is neither applied nor treated as a conflict yet. It is re-evaluated once, immediately after the composition commit and its single `onChange`, under rules 1, 3 and 4, using the equality and acknowledged reference defined above. No overwrite and no conflict signal occur mid-composition.
3. *Local divergence.* Else if the displayed document differs from the last acknowledged document under the equality above — that is, the user holds local, unacknowledged edits, regardless of whether the editor is focused, blurred, or has lost focus since typing — the incoming value **never overwrites** local work. The component keeps the local document and caret untouched and emits exactly one `onExternalConflict` carrying the incoming document and the local document. Blur never cleans local work: typing, then blurring, then receiving an external update before acknowledgement leaves the local text intact and signals one conflict (§11 RED 4). The host decides (keep local, accept external by remounting with a new key, or reconcile); the component applies no silent winner. A parent clearing the value to empty is an external update under the same rule — the sentropic precedent's focused-clear exception is not carried over, because §5.7 requires surfacing, never overwriting; hosts that need a forced reset remount explicitly.
4. *No conflict.* Else (no composition, no local divergence: the displayed document equals the last acknowledged document) the update is applied automatically, whatever the focus state: content is replaced, the selection is restored when the saved ProseMirror positions remain valid in the new document, otherwise clamped to the nearest valid position (the selection-preservation capital of §2.3, generalised from offsets to block identities: selection is re-anchored by `paragraphId` plus intra-paragraph offset where the block survives), and the last acknowledged document is then set to the incoming document. A rule-4 update that changes only the `raw` (and, where present, the `preservedKind`) of one preserved block, with every paragraph text unchanged, is applied by this rule exactly like any other no-conflict update: the preserved block renders the new `raw`, no conflict is emitted, and no paragraph is recreated.

Only a rule-4 update is automatic. Every other case either defers, records an echo acknowledgement without replacing content, or surfaces a conflict; no path silently overwrites dirty local work, and the former "clean **or not focused**" condition does not exist. Mandatory echo witness (named in §11 RED 4): mount at `A` (acknowledged `A`), type to `B` (displayed `B`, acknowledged still `A`), host echoes `B` as the new `value` (rule 1: no replacement, no remount, acknowledgement becomes `B`), then host supplies external update `C` with no intervening local edit (rule 4: `C` is applied with zero `onExternalConflict`); separately, from an acknowledged document containing a preserved block, host supplies an update identical except for that block's `raw` (not an echo under the equality above; rule 4 applies it with zero conflict and the new `raw` rendered). Treating the echo as a pure no-op without recording the acknowledgement fails the `C` step by construction, because `B` would still count as divergent when `C` arrives.

**IME composition and deferred capture (`h2a-spec` §5.7) — neutral signal, no stale snapshot (blocking).** The editor respects ProseMirror composition state and exposes it through the neutral signal of §5.5:

- `onReadinessChange` fires with `{ composing: true, ready: false }` at `compositionstart` and with `{ composing: false, ready: true }` after `compositionend` and the resulting single `onChange`, in that order. `readiness()` returns the same current value synchronously. The signal carries no text, no language and no Focus type.
- During `compositionstart`–`compositionend`, no `onChange` is emitted and no external update is applied (rule 2 above). Accents, composed characters and emoji are ordinary text once committed; the committed composition emits exactly one `onChange` whose `gesture.kind` is `"composition-commit"`.
- **Deferred capture.** `captureDocument()` is the only export-relevant read. Called while `ready` is true, it resolves immediately with the currently displayed document. Called during composition, it MUST NOT resolve with the pre-composition document and MUST NOT resolve mid-composition: it waits until `compositionend`, the single commit `onChange` has been emitted, and readiness is true again, then resolves exactly once with the committed document, which contains the composed text exactly once. The host freeze (§13.1) therefore always awaits `captureDocument()` (or waits for `ready`) and never snapshots the last `onChange` on its own. This satisfies the h2a §5.7 rule that no capture occurs during composition, without substituting a stale revision for the export.
- **Capture termination at unmount (blocking).** A `captureDocument()` promise still pending when the component unmounts (or the editor is otherwise destroyed, §5.9) does not stay pending, does not resolve with any document, and does not fire a late callback: it rejects exactly once during unmount teardown with the neutral capture error, an `Error` whose `name` is `"RichTextCaptureUnavailable"` and whose `message` is exactly `"rich-text.capture-unavailable"` (a neutral key, not a sentence in any language; it carries no document text and no Focus type). After that rejection the component emits no further `onChange`, no further `onReadinessChange`, and no deferred task callback for the destroyed editor. A `captureDocument()` call made after destruction, through a stale handle, returns an already-rejected promise with that same error: it does not throw synchronously, does not recreate the editor, does not resolve and does not hang; `readiness()` called after destruction returns `{ composing: false, ready: false }` and does not throw. Mandatory witness (named in §11 RED 5): start a real composition, call `captureDocument()` so a capture is pending, unmount before any commit, and observe the rejection with that exact `name`/`message`, exactly one settlement, and zero post-unmount callbacks.
- This behaviour requires a real browser for its witness (§11 RED 5); jsdom does not implement composition, and synthetic `CompositionEvent` dispatch alone does not establish a real composition (§11).

### 5.8 Theming through DS tokens

- All visual styling reads DS tokens: component anatomy variables `--st-component-richTextEditor-*` with semantic fallbacks, following `CodeSnippet.svelte`/`Button.svelte` (§2.1). No colour, spacing, radius, font or motion value is hard-coded where a `--st-*` token exists.

### 5.9 Mount on demand, unmount, no network

- The editor is created on mount (`onMount`) and only then: hosts mount it on demand for the active field/block (`h2a-spec` D6/C13). The subpath export is dynamically importable so a host can `await import("@sentropic/design-system-svelte/rich-text-editor")` at first edit activation; the DS does not require eager loading.
- Unmount destroys the Tiptap editor (`editor.destroy()`), removes every listener the component registered on any target (editor root, `document`, `window`), disconnects every `MutationObserver`/`ResizeObserver`/`IntersectionObserver` it created, and cancels every pending animation frame, timer and deferred task it scheduled. No listener, observer or task survives unmount on any target (FE-2 RED 8 asserts this by instrumenting registrations per target/listener/capture triple, observers and scheduled tasks created during the mount, §11). Every `captureDocument()` promise still pending at unmount is settled by the neutral rejection of §5.6 during the same teardown, before teardown completes; no pending capture is left unsettled and none resolves after unmount.
- The component performs no network access of any kind: no `fetch`, no `XMLHttpRequest`, no remote image, font or stylesheet, no beacon. This is observed at runtime for the whole scenario (browser request interception plus a `fetch`/`XMLHttpRequest` sentinel, §11 RED 8), not inferred from an import scan alone: a global `fetch` call needs no import for the scan to miss, so the scan is necessary but never sufficient.

## 6. Content profile P0 (RT-D3)

### 6.1 Enabled nodes and marks

Profile identifier: `focus.markdown.p0@1` (merged contract, §2.2 M3). The `"."` entry describes this profile as data (`profile.ts`); the `"./editor"` entry enables exactly:

| Kind | Tiptap/ProseMirror element | Editable | Notes |
| --- | --- | --- | --- |
| Node | `doc` | — | Root. |
| Node | `paragraph` (attr `paragraphId`) | Yes | The only editable block in P0. |
| Node | `text` | Yes | Inline text. |
| Node | `hardBreak` | Yes | Inside a paragraph. |
| Mark | `bold` (strong) | Yes | Keyboard + Markdown input. |
| Mark | `italic` (emphasis) | Yes | Keyboard + Markdown input. |
| Mark | `code` (inline code) | Yes | No code block follows from this mark. |
| Node | `preservedBlock` (attrs `paragraphId`, `raw`, `preservedKind`; `contenteditable=false`, atom) | No | Carries every unsupported block verbatim (§6.3). DS-internal node; never a Focus type. |

Everything else is absent from the schema. In particular there is no `heading`, `bulletList`, `orderedList`, `listItem`, `blockquote`, `codeBlock`, `table`, `image`, `link` mark or `horizontalRule` in the P0 schema. `StarterKit` is not enabled wholesale: `"./editor"` composes the granular extensions (`@tiptap/extension-document`, `-paragraph`, `-text`, `-bold`, `-italic`, `-code`, `-hard-break`, `-placeholder`, plus `UndoRedo` from `@tiptap/extensions`, as resolved at lot start) so that an upstream default can never silently widen the profile (`h2a-spec` §5.3: activating StarterKit defaults is not a fidelity policy). Undo/redo history is enabled; placeholder display is enabled and reads `messages.placeholder`.

`text/plain` fields use the same document model with marks disabled by the adapter (a plain paragraph's text is literal; Markdown input rules do not fire).

### 6.2 What a paragraph may contain

An editable paragraph is a top-level paragraph whose inline content uses only text, `bold`, `italic`, `code` and `hardBreak` — the same editable set the merged Focus source codec accepts (§2.2 M6). A source paragraph containing a link, an image or raw HTML is not an editable paragraph: the host adapter segments it as a preserved block (§6.3), and the component renders it non-editable. The component never strips a link to make a paragraph editable.

### 6.3 Unsupported blocks: preserved and non-editable, never destroyed

- Tables, code blocks/fences, diagrams (including Mermaid sources), headings, lists (preserved until the §6.4 three-condition gate passes), blockquotes, images, raw HTML blocks and any other construct outside §6.1 are `preservedBlock` nodes when, and only when, they already exist in the source document the host segmented. They render as visibly non-editable regions (`data-preserved-block`, `contenteditable=false`, accessible name from `messages.preservedBlockLabel`) and no editor gesture can place the caret inside them or transform them.
- A preserved block's `raw` is carried byte-identical through mount, editing elsewhere, and unmount, and is emitted unchanged in every `RichTextDocument`. Serialisation never regenerates a preserved block from an AST. This carries h2a capital C11/K11-adjacent preservation: a global Markdown → Tiptap → Markdown round trip must never silently normalise unsupported content away. Preservation applies only to blocks that already exist in the source; it is not a paste-creation path (see the paste rule below and §7).
- **Paste never creates a preserved block (blocking, pinned contract).** Under the pin at `98060bd0a`, the Focus return transports only `ParagraphValue[]` with `blockKind: 'paragraph'` (merged `contract.ts`) through `diffParagraphs` (`diff.ts`), and `assertParagraphText` (`codec.ts`) refuses any text that segments to a non-paragraph or multi-block result (`unsupported-paragraph-format`). A paste that would create a table, a code fence/block, or any other non-paragraph block therefore cannot be carried by the return: creating a new `preservedBlock` would make visible content disappear from the return, and flattening it into paragraphs would be refused by `assertParagraphText`. The component refuses such a paste as a whole, reports it exactly once through `onUnsupportedPaste` (§5.5), and leaves the document, the selection and the host-side return unchanged: no `onChange` is emitted, no block is inserted, no existing block is altered. Creating preserved blocks from paste requires an explicit h2a evolution (a return that can transport non-paragraph blocks), a new pin recorded in Appendix B and in `spec/SPEC_EVOL_DS_JSON_RENDER_STANDARD.md` §11.2.1, and a joint witness; it is not available under the current pin.
- If a user gesture would span an existing preserved block (select-all delete, paste replacing a selection covering one), the component refuses the destructive span and reports it through `onUnsupportedPaste`/a no-op with the preserved blocks intact; it never deletes a preserved block as a side effect of a text gesture. Explicit host-driven removal (the host supplies a new `value` without the block) is the only removal path.

### 6.4 List-item paragraph question (h2a V7): preserved until the contract evolves (blocking)

- **Rule.** Lists stay preserved and non-editable under §6.3. At the pinned contract (`98060bd0a`), `packages/focus/src/editing/codec.ts` segments only top-level `Paragraph` nodes as editable and `packages/focus/src/editing/anchors.ts` creates paragraph units only from editable segments, so no list item is an ordinary editable paragraph unit, and §6.1 contains no `bulletList`, `orderedList` or `listItem` node. The DS alone never widens P0.
- **Three-condition gate.** List items join the editable profile only when all three conditions have passed, in this order, and the widening is then made by amending §6.1 in a follow-up delivery: (1) a compatible h2a evolution — the Focus codec and anchors are extended so list-item paragraphs are accepted as editable units with stable identities, published as a new `@sentropic/focus` contract; (2) a new pin — that contract is pinned by exact version in Appendix B and in `spec/SPEC_EVOL_DS_JSON_RENDER_STANDARD.md` §11.2.1 in the same delivery; (3) the joint FE-1/FE-2 witnesses — the h2a FE-1 source-codec witness and the DS FE-2 round-trip witness pass on the same list corpus, proving on the final bundled codec that bullet and ordered list items keep a stable `paragraphId` on the list item's paragraph through open/edit/close, split, merge and Markdown serialisation, with block identity at DS level and full-source byte-identical output for unchanged lists at the host splice (§6.5, §13.1).
- **DS-only evidence.** The RT-2 list round-trip run (§11, §12) is recorded as DS block-level evidence only (lists mount as preserved blocks, block-level identity per §6.5; full-source output identity for unchanged lists is witnessed host-side, §13.1). A passing DS-only result changes nothing: lists remain preserved, the delivery is announced exactly as "P0 fields editable, lists preserved" (`h2a-spec` D20), and no adapter enables a list extension. A failing or unrun list test likewise keeps lists preserved; it never blocks the P0 delivery and never gets announced as list editing.

### 6.5 Markdown round-trip path and its qualification

- Path: source Markdown field → host segmentation (merged Focus codec, `segmentMarkdown`/`segmentText` at `98060bd0a`; the DS ships no source segmentation) → `RichTextDocument` → ProseMirror document (the `"./editor"` entry, §4.2) → editing (ProseMirror transactions and history) → `RichTextDocument` → per-paragraph Markdown via `@tiptap/markdown` in `"./editor"` for editable paragraphs only, with preserved `raw` slices spliced back at their block positions by the host adapter into the retained source (§13.1). Plain fields bypass Markdown entirely. The DS never assembles a full source string: it has no separator to write (§5.1), so any DS-side full-source serialiser would have to invent separators the model does not carry.
- The Markdown bridge is `@tiptap/markdown ^3.32.0` over the §6.1 extension set, reached only from `"./editor"`, configured with the profile's serialisation options whose data form is fixed in `packages/rich-text/src/profile.ts` (RT-0, `"."` entry) and whose live wiring lives in `"./editor"` (§12). Reason for the change from the observed sentropic `tiptap-markdown ^0.9.0` (§2.3): `@tiptap/markdown` is the official bridge from the Tiptap monorepo on the same v3 major as the core (`@tiptap/core 3.32.0`), with a v3-native storage API, where the community `tiptap-markdown` line targets the v2 API surface. Transitive dependency `marked` (MIT, see §9.2). The exact `@tiptap/markdown` and `@tiptap/*` versions are pinned in the DS lockfile at lot start (`@tiptap/markdown 3.32.0`, `marked 17.0.6`) and recorded in the lot report.
- **Two identity levels (blocking; RT-0 resolution of RED 2 against §5.1).** The merged specification previously required the DS core to reproduce the whole source byte-identically (former §11 RED 2) while §5.1 stores no separators and the Focus codec refuses paragraph texts carrying separators (see §5.1). No `RichTextDocument` value can satisfy both, as the RT-0 run measured (a 6-byte residue: two CRLF separators and trailing blank content, with every block value already identical). The rule is now split by ownership, with no DS-side splice helper (justification at the end of this section):
  - **DS level — block identity.** At the DS boundary the round-trip assertion is block-level: for an unedited cycle, mount → focus → blur → unmount emits zero `onChange` (§5.3), block order and every `paragraphId` are unchanged, every unchanged paragraph `text` is byte-identical to the host-segmented slice that entered, and every preserved `raw` is byte-identical. For a single-paragraph edit, the edited paragraph carries exactly the new text and every other block (neighbouring paragraph texts, preserved `raw` values, order, identities) is unchanged. No DS test compares a reconstructed full source string, and no DS code joins blocks with an invented separator.
  - **Host level — full-source identity.** Reproducing the whole source byte-identically, separators included (blank lines, CRLF/CR forms, trailing whitespace, final newline), is the host splice: FE-3 reuses the pinned `applyParagraphChanges` (`packages/focus/src/editing/diff.ts:40–83` at `98060bd0a`) as that splice — it preserves every gap byte (preserved `raw` slices included, which never leave the gaps) and joins genuinely inserted paragraphs with `"\n\n"` — with the retained baseline kept separately as the `freezeReturn` input. It is witnessed in h2a lot FE-3 (§13.1, including agreement after split, merge, paste and undo) and recorded as an interface requirement there. A DS green never substitutes for that witness.
- **Qualification, not declaration (`h2a-spec` §5.3/U1).** A declared `@tiptap/markdown` version is not a round-trip proof. The profile is qualified only when the §11 round-trip witnesses pass on the final bundle: at DS level, open/edit-nothing/close over every P0 construct and every preserved construct of the corpus yields block identity (paragraph above) and the host-side Focus diff of the unedited document against its baseline is empty; at host level, the FE-3 splice witness (§13.1) yields the byte-identical full source. Any marker, spacing or line-break normalisation of unchanged *block content* at DS level is a failure, because it would manufacture false amendments; separator bytes are not the DS's to normalise or to preserve. The component itself computes no delta for this check (§5.3); emptiness is established host-side with `diffParagraphs`.
- **Segmentation stays host-side; DS equivalence is conversion equivalence.** The Focus codec (`@lezer/markdown` slices, §2.2 M5) remains the only segmentation authority: the same source produces the editable/preserved block boundaries and paragraph texts host-side, and the DS neither mirrors nor substitutes that segmentation in production code. What the DS qualifies instead is that its `"./editor"` conversion preserves exactly the host-segmented blocks it is given: `RichTextDocument` (built host-side from a vector's segments) → ProseMirror document → `RichTextDocument` returns the same ordered blocks, the same identities, the same paragraph texts and the same preserved `raw` values, and each editable paragraph's Markdown through `@tiptap/markdown` re-segments host-side to exactly that paragraph (the `assertParagraphText` shape). The qualification oracle stays the DS-side vector set of §11.3/RT-2 (`packages/rich-text/tests/fixtures/focus-segmentation-vectors.json` [N], exercised by `packages/rich-text/src/segmentation-equivalence.test.ts` [N] against `"./editor"`): at the pin `98060bd0a` no h2a-published data artefact delivers the Focus codec's expected boundaries — the fixtures under `packages/focus/tests/` (including `packages/focus/tests/fixtures/editing-vectors.json`) sit outside the `files` field of `packages/focus/package.json` (`["dist", "registry/entries.v1.json", "schemas/", "skills/", "README.md", "LICENSE"]`) and no `exports` entry names them, so they are not importable by pinned package version and this specification invents no such artefact. The DS vectors carry verifiable provenance (§11.3) and are the mandatory RT-2 gate today; a future h2a-published oracle (a dedicated exported fixture artefact at a new pin) is a `source-gap` dependency, recorded as such in §16, and replaces the DS vectors only through a pin bump recorded in Appendix B and in `spec/SPEC_EVOL_DS_JSON_RENDER_STANDARD.md` §11.2.1. The absence of that published oracle never suspends, skips or weakens the RT-2 gate.
- **Why no DS-side splice helper.** A DS helper that rejoined blocks into a full source would need the original separator bytes and block ranges, which are Focus manifest data (D9 ownership, §0.2): the DS would have to receive, store and interpret host segmentation output beyond the `RichTextDocument` wire shape, duplicating the host adapter's splice and creating a second place where separator handling could drift from the Focus codec ranges. The splice therefore stays in the single owner that already retains the source and the ranges — the host adapter — and the DS exposes no `sourceFromDocument`-style full-source serialiser (the RT-0 hand-written codec is disposed of in §12).

## 7. Security (RT-D4)

- **Parsing boundary.** Mounted content and pasted content enter only through the P0 ProseMirror schema (§6.1). Raw HTML is never assigned to the DOM as markup by the component; there is no `innerHTML` content path. Content already present in the mounted source that the schema cannot represent is a preserved block (§6.3); pasted content that the schema cannot represent as paragraphs is refused, per the paste rules below. The component never reconstructs Markdown source from rendered HTML.
- **Paste.** On paste, the component parses the clipboard payload (`text/html` when present, else `text/plain`) through the schema with these rules, in order:
  1. Strip every `data-paragraph-id`/`paragraphId` and allocate fresh identities (§5.2).
  2. Drop `script`, `iframe`, `object`, `embed`, `form`, event-handler attributes (`on*`), and `style` attributes wholesale; a pasted `</script>` sequence is text or dropped, never an element.
  3. Links: the `link` mark is not in the schema, so pasted links degrade to their text content; `javascript:`, `data:text/html` and other scriptable protocols never survive as attributes because no link node exists to carry them.
  4. Images: the `image` node is not in the schema. Remote images (`http:`, `https:`, protocol-relative) and local/data images alike produce no `<img>`, no request and no placeholder fetch; the alt text, when present, is inserted as plain text and the rejection is reported via `onUnsupportedPaste`.
  5. Non-paragraph blocks (refusal, pinned contract): if the payload, after rules 1–4, would create any block that is not a `paragraph` — a table, a code fence or code block, a heading, a list, a blockquote, an image block, a horizontal rule, a raw HTML block, a diagram source, or any other construct outside §6.1 — the whole paste is refused. The component emits exactly one `onUnsupportedPaste` carrying the `rejectedKinds` that would have been created (§5.5), emits no `onChange`, inserts no block, and leaves the document, the selection and the host-side return byte-identical to their pre-paste state. This rule applies whether the payload carries Markdown source text (`text/plain` with a fence or table syntax) or only rendered HTML (for example a `<table>` element): the component does not turn either form into a preserved block and does not flatten either form into paragraphs. Paragraph-only paste (plain paragraphs with `bold`/`italic`/`code`/`hardBreak`) is the only paste that inserts content, with fresh identities under rule 1. Their insertion as preserved blocks would require the h2a evolution, new pin and joint witness named in §6.3 and is refused until then.
- **No remote fetch.** The component loads no remote image, font, stylesheet or script and issues no request (§5.9). Rendered output contains no `src`/`href` to a remote origin from edited content.
- **CSP.** The component is compatible with the portable host's `connect-src 'none'` posture (`h2a-spec` §5.5/D5) and with the MCP Apps default CSP shape recorded in the JSON render standard (`connect-src 'none'`). It requires no `unsafe-eval`, no inline-script exception beyond the host's own bundle, and no `img-src`/`font-src` remote allowance. Any future need for a CSP exception is a stop signal to record, not a waiver to add silently.

## 13. Interfaces with h2a lots (RT-D10)

### 13.1 What FE-3 consumes, and when

FE-3 (h2a portable in-place editing) consumes, from the published DS packages at an exact pinned version recorded in `packages/h2a/focus-kit/package.json` host-side:

- `@sentropic/design-system-rich-text` (the pure `"."` entry for types, profile descriptors and document logic, and the `"./editor"` entry for the runtime the adapter mounts) and `@sentropic/design-system-svelte/rich-text-editor` (the component), imported by exact subpath — never the DS barrel.
- The host adapter (`packages/h2a/focus-kit/src/EditableField.svelte` + `editing-session.js`, h2a-side files named by the h2a specification) supplies: the Focus manifest's paragraph identities as `RichTextDocument` block IDs, a Focus-compatible `allocateId`, the resolved `messages` catalogue, the `editable` state from dossier-level amend mode, and the retained Focus baseline (`ParagraphValue[]` from the manifest it holds). On each `RichTextChangeEvent` it maps `document.blocks` to draft `ParagraphValue[]` through those identities and computes the per-paragraph diff with `@sentropic/focus/editing` (`diffParagraphs`, merged `packages/focus/src/editing/diff.ts`) against the retained baseline, then splices host-side by reusing that same pinned module — `applyParagraphChanges` (`packages/focus/src/editing/diff.ts:40–83` at `98060bd0a`) — toward the return that h2a FE-4 machinery freezes. FE-3 implements no second splice and no second diff: `applyParagraphChanges` is the splice implementation FE-3 reuses (host-splice bullet below). The two pairs are kept separate: `applyParagraphChanges(baselineDocument, baselineManifest, transactions)` returns a spliced `{ document, manifest }` whose `baseHash` is `baseDigest(splicedDocument)`, while `freezeReturn` is always called with the retained baseline `(document, manifest)` unchanged; the spliced manifest is never substituted as the freeze baseline. `gesture` is consumed as provenance only (logging, caret handling); it is never translated into `ParagraphChange` records by hand, and no second diff algorithm exists on either side of the boundary. The retained baseline never advances on freeze or export (§5.3): `freezeReturn` preserves the supplied document and manifest and validates any previous return against that same base, and `carryManifest` is reserved for a new authoritative producer version once acknowledged. The FE-3 freeze check therefore runs the §5.3 witness end to end — baseline `A`, type to `B`, controlled echo of `B`, freeze `R1`, undo to `A`, freeze `R2` with `transactions: []`, identical `source.baseHash`/`manifest.manifestBaseHash` on `R1` and `R2`, and `R2` superseding `R1` — and any baseline advance at echo, freeze or undo fails FE-3. For export, the adapter awaits the component's deferred capture (`captureDocument()`, §5.6) so the frozen document is the displayed revision, never a mid-composition or stale snapshot. The DS component supplies no diff, no anchors and no baseline to the wire; the return envelope is built host-side.
- **Host splice: full-source byte identity (interface requirement on FE-3, blocking).** The DS boundary stops at block identity (§6.5); reproducing the source as a whole is the host adapter's splice, and FE-3 must implement and witness it as follows. (a) *Retention:* for each edited field the adapter retains the original source string and the Focus codec segmentation for it (the ordered `[{ start, end, editable }]` ranges from `segmentMarkdown`/`segmentText` at the pin, with the gap bytes between ranges — blank lines, CRLF/CR forms, trailing whitespace, final newline — never normalised, trimmed or re-emitted from a template). (b) *Splice (reuse, no second reconstruction):* on export FE-3 calls the pinned `applyParagraphChanges(baselineDocument, baselineManifest, [diffParagraphs(baselineValues, draftValues)])` and uses its returned `document` as the spliced source. That function is the only splice: at `98060bd0a` (`diff.ts:40–83`) it tokenises each field as gap bytes (`source.slice` between manifest paragraph ranges) interleaved with paragraph slices, replaces or deletes paragraph tokens in place, preserves every gap byte verbatim, and joins a genuinely inserted paragraph to its neighbours with `"\n\n"`. FE-3 writes no separator of its own, creates no range template and re-emits no gap from a template; split/merge/paste identity following (§5.2, §5.3 gesture provenance) decides only how `document.blocks` map to draft `ParagraphValue[]` before the diff, never a second range splice. The baseline pair retained under (a) stays the `freezeReturn` input (see the adapter bullet above); the spliced `{ document, manifest }` returned here is the exported source, not a new freeze baseline. (c) *Witnesses (mandatory, in FE-3, against the Focus codec ranges):* over the same corpus shape as §11 RED 2 (P0 constructs, preserved table/fence/heading/list, CRLF separators, trailing blank lines, final newline). *No-change:* open → edit nothing → the `applyParagraphChanges` output reproduces the original source byte-identically (full string equality, separators included) and `diffParagraphs` against the retained baseline is empty. *Single edit:* edit exactly one middle paragraph → the spliced source equals the original with exactly that paragraph's range replaced by the new text, every other range and every gap byte identical. *Refused paste (the FE-3 half of RED 7):* for each non-paragraph payload of §11 RED 7, after the DS refusal (document unchanged, selection unchanged, zero `onChange`, refusal reported — asserted DS-side in `paste.test.ts`), FE-3 asserts the host consequence with the retained baseline kept separately for `freezeReturn`: `diffParagraphs(baselineValues, draftValuesAfterRefusal)` adds no new transaction or change over the pre-paste draft, `freezeReturn` called with the retained baseline `(document, manifest)` yields a return unchanged from the pre-paste freeze (same transactions, same `source.baseHash`/`manifest.manifestBaseHash`, same supersession), and the whole source from `applyParagraphChanges` is byte-identical to the pre-paste source. *Agreement after split, merge, paste and undo:* for each gesture — Enter-split, Backspace-merge, paragraph-only paste, and undo back toward the baseline — FE-3 captures the draft via `captureDocument()` (§5.6), maps it to draft `ParagraphValue[]`, computes `diffParagraphs` then `applyParagraphChanges` as in (b), and asserts the two sides agree: `readParagraphs(splicedDocument, splicedManifest)` from the spliced output deep-equals the captured draft `ParagraphValue[]` (same `paragraphId` values, same texts, same order and field addressing), and each spliced field string equals the baseline source with every gap byte preserved and every genuinely inserted paragraph joined by `"\n\n"` exactly as `diff.ts:40–83` writes it (undo to the baseline yields the empty diff and a spliced source byte-identical to the original). Any case failing fails FE-3; a DS block-identity green (RT-2) never substitutes for these witnesses, and these witnesses never re-open the DS model to store separators (§5.1). This is the single splice implementation; the DS exposes no splice helper (§6.5), so no second separator handling exists to drift from these ranges.
- Timing: FE-3's default path unblocks when RT-1's gate is green **and** h2a has installed the exact published artefact and run one offline paragraph/question edit against it (the observable unblock stated by merged `docs/focus/document-editing.md`: install the exact published artifact, run the FE-3 offline edit, then FE-4 export/import and the tarball round trip). ### 13.3 What FE-8 needs from the DS

- **Measurable reactivity invariants on the component** (budgets themselves are FE-8's phase-B output, `h2a-spec` D22; the DS supplies the measurable surface, not the numbers). Each invariant is observed directly on the mechanism it names; a proxy never satisfies it:
  1. *No remount per keystroke:* the internal witness (`packages/rich-text/src/reactivity.test.ts`, §11) counts editor-factory constructions and destructions across a typing burst — exactly one construction, zero destructions — and the browser suite additionally checks that the editor DOM root element is the same node before and after the burst. A stable DOM root alone never satisfies this invariant, because it does not prove a stable ProseMirror instance.
  2. *No whole-document reparse per keystroke:* the same internal witness counts calls to the `"./editor"` whole-document conversion / Markdown parsing entry across the burst — zero whole-document calls per keystroke; only the affected block is touched, as a ProseMirror transaction — and checks that preserved blocks' `raw` values are unchanged in every emitted document. A single `onChange` count, or equality of one `raw` string (a value with no observable object identity), never satisfies this invariant; the counters observe the construction and parsing calls directly, inside the package's own tests, and no editor, view or parser object is exposed in the public API to make the observation.
  3. *Caret/selection/scroll preservation:* locale (`messages`) and theme (token) changes preserve the real `Selection` anchor (block ID + offset) and scroll position — asserted in `RichTextEditor.browser.test.mjs`.
  4. *Stale-result safety:* an external update arriving during composition or while locally divergent surfaces via `onExternalConflict` and never overwrites (§5.6); the exported snapshot equals the displayed revision because the host freeze awaits `captureDocument()` (§5.6, §13.1), never a mid-composition state and never a bare re-read of the last `onChange`.
  5. *Zero network per session:* request interception in the browser suite counts zero requests from mount through edit to unmount (RED 8 network half, observed for the whole scenario).

## 15. NOT covered

Each item below is explicitly excluded from this specification and from the Stage-1 delivery. Announcing any of them as delivered under this specification is a scope breach.

1. **The Focus return, manifest, diff, reconciler, digests and schemas.** Owned by h2a/Focus (FE-0/FE-1/FE-5). The DS consumes them by pinned reference only (§13.4) and defines no second shape.
2. **Full-document editing:** table-cell editing, diagram source or scene editing, code-block editing, heading editing, blockquote editing, link/image editing, and any Markdown construct outside the §6.1 P0 profile. Those blocks are preservation witnesses, not editing witnesses.
3. **List editing before the §6.4 three-condition gate.** Lists stay preserved and visibly non-editable until a compatible h2a evolution, a new pin recorded in both specifications, and the joint FE-1/FE-2 witnesses have all passed. A DS-only round-trip result never enables list editing.
4. **A formatting toolbar, slash menu, mention/autocomplete system, or any popover UI.** P0 input is keyboard + Markdown input rules (Q-RT-2).
5. **Collaborative or multi-writer editing:** CRDTs, presence, simultaneous cursors, a document server, and any `LiveDocumentStore` implementation.
6. **Persistence, autosave, transport and business logic in the component:** no localStorage draft, no `apiPut`, no store, no Track write, no inbox delivery. Draft recovery and export are host duties (h2a FE-4).
7. **React, Vue and Angular adapters claimed as delivered** before their §4.3 stage gates pass. Stage 1 is Svelte only and is announced as such.
8. **Retro-editing previously rendered HTML files** and any `renderHtml`+runtime host qualification (h2a V13): allowed by the Focus contract, not a DS gate here.
9. **Performance budgets.** Numeric keystroke/paint budgets are FE-8 phase-B outputs derived from measurement (`h2a-spec` D22). This specification supplies measurable invariants (§13.3) and no threshold numbers.
10. **The business substance of any dossier** and the qualification of the real reference case (h2a FE-9). DS fixtures are synthetic and labelled as such (§11.3).
11. **Publication mechanics beyond the DS guard:** npm availability of any h2a package, CDN distribution, and MCP `ui://` hosting of the editor are not asserted here.
12. **A second editor.** Neither a `focus-kit` fallback maintained past its replacement gate (§13.2) nor a per-framework re-implementation of the profile and editor conversion (§4.1 option 3) is covered or permitted under this specification.
