## 0. How to read this specification

### 0.1 Source tags (mandatory on every decision)

Every decision in §3 carries one primary source tag.

| Tag | Meaning |
| --- | --- |
| `frozen-requirement` | A value or behaviour from the frozen requirements file (§2.1). It is final: no lot may re-open it, mark it provisional, or substitute a measured code value for it. |
| `measured-code` | A fact read from the pinned hrpolnav kit (§2.2, sha256 per file), the sentropic `4138a0ec` code it copies byte-identically, the radar origin, or this repository at the base above. Measurements state their locator. Where a measurement conflicts with a `frozen-requirement`, the frozen value governs and §15 records the difference. |
| `ds-proposition` | A design choice made by this specification for the design system. It requires DS owner ratification where §17 states so and must never be reported as an owner requirement. |

`SHALL` / `MUST NOT` state the proposed contract. Frozen requirements already carry force from the owner validation of 2026-10-21; `ds-proposition` clauses acquire force at ratification of the corresponding decision.

### 0.2 Units and the one scale

- All card values are **card pixels**: CSS pixels at zoom 1, on the 1:1 SVG scale of the reference render (`frozen-requirement`, requirements §"Atomic card"). A token whose value is stated in card pixels does not scale with the diagram zoom unless its row says so; the rule (§5.4) is the single exception that is defined in screen pixels.
- Zoom is a host/view concern (camera in `PresentationState`, `packages/diagram-core/src/view.ts`). No card component in this specification owns a zoom control. The generic scene figure (§7.6) owns zoom/pan/viewer chrome as figure behaviour, never as card behaviour.
- Every geometric or typographic value is a **named component token** (§5.3, §6.4, Appendix A). A raw hex value, a raw pixel value outside a token definition, or a locally redefined `--st-*` token in a card, a dossier, a kit or a scene stylesheet is a defect (§5.5).

### 0.3 What this specification does not do

It creates no package, no component and no test. It defines the contract that lots DC-0 to DC-4 (§12) implement, the gates they must pass, and the acceptance items (`CA-…`) that witness each gate. File lists in §12 use `[N]` for a new file and `[M]` for a modified file, following the rich-text specification's convention.

## 1. Goal, scope, non-goals

### 1.1 Goal

Deliver reusable design-system modules, validated at pixel parity (§10):

1. **Atomic card** — the leaf card, for example « 1. Server API » (`frozen-requirement`, requirements §"The two modules").
2. **Wrapping card** — the zone/group frame, collapsed and expanded, for example « H2A · Responsible AI Organization », **including its interactive fold/unfold mechanism** as part of the component. **Collapsed, the wrapping card is the atomic card**: the same `DiagramCard` component, plus the +/− `IconButton` in its reserved toggle slot (§6.2). No display hack of §2.6 survives in the DS.

Both modules:

- are **pixel-exact** against their references (§10: atomic render for atomic and collapsed, expanded-zone render for expanded), witnessed by a visual parity test;
- work as **xyflow (Svelte Flow) custom nodes** with handles, and standalone (§8);
- are **embeddable in graphs** and **editable Tiptap-style** (§11, gated on RT-1);
- bind to the **diagram-core pivot document** as their only model; Engram provides the profiles; there is no second model (§4);
- render **generic scenes**: any scene folds at any nesting level, with default folds, layout tree and routing relaxation supplied as data/engine options (§7.5), and a legend carried by an ordinary wrapping card (§7.6). The hrpolnav scenes and the `4138a0ec` central scene are the acceptance scenes (§2.5, Appendix C).

Owner verbatim (requirements file, §"The two modules"): « réutilisable au pixel »; « mode xyflow ou la suite »; « doivent devenir des modules design system incubables dans les graphiques et doivent devenir éditables a la tiptap ».

### 1.2 In scope (this specification)

Section map: §2.6 display-hack inventory (none survives); §4 pivot binding; §5 atomic card (including the reserved toggle slot); §6 wrapping card (collapsed renders the atomic card, expanded renders the shared zone header plus children) and the collapsed-subtitle centring mapping; §7 interactive fold/unfold, generic scenes and the generic scene figure; §8 xyflow nodes, standalone use and graph embedding; §9 pictograms; §10 pixel parity and geometry checks; §11 editable surface (gated on RT-1); §12 lots, gates and acceptance items; §13 staged out-of-scope items; §14 consumer switch-over (per-file mapping); §15 differences between code and frozen requirements; §16 changes required in L-R16 (and in L-R15(c)(d), §10.11, §10.12 where they touch these components); §17 open questions.

### 1.3 Non-goals

- No layout engine is specified here beyond the fold reflow contract of §7.3 and the generic-scene engine options of §7.5: ranking, docking, orthogonal routing and label placement remain the L8 engine rules (L-R1 to L-R14) implemented by `packages/diagram-canvas`.
- No edge editing, no edge re-connection, no draw.io export shape is specified (§13 names their owners). The legend zone's *content* (which tints, which labels) is consumer data (§7.6); no separate legend component is specified.
- No React, Vue or Angular component is claimed delivered before its stage gate (§12.6). Framework parity is recorded per stage, never claimed from types alone.

### 2.1 Frozen owner requirements (requirements file, read in full)

Status line of the source file: owner-validated on 2026-10-21. Frozen values (requirements file; each is restated as a token in §5/§6 and collected in Appendix A):

- **Atomic card.** Fixed size **460 × 200** (ratio 2.30:1); every card the same size; a card never grows with its text. **Square corners**: on a 3 px radius the owner word is « strictement invisibles » — no radius. Left accent bar and border as in the radar-immobilier `ServiceNode` reference (`fa8133c2`). Header: icon 70; icon → text gap 6; kicker 22 px, weight 400, uppercase, grey secondary token; title 32 px, weight 700, line-height 1.3. Body: 24 px, weight 400, line-height 1.3; body left inset is the original + 4 px (accent bar → first glyph 14 px). Rule: 1 px, border-subtle token (`#bdcad0` fallback), 4 px margins; it stays **1 screen px at every zoom**, including the overview. Footer (for example « service: Sentropic ») pinned to the bottom; bottom offset is the original 9.25 px; the owner rejected the extra bottom inset. **No ellipsis, ever**: wording must fit the allocated size, otherwise an overflow diagnostic is emitted; no clipping.
- **Wrapping card.** **One header component for all zones** — owner: « utilise le meme composant pour tous ». Same typography as the atomic card for every role: title 32/700; kicker 22/400, uppercase grey, **not bold**; subtitle 24/400. Icon 70, the same as the cards — owner: « pourquoi les icone des groupes sont plus petits ». The kicker carries the package name: `H2A`, `SENTROPIC`, `ENGRAM`, `DESIGN SYSTEM`; « SENTROPIC & 3RD PARTIES » / FR « SENTROPIC & TIERS » for Access surfaces; « SENTROPIC » for its sub-zones. The title is shown without the package prefix. The header follows its actual content (no reserved empty title line). The title → subtitle gap equals the card's. Expanded: the subtitle wraps under the icon from the left inset; the header is separated from the body by the same rule as the card footer. Collapsed: the collapsed frame has the card size; its subtitle is **centred horizontally and vertically** in the free area under icon + titles, with a 16 px side margin on each side; lines are simply centred — no justification, no letter/word stretching; owner: « pas de justifier les caracteres ». Zone frames side by side in a row share top and height; card rows and columns are aligned with 0 px deviation.
- **Expanded zone spacing (frozen).** Subtitle last line → header rule: **4 px** in every zone, whatever the number of subtitle lines; it equals the card's body → rule gap. Header rule → top of the child cards: **16 px**. Bottom of the child cards → zone bottom edge: **16 px**. Top and bottom stay balanced. Edges never reserve empty height: they route in the gutters between cards, along the frame, or outside it.
- **Icons.** One **blue duotone pictogram family**, delivered as a DS asset on its own subpath: same base diamond, palette, layers, 64-unit viewBox and stroke weight. It includes the pictograms added for #711: `brain` (AI) and `robot` (agents). Lucide outline icons are never mixed inside diagram cards.
- **Fold/unfold (part of the wrapping card).** Every wrapping card can be collapsed or expanded in place with a +/− icon button, the DS Lucide `IconButton`; its focus ring appears on keyboard focus only (`:focus-visible`), never after a mouse click. Collapsed, the wrapping card takes the atomic card size (460 × 200) at every nesting level, with the collapsed-subtitle centring above. Expanding or collapsing reflows the layout without collisions, and edges re-route. Global controls: « Expand all / Collapse all », and per-zone chips in a bar above the canvas. Performance: no continuous work at idle; the worst interaction stays under 1.8 s, measured over 600 interactions and 240 stress toggles; timeouts are never raised.
- **Edges (future, non-blocking).** Edges can be re-connected and their labels edited inline, as proposals the host applies or refuses, in diagram-core. Track `01M5F3XSAJC2H6S9ZREP7JFFJ6`. Out of scope here (§13).
- **Performance (general).** No continuous work at idle. Worst interaction under the 1.8 s UI budget; timeouts are never raised.

Raw-feedback verbatims that the frozen file already settles, quoted here only so a reader can trace them (they add no requirement beyond §2.1): « les "+" sont immondes (bcp trop grand, et on a un design system) » (the complaint is size/style, the +/− controls stay); « a la premiere présentation, laisse tout replié » (initial state, §7.2); « utilise un seule modele de largeur pour les fiches (le moins large petit donc) »; « mets un S a sentropic » / « mets un O a organisation » (title capitalisation is content, never a renderer transform — §6.5).

## 3. Decisions

One decision per item. `DC-D…` ids are this specification's own; `L-R…` ids belong to the JSON render standard and are only referenced.

### DC-D1 — Two components, one shared header row, collapsed renders the atomic card — `frozen-requirement` (component split: `ds-proposition`)

The atomic card is **`DiagramCard`**; the wrapping card is **`DiagramZone`**. Both are Svelte components in `packages/components-svelte`, delivered first; React/Vue/Angular adapters are staged (§12.6) and reuse the same token and measurement contract. Every zone header — atomic-level or nested, expanded or collapsed — follows one header model (owner: « utilise le meme composant pour tous »), realised without duplication:

- the header row (icon 70, kicker over title, optional toggle slot) is one internal component, **`DiagramCardHeader`**, composed by `DiagramCard` and by the zone header;
- **`DiagramZoneHeader`** (internal, not a public export) composes `DiagramCardHeader` plus the expanded subtitle block and is rendered by `DiagramZone` only when expanded;
- **`DiagramZone` collapsed renders `DiagramCard`** (§6.2): the collapsed zone's header is therefore the atomic card's header by construction, not a second header that resembles it.

`DiagramZoneHeader` and `DiagramCardHeader` are not public exports: their contract is exercised through `DiagramZone` and `DiagramCard`. A per-zone header variant, a reserved empty title line, a second header implementation, or a collapsed-only header is a defect.

### DC-D2 — Pivot binding: entity → card, container → zone, no second model — `frozen-requirement` (mapping mechanics: `ds-proposition`)

A `generic@1` `node` entity (or any profile entity type declared as a card type by its Engram profile) maps to `DiagramCard`; a `container` entity maps to `DiagramZone`; containment is the profile's `contains` tree, never a component prop (§4). Card slots travel as profile-declared typed attributes; a renderer invents no slot by splitting a name or parsing an undeclared attribute. Collapse state is **view state** (`ViewDocument` groups + the layout input of §7.3), never a document attribute and never component-local state that a second view could disagree with.

### DC-D3 — Every value is a named component token at its frozen value — `frozen-requirement`

Tables §5.3/§6.4 and Appendix A are normative. Tokens only: no raw hex, no raw pixel value outside a token definition, no locally redefined token, in light and dark alike. The decomposition of any composite inset is fixed by stating each token's measurement edges; where the kit code's decomposition sums to a different total than the frozen token, §15 flags it and the token governs.

### DC-D4 — Zero-ellipsis: overflow is a diagnostic, never a rendering choice — `frozen-requirement`

No slot is ever truncated, clipped or ellipsised, at any zoom, in any state (§5.4). A text that does not fit its frozen allocation raises the diagnostic `card-overflow` (card variant) or `zone-overflow` (zone header/collapsed body), naming the component instance, the slot and the measured need against the allocation. The host shortens the wording or the profile allocation process re-issues the content; the renderer never resolves overflow by itself. This decision replaces every kit fitting device of §2.6 (DH-07 title shapes, DH-08 generated summaries, DH-12 hand overrides): fit failures surface as diagnostics, never as silent content edits.

### DC-D5 — Fold/unfold is part of `DiagramZone` — `frozen-requirement` (engine assignment: `ds-proposition`)

The +/− control is the DS `IconButton` (`size="sm"`, `variant="ghost"`, Lucide `Plus`/`Minus`) with its ring on `:focus-visible` only, rendered in the reserved header slot (§5.1, §7.1) in both states of a zone and never on a leaf card unless a host passes a toggle to a standalone card. The chips bar is **`DiagramZoneFoldBar`**; Expand all / Collapse all are host/figure controls emitting the same per-zone state changes in bulk (§7.2). The layout and routing engine that reflows a fold in the DS is **`packages/diagram-canvas` (`layoutDocument`) extended with the L-R15(c) collapse input**, reusing `packages/diagram-core` view state. From the kit, the *algorithms* of §7.4 are ported as behaviour (representative projection, edge aggregation, header measurement, bounded route memoisation); no kit file, hand layout table or scene data is copied.

### DC-D6 — xyflow nodes are thin wrappers; measured size feeds layout — `frozen-requirement` (wrapper shape: `ds-proposition`)

`DiagramCard` and `DiagramZone` each have an xyflow (Svelte Flow) node form (§8) with handles, the fixed 460 × 200 footprint for leaves and for collapsed zones, and the engine-computed rectangle for expanded zones. The size the layout consumed is the size the node reports: the wrapper takes its box from the `ViewDocument` occurrence geometry and never re-measures itself into a different box. Standalone use (no xyflow) renders the same components from the same props.

### DC-D7 — Pictograms: one blue duotone family on its own subpath — `frozen-requirement` (subpath name: `ds-proposition`)

The icon slot draws only from the blue duotone family of §9 (same base diamond, palette, layers, 64-unit viewBox, stroke weights), including `brain` and `robot`. The set ships as `@sentropic/design-system-svelte/diagram-icons`, an explicit subpath export, **never through the main barrel**: a host that draws no diagram card loads no pictogram. No Lucide glyph is drawn inside a diagram card; the fold control (§7) sits in the header's toggle slot, outside the pictogram slot, and keeps the DS `IconButton` contract.

### DC-D8 — Pixel parity against named references, collapsed against the atomic card — `frozen-requirement` (method: `ds-proposition`)

Acceptance compares DS renders by the method of §10: the atomic card and expanded zones against `governance-r11-portable.html` at `4138a0ec` (sha256 in the header); **collapsed zones against the DS atomic card render for the same field set plus the toggle** (§10.1) — never against the #711 collapsed frame (460 × 272, header plus centred subtitle). Where a frozen requirement overrides the code that produced a reference (collapsed height, ellipsis, footer pin, body inset, dark tokens — §15), parity asserts the frozen value and lists the reference's value as an intentional deviation; a deviation not listed in §15 fails the test. The HRPN folded-card render at 460 × 200 (kit at §2.2.1) is a secondary witness for collapsed geometry on HRPN scenes, not the reference: its DH-07 title shapes and DH-08 slot split are not parity targets.

### DC-D9 — Editable surface, fully specified, gated on RT-1 — `frozen-requirement` (gating: `ds-proposition`)

Inline editing of kicker, title, body and footer is specified in §11 through the rich-text editor (profile P0). Editing emits diagram-core commands carried in §4.6 `proposal` events; the host applies or refuses them; the component never mutates the document itself. Lot DC-4 implements §11 and **cannot start before RT-1** (the Svelte rich-text adapter, **under way since the owner GO of 2026-10-22**) passes its gate. No fallback editor is specified or permitted.

### DC-D10 — Lots DC-0 to DC-4, RED-first, each with its gate — `ds-proposition`

§12. No lot claims the next lot's surface. The switch-over point for both consumers is **DC-3** (§14).

### DC-D11 — Staged items stay with their owners — `frozen-requirement`

draw.io export keeping folds as collapsible groups belongs to the DS draw.io converter work (L8 dossier r3 vehicle); editable/re-connectable edges belong to Track `01M5F3XSAJC2H6S9ZREP7JFFJ6`. This specification defines no shape for either (§13). The legend zone (§7.6) is a generic zone and is not staged: only a dedicated legend *component*, if one is ever required, would be staged (Q2, §17).

### DC-D12 — Generic scenes: fold everywhere, scene specifics as data — `measured-code` (contract split: `ds-proposition`)

The HRPN adaptations generalise the kit from one gated scene to any scene. The DS adopts the generalisation as contract and the specifics as data (§7.5 table):

- **DS contracts** (`diagram-core` view state, `diagram-canvas` engine options, components): fold state for any container in any scene (no scene-id gate); a layout-tree input; a routing-relaxation option with reported counts; the generic scene figure (§7.6); a legend carried by an ordinary zone.
- **Consumer data** (host-supplied, never hard-coded in the DS): the per-scene default fold set, the per-scene layout tree, the per-scene relaxation choice, legend entries and tint mappings, zone kicker/title/subtitle/icon/footer strings.

A DS package that contains a scene id, a zone id, a default fold list, or a layout tree for a named scene is a defect.

### DC-D13 — Collapsed size is 460 × 200 — `frozen-requirement`

The frozen requirements state the atomic card size for a collapsed wrapping card; the #711 code uses 460 × 272 (`COLLAPSED_CARD_HEIGHT`, `src/governance-layout.js:6`); the owner order of 2026-10-22 states the foldable cards are identical to the normal cards, and the HRPN base already renders them at 460 × 200 (`hrpn/pack.js` folded height, `hrpn/check-geometry.mjs:33`, `hrpn/check-browser.mjs:95`). **Decision: 460 × 200 at every nesting level.** The divergence from the #711 code and its consequence for the parity test are recorded as DIF-01: the collapsed parity reference is the atomic card render (DC-D8), and the portable's collapsed frames are excluded from box comparison by name. The collapsed-subtitle centring rule (16 px side margins, no justification) is kept and mapped inside the atomic card body area in §6.2.1; it is the one deliberate difference between a leaf card's body (left-aligned function/detail lines) and a collapsed zone's body (centred summary lines), and it is implemented inside `DiagramCard`, not as an external override.

### DC-D14 — No display hack in the DS — `ds-proposition` (from the owner order)

No mechanism of §2.6 (DH-01…DH-13, CH-01…CH-04) is ported, renamed or reintroduced: no scene-flag size switch, no second collapsed renderer, no rendered-string surgery, no rule deletion, no invented adapter field feeding a collapsed-only slot, no duplicated tint CSS, no toggle-clearance constant or header padding override, no parenthesis relocation or body deletion, no generated « +N » summary, no compact-legend flag/filter/append, no kicker text replacement, no icon-map mutation, no title pre-fitting table, no `foreignObject` sizing pass, and no check that skips or strips the folded identity. Each hack's DS replacement is stated in §2.6 and witnessed by the acceptance items named there. A reviewer who finds a collapsed-only style rule, attribute or branch in a DS lot whose effect is to make the collapsed zone *look like* the card (rather than *be* the card) records it as a DC-D14 defect against that lot's gate.

## 4. Pivot binding (diagram-core)

### 4.1 Entity mapping

| Pivot element (`generic@1` names; other profiles by declaration) | Component | Occurrence |
| --- | --- | --- |
| Entity whose type is declared a card type (`node` in `generic@1`) | `DiagramCard` | One `EntityOccurrence` with `Geometry` 460 × 200 (§5.2) |
| Entity whose type is declared a container type (`container` in `generic@1`) | `DiagramZone` | One `EntityOccurrence`; expanded geometry from layout, collapsed geometry 460 × 200 (§6.2) |
| `contains` relation (roles `parent`/`child`, hierarchy `containment`) | Nesting of zones and cards | Drawn by nesting; no `RelationOccurrence` (engine rule, `diagram-canvas` §"OUTPUT") |
| `link` relation (roles `source`/`target`) | Edge between cards/zones | One `RelationOccurrence`; route from `relationRoute(view, occurrenceId)` (§8.2) |
| Semantic port + `PortOccurrence` (`side`, `order`, `anchor`) | xyflow handle (§8.2) | One handle per port occurrence |

The mapping is by **declared type**, never by name pattern, depth or child count. A profile that declares further card or container types (Engram profiles) names them in its declaration; the components consume the declaration. `DiagramCard` never renders a container's children and `DiagramZone` expanded never renders a leaf's body lines: the variant is selected from the entity type, exactly as L-R16(a) selects the card variant from content presence for dossier diagrams. Collapsed, `DiagramZone` renders a `DiagramCard` for its own entity (§6.2); it still renders no child entity.

### 4.2 Card slots as profile attributes (schema work, gated)

`generic@1` today declares, for `node`: `name` (text, required, ≤ 200), `state`, `weight`, `duration`, `createdAt`, `pinned`, `tags`, `owner`; for `container`: `name` (required, ≤ 200, unique), `collapsed`. It declares **no** kicker, body, footer, icon or tint attribute, and `validateDocument` refuses an undeclared attribute as `attribute-not-in-schema` (`packages/diagram-core/src/validate.ts` via `src/attributes.ts`). Therefore:

- The slot attributes are **profile schema work owned with the Engram profile definitions** (the same h2a-side schema item the L8 amendment lists in its §10.13): the profile in force for a card scene SHALL declare, per card type, the optional attributes `kicker` (text), `body` (text; body lines in order, §5.1), `detail` (text; the secondary-tone body line), `footer` (text), `icon` (text; a §9 glyph name — never SVG data), and, per container type, `kicker` (text; the package name, §6.3), `subtitle` (text) and `footer` (text; the collapsed card's footer, §6.2 — the field the kit adapter had to invent as `cardFooter`, DH-05, becomes a declared attribute). Attribute length bounds are set by that profile work so that the measured corpus of §10 fits; the frozen geometry does not move to fit a longer bound (DC-D4).
- `name` remains the title source: for a card, the entity `name` is the title; for a zone, the entity `name` is the zone title **without** any package prefix (§6.3). A document that stores « H2A · … » as a zone name is migrated by its producer, not parsed by the renderer (no ` · ` splitting anywhere in a component — the adapter splitting of `hrpn/scene-adapter.js:42–52` is consumer migration logic, not a DS rendering rule).
- Tint/tone is **not** a `generic@1` attribute today. HRPN tints (Appendix C) are scene semantics carried outside `generic@1` attributes by the fixture's own statement (`profileMapping.extraFields`). In the DS, a card's tone resolves from the profile-declared tone kind where a profile declares one (L-R17 tones), and HRPN tints map to tone tokens only through the consumer's own mapping (§14) — the DS ships no HRPN tint token and no `data-tint` mechanism (DH-06).
- Until the profile in force declares the slot attributes, a scene renders simple label nodes under L-R12 and **no** card: inventing slots is forbidden (L-R16(b) rule, carried over unchanged). DC-1's gate therefore includes the profile declaration for the scenes it accepts (§12).

### 4.3 Collapse state is view state

Two carriers exist at this base and the choice is normative:

- `container.collapsed` (semantic attribute) is **not** the fold state. Folding is presentation: two views of one document may fold differently, a fold must not bump `document.revision`, and an undo of a text edit must not unfold a zone. Recording a fold as an `update-entity-attributes` command would violate all three.
- The fold state is the **view state**: one `VisualGroup` per container in the `ViewDocument`, with the deterministic id form of L-R15(c) (`grp.<len>.<local id>`) and `collapsed` set from the layout input, plus the `layoutDocument` collapse input itself (§7.3). `DiagramZone` receives `collapsed` as a prop derived from that state; its toggle emits the §7.2 event; the host re-runs layout and replaces the `ViewDocument` wholesale. Component-local fold state that survives a `ViewDocument` replacement, or that a static export cannot read back, is a defect (§10.12 of the JSON render standard: the export preserves the supplied collapse state). The per-scene default folds (§7.5) are the *initial* value of this view state, supplied as data; they are stored in the `ViewDocument` the host first supplies, not in the document and not in a component default.

### 4.4 Commands and proposals (editing and interaction boundary)

- Components never mutate a `SemanticDocument` or a `ViewDocument`. Every outward effect is an event of §4.6 of the JSON render standard: `intent` (`select`, and the diagram `collapse`/`expand` names of its §10.11) for interaction, `proposal` (`{ "event": "proposal", "transaction": { "commandId", "baseRevision", "commands": [...] } }`) for edits the host applies with compare-and-swap or refuses.
- Text edits (§11) propose `update-entity-attributes` commands against the slot attributes of §4.2. Fold toggles propose **no document command**: they are `collapse`/`expand` intents answered by a freshly laid-out `ViewDocument` (§7.2).
- A proposal's `baseRevision` is the revision the component rendered from. A host refusal (including `revision-conflict`) leaves the rendered document untouched; the component shows no local winner (§11.3).

### 4.5 No second model

No type in `packages/components-svelte` re-declares an entity, a relation, a containment tree or a fold set. Props (§5.1, §6.1) are projections of one entity (plus its view state) computed by the host or by the xyflow adapter (§8); the projection is derived deterministically from `(SemanticDocument, ViewDocument)` and is never persisted as a model. The HRPN fixture shape (`entities[]`/`relations[]`, §2.5) and the kit scene shape (`groups`/`nodes`/`edges` of `hrpn/scene-adapter.js`) are inputs to a host-side projection onto `generic@1`, not component input formats.

### 5.2 Geometry — fixed size, measured once

- The card box is **460 × 200 card px** (`--st-component-diagramCard-width/height`), `box-sizing: border-box`, at every zoom (the box scales with the host transform; its card-pixel size never changes). Every card in a scene is the same size; rows and columns align with **0 px deviation** (geometry check §10.3). A collapsed zone reports the identical box (§6.2): layout, docking and routing consume one footprint for leaves and folded zones, with no folded-height variant (DH-01).
- The card **never grows with its text** (`frozen-requirement`). There is no `auto` size variant for `DiagramCard`: the L-R16 `size: 'auto' | 'fixed'` prop does not survive into this component (§16, LR16-C2). A scene that needs a larger leaf uses a zone, not a larger card.
- The measured footprint that feeds autolayout is the token box itself (460 × 200), taken **before** placement (§10.6 layering rule of the JSON render standard: card measurements are engine input). A token change that alters the footprint recomputes placement, docks and routes in the same layout call; an appearance-only change (fill, border colour, glyph inside the unchanged 70 px icon box) never moves a dock, route or rank.
- Text allocations are measured with the toggle state that will be rendered: a card rendered with `toggle` wraps its title against the header width **minus the toggle slot**; a card without `toggle` wraps against the full header width. The measurer (§7.4) receives the same allocation the renderer uses, so a folded zone's title and a leaf card's title obey one wrapping rule with two declared allocations — the declared replacement for `FOLD_TITLE` (DH-07).
- Anatomy, top to bottom (border-box edges; token names in §5.3): accent bar on the left edge; header row (icon box, then kicker over title, then the toggle slot when present); 6 px gap; body lines (full width at the body inset, left-aligned for leaf content, `text-align: left`; centred for collapsed-zone summary content, §6.2.1); rule; footer pinned to the bottom (§5.4). Vertical centring of the whole block inside a stretched rectangle is L-R15(a) and does not apply to the fixed card (its rectangle is never stretched — a rank that grows leaves the card at 460 × 200 and centres the *card*, per L-R6/L-R15(a) as amended in §16).

### 5.4 Rule, footer pin and the zero-ellipsis policy

- **One rule, 1 screen px.** The card draws exactly one rule element. In SVG hosts it is a `line` with `vector-effect="non-scaling-stroke"` and `stroke-width: 1` on the border-subtle token, so at overview scale it remains 1 screen px (the kit portable keeps both an HTML rule and an SVG overlay line; the DS component keeps only the non-scaling form — DIF-07, and no lot reintroduces the deleted-SVG-rule asymmetry of DH-04). In pure-HTML hosts the same visual is produced by a 1 px element counter-scaled by the host transform; a rule that thickens or thins with zoom fails §10.
- **Footer pinned.** The footer is pinned to the bottom of the fixed box: in flow terms the footer block is pushed by an automatic top margin (`margin-top: auto` or the flex equivalent) so that its text-box bottom sits at `footerBottomInset` from the bottom border's inner edge **whatever the body line count** (zero, one or two lines). The kit code reaches 9.25 only because its fixed content happens to fill the box (no pin construct) — DIF-04; DC-1 implements the pin and §10 asserts the inset at each body line count.
- **Zero-ellipsis (blocking).** CSS for every text slot forbids `text-overflow: ellipsis`, line clamping and content clipping as a fit mechanism: `overflow` on the card is `visible` for measurement purposes in tests, and the shipped style contains no `ellipsis`, no `-webkit-line-clamp` and no `white-space: nowrap` on card text (the kit style declares all three — DIF-02). Text wraps at word boundaries inside its allocation with the §7.4 measurer; a slot's allocation is its frozen box (kicker/title: header width at inset 92 to the card's right padding edge, minus the toggle slot when `toggle` is present; body: full width at `bodyInsetFromBar` for leaf content, the centred width of §6.2.1 for collapsed-zone content; footer: full width). If the measured need (lines × line-height, or a single unbreakable word wider than the allocation) exceeds the allocation, the component:
  1. still renders the complete strings (no character is dropped, shortened or replaced);
  2. raises `card-overflow` with `{ entityId, slot, neededPx, allocatedPx }` through `onDiagnostic` and sets `data-card-overflow="<slot>"` on the root;
  3. leaves geometry unchanged (the box stays 460 × 200; the layout is not recomputed around a grown card).
  The host surfaces the diagnostic in its diagnostics list (the diagram-core `Diagnostic` shape, §12 CA-DC1-4) and shortens the wording; a scene with an unresolved `card-overflow` fails its geometry gate (§10.3). Overflow is therefore visible in checks and in the host UI, never hidden inside the card. The same rule applies to the zone header as `zone-overflow` (§6.2).

### 5.5 Colours, tokens only, dark mode

### 6.2 Expanded and collapsed anatomy

**Expanded.** `DiagramZoneHeader` (icon 70 at the 16 px header inset via `DiagramCardHeader`, kicker over title at the 92 px text inset, toggle in the header slot, subtitle wrapping under the icon from the left inset at `x + 16`); then the header rule — the same rule as the card footer rule (1 screen px, border-subtle, same insets); then the content box. #### 6.2.1 How the collapsed-subtitle centring rule maps inside the atomic card body area

Frozen rule (requirements, §2.1): collapsed, the subtitle is centred horizontally and vertically in the free area under icon + titles, with a 16 px side margin on each side, lines simply centred, no justification. In the kit this free area is a frame area (frame inset 16 + margin 16 ⇒ text width `width − 2 × (16 + 16) = 396`, `src/architecture-svg.js:33–38`) and the vertical centre is a baseline formula with a `+7` glyph-bounds offset (DH-02). The DS keeps the rule and changes only its reference box:

- **Reference box = the atomic card's body area.** The body area is the rectangle between the header block (header row + 6 px `gap`) and the rule (or, with no footer, the card's bottom padding edge). Its vertical extent is therefore fixed by the card anatomy — the same lines the footer pin (§5.4) measures from — and no frame-area or baseline-offset computation exists.
- **Horizontal:** the subtitle wraps with the §7.4 measurer at **396 px** (`460 − 2 × 32`), i.e. each side margin is 32 px from the card edge, decomposed as the card's body inset plus the frozen 16 px side margin inside it (tokens `collapsedInset` 16 + `collapsedSubtitleMarginInline` 16, §6.4, now measuring the body area of the card instead of a frame area). Each wrapped line is centred on its own within that 396 px measure (`text-align: center` equivalent). **No justification:** letter-spacing, word-spacing and glyph scaling keep the card body values; `textLength`/`lengthAdjust` or any spacing change to fill a line is forbidden and asserted absent (§10.2).
- **Vertical:** the wrapped line block (at most the body allocation: two lines at 24/1.3 under the frozen card content sum) is centred within the body area height. A one-line subtitle therefore sits in the middle of the two-line body allocation, not on its first line. This centring is a rendering mode of `DiagramCard`'s body when the card carries collapsed-zone content, declared in the component (§5.1 `body` rule) and tokenised in §6.4 — it is not a consumer CSS override and it applies to no leaf card.
- **Overflow:** a subtitle needing more than the body allocation (more lines than the area holds at 396 px, or one unbreakable word wider than 396 px) still renders completely, keeps the box at 460 × 200, and raises `zone-overflow` with slot `collapsed-subtitle` (§5.4 mechanics). It is never fitted by reducing the font, narrowing the margins, or switching to left alignment.

Leaf-card body lines remain left-aligned and top-aligned in the same body area (§5.2). The centred summary and the left-aligned function/detail lines are the two declared body contents of one component; parity for the collapsed body is asserted against a `DiagramCard` rendered with the same subtitle, centred mode and toggle (§10.1), so the centring is witnessed as card behaviour, not as a zone drawing that resembles one.

## 7. Interactive fold/unfold, generic scenes and the generic scene figure

### 7.1 The toggle control

Each foldable `DiagramZone` header carries one toggle: the DS `IconButton` (`@sentropic/design-system-svelte` barrel export), `size="sm"`, `variant="ghost"`, Lucide `Plus` when collapsed, `Minus` when expanded, `aria-expanded` set from the collapsed state, `aria-label` from the host-supplied `toggleLabel`. Expanded, `DiagramZoneHeader` renders it in the header slot; collapsed, `DiagramCard` renders it in the same slot through the `toggle` prop (§5.1) — one control, one placement rule, both states. The icon size inside the button follows the DS button anatomy token (`--st-component-button-anatomy-density-sm-fontSize`), as `FrameToggle.svelte` does. The focus ring is the `IconButton`'s own `:focus-visible` ring: it appears on keyboard focus and **never after a mouse click** — the kit browser witness (focus via keyboard: ring present and `:focus-visible` matches; click afterwards: no ring, `box-shadow: none`) is ported as a DC-2 test (§10.2). The control is placed inside the header's toggle slot, clear of header text at every width by layout (§5.1), not by a clearance offset. No `foreignObject` mounting or sizing pass exists (DH-13). The control never renders a text "+" or "−" glyph, never exceeds the header height, and takes the header's tone tokens. Plus/Minus here are DS control glyphs (Lucide via `IconButton`); DC-D7's ban on Lucide inside diagram cards covers the pictogram slot only.

### 7.2 State changes, chips bar, Expand all / Collapse all

- Activating a toggle emits the §10.11 intent: `{ "event": "intent", "name": "collapse" | "expand", "target": "<container entity id>", "context": { "group": "<grp.… id>" } }`. The component mutates no geometry. The host answers with a freshly laid-out `ViewDocument` (§7.3) and the renderer replaces geometry wholesale — stale boxes are never animated into place. While a re-layout is in flight the host surface exposes `aria-busy` (the kit figure's contract) and the toggle that initiated it keeps focus; on completion focus returns to that toggle (the kit `setDetail(…, focusId)` behaviour, ported as host/figure behaviour).
- **`DiagramZoneFoldBar`** (chips bar): one chip per foldable zone in the current view, in document order, each chip a DS `Button size="sm" variant="secondary"` showing the zone title with a `Plus`/`Minus` icon and `aria-expanded`. It sits above the canvas (host/figure-placed), scrolls horizontally on narrow viewports (the kit `mobile-frame-controls` shape), and emits the same `collapse`/`expand` intents as the in-frame toggles. Chip labels are host-supplied localisations of (state, title); the bar holds no fold state of its own.
- **Expand all / Collapse all** are host/figure controls with host-supplied labels (for example « Tout déplier / Tout replier », "Expand all / Collapse all"). Semantically they are bulk applications of the per-zone transition over every foldable zone in the view, delivered as one host layout pass (one replacement `ViewDocument`), not as N sequential re-layouts. Their disabled states derive from the view state (Expand all disabled when nothing is collapsed, and conversely), as in the kit figure.
- **Initial state.** The initial fold set is **data** (§7.5): the host supplies it in the first `ViewDocument` (for example the HRPN per-scene defaults, or all-collapsed for a first presentation of the governance scene — owner: « a la premiere présentation, laisse tout replié »; the kit sentropic figure initialises its collapsed set to all groups, the HRPN figure to `defaults.js`). A component defaults nothing by itself; a host may restore a persisted view state instead, only through the `ViewDocument` it supplies.

### 7.3 Engine: what runs the reflow in the DS

**Decision (DC-D5): the DS engine is `packages/diagram-canvas`.** A fold is a layout call, not a component behaviour:

1. Input: the `SemanticDocument`, the injected `TextMeasurer` (with the card roles of §7.4), `targetWidth`, the collapse input — `layoutDocument` gains `options.collapsedContainers?: readonly EntityRef[]` (semantic **container entity** ids, nothing else), exactly the L-R15(c) engine input — plus the generic-scene options of §7.5 (`layoutTree`, `routingRelaxation`). This input does not exist at the measured base (§2.4): implementing it is part of lot DC-2 (engine side), including the L-R15(c) semantics: a collapsed container removes its descendant entities from the drawing (no reserved empty box), keeps its own occurrence at the collapsed size (460 × 200, §6.2 — L-R15(c)'s "header only" size is superseded for zones by the frozen card size, §16), re-runs placement, docking, routing and label placement on the collapsed graph in the same call, records one `VisualGroup` per container with `collapsed` set, lifts incident relations (one end hidden: drawn to the collapsed container's rectangle; both ends hidden in the same container: not drawn; ends in two different collapsed containers: container-to-container), restores a descendant's recorded flag when an ancestor re-expands, and reproduces the pre-collapse canonical geometry exactly on re-expansion.
2. Output: one replacement `ViewDocument` (occurrences, routes via `relationRoute`, groups with collapse state, camera preserved unless the host refits). Determinism is the engine's existing contract: same document + same collapse input + same §7.5 options ⇒ same canonical bytes (`serialiseView`), independent of record insertion order.
3. Edges route in the gutters between cards, along the frame, or outside it; a route never reserves empty height inside a zone (frozen spacing rule). The routing, docking and label rules are L-R1 to L-R14 as implemented by `diagram-canvas`; fold adds obstacles (the collapsed card box is an ordinary obstacle rectangle), it does not add a routing mode. The relaxation of §7.5 changes which crossings are *accepted and reported*, never the obstacle rules: no route passes through a card or a header in any mode.

`packages/graph` is not the fold engine (it renders graphs; it does not implement L-R docking/routing), and xyflow is never a layout engine here (§8.1). ELK (`elkjs`) is not adopted: the kit vendors it for study layouts, the L8 amendment records "allowed and not adopted", and no DC lot introduces it.

### 7.6 Legend zone and the generic scene figure

**Legend zone.** A scene that carries a legend declares one more container (the kit's `LEGEND`: kicker `HRPN`, title « Legend », subtitle « Card tints and link styles of this scene ») holding one child per tint used by the scene, plus a managed-service entry (no tint) and the link styles (solid; dashed when the scene has dashed relations). Legend *texts* (tint legend paragraphs, category labels) are consumer data (§7.5).

**Generic scene figure — `DiagramSceneFigure`** (`ds-proposition`, from `hrpn/GovernanceSceneFigure.svelte`). One reusable figure component, exported from the barrel (§5.6), that renders any scene the engine can lay out:

- Props: the scene identity and its laid-out model (a `SemanticDocument` + current `ViewDocument`, or a host-resolved scene record carrying both), `defaultFolds` (initial collapsed ids, data — §7.5), `legend` (whether the supplied scene's legend zone is included; the figure includes/excludes it in the document it lays out, it does not draw a legend itself), `title` / `label` (host-supplied heading and figure label), `compact` (figure chrome density), and host-supplied localised strings for every control (zoom, Expand all / Collapse all, viewer, chips). - The figure owns no model: fold state lives in the `ViewDocument` it is given and in the layout passes it requests (§7.2 events); a second figure over the same documents shows the same folds. The consumer page chrome around it (captions, sources, previous-view switcher, dossier annotations) is not part of the component.

`DiagramSceneFigure` is delivered by lot DC-3 (§12) together with the xyflow nodes, because the switch-over (§14) replaces whole figures, not isolated cards.

### 7.7 Performance contract (frozen budget)

- **No continuous work at idle.** After load and after any fold settles, the card/zone/figure subtree performs no periodic work: the §10 performance witness (10 s idle window, the kit thresholds: idle task < 100 ms, idle script < 10 ms, zero animation-frame callbacks, zero resize-observer callbacks attributable to these components, bounded heap) must pass. No polling timer, no standing `ResizeObserver` on card content (fixed size makes one unnecessary), no route recomputation without a state change. The kit figure's frame-control sizing observer (DH-13) has no DS equivalent to exempt: the toggle needs no observer.
- **Worst interaction < 1.8 s.** Every fold interaction — single toggle, chips-bar toggle, Expand all, Collapse all — completes (state visible + `aria-busy` cleared) in under 1800 ms, measured over **600 interactions** across the acceptance scenes and **240 stress toggles** (the kit stress pattern: 120 per language on the central scene), on the §10.2 browser matrix. Timeouts are never raised to make a slow interaction pass: the 1800 ms bound is the test timeout as well as the assertion, as in the kit browser checks. A fold that cannot meet the budget on an acceptance scene is a lot failure, not a budget renegotiation. Relaxed routing (§7.5) is inside this budget: the HRPN build measures 30–300 ms per non-prepared fold on the acceptance scenes, and DC-2/DC-3 re-measure it in the browser harness.
- Reflow is synchronous with the layout call: no intermediate geometry (overlapping or half-moved boxes) is ever painted as a settled state; `aria-busy` covers the in-flight interval.

## 8. xyflow nodes, standalone use, graph embedding

### 8.1 xyflow (Svelte Flow) node forms

For each component, a node wrapper in the xyflow subpath (`ds-proposition` names, lot DC-3): `DiagramCardNode` and `DiagramZoneNode`, exported from `@sentropic/design-system-svelte/diagram-nodes` (own subpath, §5.6 rule — an app without xyflow loads no xyflow code). The wrappers render `DiagramCard`/`DiagramZone` unchanged inside the xyflow node element — a collapsed zone node therefore contains the atomic card, identically to the non-xyflow rendering; xyflow is the render and interaction layer fed by engine geometry, never a second layout engine (JSON render standard §10.11, carried over):

- Node `width`/`height` are the occurrence geometry from the `ViewDocument` (leaf and collapsed zone: 460 × 200; expanded zone: the laid-out rectangle). The wrapper sets xyflow's node dimensions from that geometry and reports the same box as its measured size: xyflow's internal measurement of the wrapper must equal the occurrence box within 1 CSS px, and any mismatch raises `node-size-mismatch` in the DC-3 harness rather than silently feeding a different size back to layout. **Measured size fed back**: hosts that let xyflow measure (rather than declaring dimensions) pass the measured box to the next layout call as the node's footprint input, so placement, docks and routes are computed on the rectangles actually drawn (§10.6 layering rule).
- Dragging never writes geometry directly. Where the host enables editing, drag end emits the §10.11 `proposal` event (`move-occurrence` with `geometry` placement only; `port`/`waypoints` placements are forbidden in a proposal) and the host answers with a freshly laid-out `ViewDocument` whose geometry wins on any conflict. Hover, pan and zoom emit no event.
- If xyflow fails to load, the host renders the static SVG form (JSON render standard §10.12) for the same geometry instead of a blank surface.

### 8.2 Handles

Two endpoint kinds, per §10.11 of the JSON render standard (which DC-3 implements without change):

- **Port endpoint:** one handle per `PortOccurrence` — side from `side` (`north/east/south/west` mapped to xyflow `Position`), position along the side from `anchor`, handle id encoding the port occurrence id.
- **Entity endpoint (no port):** one handle per relation end, derived from the endpoint's entity occurrence and the first (source) or last (target) point of `relationRoute(view, occurrenceId)`: side is the rectangle side containing that dock point, position is read from the dock coordinates, id is `<occurrenceId>#source` / `<occurrenceId>#target`. Deriving handles from port occurrences alone is forbidden (the §15 witnesses of the JSON render standard carry zero port occurrences).

Handle presentation follows the radar origin: handles are invisible (`opacity: 0`, `pointer-events: none`) in the reading surface and become connectable only in a host-declared connect mode; the centre handle (anchor 0.5, L-R1) is an ordinary handle. The radar node's full slot grid (4 sides × 10 slots × target/source) is the *origin* contract of one application, not the DS contract: DC-3 implements the two-kind derivation above, which reproduces the docked geometry without inventing undocked slots (§16, LR16-C6).

### 8.3 Standalone use

Outside xyflow, `DiagramCard` and `DiagramZone` render from props alone (§5.1/§6.1) at the same token geometry: a documentation page, a dossier panel or a graph side panel hosts them with no canvas, no layout call and no `ViewDocument` (the host supplies `collapsed` and content directly). Standalone rendering is pixel-identical to the in-diagram rendering for the same props (asserted in DC-1/DC-2 by rendering the parity corpus standalone and in a scene) — including a standalone collapsed zone, which is a standalone `DiagramCard` plus its toggle. The fold toggle in standalone use emits the same intent shape with the standalone zone's id; a host that cannot reflow may leave `toggleLabel` unset, rendering the zone non-foldable (§6.5).

### 8.4 Embedding in graphs

The components are DOM components. In `packages/graph` (WebGL) hosts and in mixed canvas hosts, cards and zones embed as DOM overlays anchored to graph node positions (the host projects graph coordinates to the overlay plane; the card box stays 460 × 200 card px at the overlay's scale). No WebGL re-implementation of the card is specified or permitted (a second rendering of the same card would break DC-D8 parity). A graph host that cannot overlay DOM renders the static SVG form of the same geometry (§8.1 fallback rule).

### 9.1 Family contract (frozen)

One family, drawn identically in cards and zones (leaf, collapsed and expanded alike), at the 70 px icon box:

- **Geometry:** `viewBox="0 0 64 64"` (64-unit viewBox). Base diamond (canonical, from the validated #711 render): `M8 53L32 44L56 53L32 62Z`. Every glyph keeps this base, this viewBox and this layer order; a glyph that needs a different base is a new family, not a variant. - **Layers, in paint order:** (1) `base` — the diamond, fill = info accent at 18 % over the card surface; (2) `face` — the glyph face path, fill = info accent at 75 % over the surface, stroke = info accent, stroke-width 1.5, round joins; (3) `line` — the glyph detail path, no fill, stroke = surface colour, stroke-width 2.5, round caps/joins; the `dark` line variant strokes in the info accent instead (the radar `join`/`graph`/`network` case, the kit `link` flag). - **Text-bearing glyphs:** the radar set carries optional centred text (for example `S3` at 13 units, weight 750, surface fill). Text inside a pictogram is part of the glyph asset, never host-supplied content, and never localised.

## 10. Pixel parity and geometry checks

### 10.1 Principle and references

Parity is a **test**, not an intention: DC-1/DC-2/DC-3 each ship a failing-first parity harness, and a lot is not done while its parity items are red. Two comparison layers, both required: (a) **geometry** — boxes compared numerically (headless, no pixels); (b) **pixels** — raster comparison on the same boxes. Geometry catches drift pixels hide at small sizes; pixels catch paint (colour, stroke, glyph) drift geometry cannot see.

References, by subject (DC-D8):

| Subject | Reference | Note |
| --- | --- | --- |
| Atomic card (leaf) | Portable render at `4138a0ec` (sha256 in the header), central-scene card corpus | Unchanged from r1. |
| Expanded zone (header, rule, frame) | Portable render at `4138a0ec`, same corpus | Unchanged from r1. Deviations only as listed in §15. |
| **Collapsed zone** | **The DS `DiagramCard` render for the same kicker/title/subtitle/footer/icon/tone, with the toggle in its slot and the subtitle centred per §6.2.1** | The #711 collapsed frame (460 × 272, header + centred subtitle in a frame area) is **not** a reference (DIF-01). ### 10.2 Visual parity test (method)

Following the kit browser-check matrix shape and the dossier host-pair precedent (0.5 % of pixels differing):

1. **Fixture extraction.** At test time (never as a shipped copy), the harness extracts the portable reference from the pinned commit: `git -C <sentropic> show 4138a0ec…:docs/governance/governance-r11-portable.html` (sha256 asserted equal to `831cbdee…` before any comparison; a mismatch aborts the run as a fixture error, not a test failure). Kit-side fixtures, where a lot needs them, are read by path from the pinned governance-kit (§2.2.1) with the same hash-assert-then-use rule. The DS-side corpus is the same FR/EN field set rendered by the portable's central scene: every card field and zone header of that scene, transcribed once into DS fixtures (a `SemanticDocument` + view state per fold state: all-collapsed, all-expanded, and the mixed folds the kit browser run exercises), committed in the DS test tree with their source (scene id + field) recorded per fixture. For collapsed states the corpus pairs each zone fixture with its atomic reference fixture (same fields, toggle present, centred subtitle), generated from the same transcription — the pair, not the portable frame, is what DC-2 compares. HRPN scenes (Appendix C) are *additional* acceptance scenes (§12) under §10.1.
2. **Rendering.** Headless Chromium (the repository's existing `puppeteer-core`/`playwright-core` + system Chromium shape; no new browser dependency). Both renders at 100 % and 300 %, in light and dark, FR and EN. The DS render runs standalone (§8.3), in a laid-out scene, and (DC-3) in xyflow and in `DiagramSceneFigure`; all forms are compared.
3. **Fonts (blocking).** Same font stack and sizes on both sides: the DS side resolves `--st-font-sans` to the same Inter stack the portable embeds. The test environment must provide Inter (the host's installed font); if Inter is absent the run is `unverified` for pixels and reports `source-gap: font` — it never passes on a fallback stack and never embeds the OFL subset into the package to force a pass. Text measurement for layout (§7.4) uses the same stack's measured advances, versioned (`measurerVersion`) so a font change invalidates memoised layouts (§7.4).
4. **Tolerance.** Boxes (card, zone frame, icon box, header text block, rule, footer, body block, toggle slot) equal within **1 CSS px** per edge. Pixels: at most **0.5 % of pixels differing** per compared box (per-channel threshold set at DC-1 and recorded in the harness; anti-aliasing edge pixels are counted, not masked out — a harness that excludes edges to pass is a defect). Full-string presence: every fixture string is found complete in the rendered text (no ellipsis character `…` introduced by rendering, no clipped glyph box) — the 720-field zero-ellipsis corpus shape of the kit checks, re-run on the DS corpus in both leaf and collapsed forms. Collapsed-specific assertions: subtitle block centred horizontally and vertically inside the body area within 0.02 px (§6.2.1), 16 px side margins inside the 16 px inset, per-line centring with letter/word spacing equal to the card body's (no justification), toggle slot box equal to the `IconButton` box, and header/body/rule/footer boxes equal to the atomic reference's for the same fields.
5. **Deviations.** Each §15 deviation (collapsed 200 vs 272, footer pin at all body counts, body glyph at 14, single non-scaling rule, token dark scheme) has its own assertion against the frozen value and is **excluded** from the portable box comparison by name in the harness, with the portable's measured value printed in the report. An exclusion not listed in §15 fails the run. Collapsed portable frames are excluded wholesale under DIF-01 (reported with their 272 height), never partially compared.
6. **Contrast.** The resolved-token matrix of L-R17(b) (every shipped theme × light/dark × tone: detachment ≥ 3:1 by fill or qualifying boundary, primary text ≥ 4.5:1, secondary/detail ≥ 4.5:1 on the fill) is computed on the DS token values, plus the kit `contrast()` browser measurement (text ≥ 4.5, secondary ≥ 4.5, boundary-vs-fill ≥ 3) on the parity scenes. The kit card's local secondary override (`#52656b`) is not reproduced; if the semantic secondary fails a row, the theme token is the fix (§5.5).

### 10.3 Geometry checks (equivalent to the kit geometry checks)

## 11. Editable cards (Tiptap-style) — gated on RT-1

This section is specified in full and implemented only by lot DC-4, which **cannot start before RT-1** (the Svelte rich-text adapter, rich-text specification §12) passes its gate (DC-D9). At the measured base RT-0 is merged and private; RT-1 is **under way since the owner GO of 2026-10-22** and has not yet passed its gate (§2.4). DC-4 adds no editor of its own and no fallback editor.

### 11.1 Which fields edit, and through what

In an editing host, each text slot of `DiagramCard` and the header slots of `DiagramZoneHeader` become inline-editable in place (no modal, no separate form): **kicker, title, body lines and footer** for the card; **title and subtitle** for the zone (the zone kicker is package identity, §6.3 — its editability is open question Q1, §17; until answered, DC-4 ships the zone kicker non-editable and the card kicker editable). Editing uses the rich-text editor component (`@sentropic/design-system-svelte/rich-text-editor`, profile P0 `focus.markdown.p0@1`: paragraphs with bold/italic/inline-code; everything else preserved) mounted on demand for the active field only, under the rich-text specification's controlled contract: value in (`RichTextDocument` projected from the field's current string), complete document + gesture provenance out, opaque block identities carried by the host adapter, no diff computed in the DS, external updates surfaced never overwritten, no network, language-free with injected messages and the `⟦untranslated:…⟧` marker.

Field ↔ editor projection (`ds-proposition`, fixed here): a card field is a single-field `RichTextDocument` whose blocks are the field's lines (body: one block per body line, in order; kicker/title/footer/subtitle: one block). The projection is derived from the profile attribute strings (§4.2) by the host adapter; the card component itself holds no `RichTextDocument` when not editing. For a collapsed zone, editing targets the zone's fields (title, subtitle, footer) through the card it renders: the editor mounts inside the `DiagramCard` instance, but the proposal is issued against the **zone** entity (§11.2) — collapsing or expanding during an edit keeps one draft on the zone's field, never two drafts on the card-shaped and header-shaped renderings. Multi-paragraph field content beyond the field's line structure is preserved-block content under P0 and renders non-editable in place, exactly as the rich-text profile prescribes.

### 11.2 What an edit emits

A completed editing gesture (the rich-text component's single `onChange` for that gesture) is converted by the host adapter into a diagram-core transaction and emitted as a §4.6 `proposal` event:

```json
{ "event": "proposal",
  "transaction": {
    "commandId": "<host-allocated>",
    "baseRevision": 0,
    "commands": [
      { "kind": "update-entity-attributes",
        "entity": "entity:<id>",
        "attributes": { "footer": { "kind": "text", "value": "service: Sentropic" } } }
    ] } }
```

Rules: one proposal per completed gesture, carrying the complete new field value(s) for the edited entity (never a character diff — the Focus per-paragraph diff, where a Focus host needs one, is computed host-side by `@sentropic/focus/editing` against its retained baseline, as the rich-text specification §5.3 prescribes; the diagram host's equivalent is its own command application). The host applies the transaction with compare-and-swap on `baseRevision` (diagram-core `applyTransaction`: refusal returns diagnostics, including `revision-conflict` and profile refusals such as `text-too-long`), then supplies the new `(SemanticDocument, ViewDocument)`; the component re-renders from it. A refused proposal leaves the displayed document untouched and the local draft preserved in the still-mounted editor (host keeps it mounted and shows the refusal through its own diagnostics surface); the component applies no silent winner. Overflow after an edit (§5.4) is re-measured on the new value: an edit that makes a field overflow raises `card-overflow`/`zone-overflow` on the next render and the host may refuse or accept-with-diagnostic under its own policy — the editor never truncates the field to fit (P0 has no card-length concept).

### 11.3 Non-editing hosts and states

`editable={false}` (or the host's viewer/locked state) renders every field as static text with the editor never mounted: typing, paste, drop and mutation shortcuts are inert because no editor exists to receive them (the rich-text viewer/locked rule, carried over). Switching `editable` takes effect without remounting the card (only the active field's editor mounts/unmounts). Locale/theme changes during editing follow the rich-text invariants (no remount, no identity change, caret/selection preserved). Unmount destroys the editor with no surviving listener, observer or pending capture (rich-text §5.9, asserted by DC-4's tests).
