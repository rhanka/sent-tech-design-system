## 1. Question and scope

### 1.1 The question

The owner asks for the reverse engineering of every editable Tiptap element in Sentropic, "comme le templater de sentropic ou on l'utilise", toward DS parity (`owner-verbatim`, header). B1 answers, at STUDY rung:

1. What editable surfaces exist in Sentropic today, measured — every consumer of `<TipTap` and `<EditableInput`, plus every other `contenteditable` or rich input — with editor features, host behaviours, data formats and collaboration hooks per surface (§2)?
2. What can a user observably do on each surface (§3)?
3. For each behaviour, what is the parity verdict against the FE-2 editor as specified at pin `ebd0812f` (RT-0 code partially conformant, RT-1 as specified): already covered, covered by a later RT lot, needs a new DS capability, or stays app-side (§4.1)?
4. How can iso-behaviour between the Sentropic editor and the DS editor be shown without copying code (§4.2)?
5. Which choices should carry the work, on two separate axes — Axis 1: (A) DS-delivered named packs under versioned profiles versus (B) host composition from a closed DS catalogue (open slot rejected); Axis 2: one editor everywhere (C-monolith) versus a small family of presets (C-family) (§4.3) — and what lots, gates and open questions follow (§5, §7, §8)?

The collaborative sentence of the owner request ("prévoir l'édition concurrente et le lock", "peut-être intégré nativement") and the spreadsheet sentence ("éditeur type gsheet comme celui d'odoo") are B2 and B3. B1 inventories the lock, presence and SSE hooks Sentropic already wires around its editables (§2.9) because the parity map must classify them, and it states the B1→B2 interface (§6.2). It does not design concurrent editing, and it does not design a grid.

### 2.4 The core: `TipTap.svelte` measured

File: `sentropic:ui/src/lib/components/TipTap.svelte` (227 lines), Svelte 4 style (`export let`, `createEventDispatcher`).

- **Construction.** `new Editor` on mount with `editable: !disabled` (`sentropic:ui/src/lib/components/TipTap.svelte:75`). Extensions, in order: `StarterKit.configure({ bulletList: false, orderedList: false, listItem: false, heading: false })` (`sentropic:ui/src/lib/components/TipTap.svelte:80`), then `BulletListWithClasses`, `OrderedListWithClasses`, `ListItemWithClasses`, `HeadingWithClasses` from the Tailwind module, then `Markdown` (`tiptap-markdown`), then `Placeholder.configure({ placeholder, showOnlyWhenEditable: true })` (`sentropic:ui/src/lib/components/TipTap.svelte:94`). Only those four StarterKit extensions are disabled; every other StarterKit default stays enabled. The exact default set (which marks, nodes, history, drop/gap cursor behaviour) is defined by `@tiptap/starter-kit@3.31.3`, not by this repository, and was not read from an installed copy in this session: `source-gap` U-B1-1 (§2.13). What the repository itself guarantees is narrower and sufficient for the parity map: paragraphs, text, headings 1–6 with Tailwind classes (`sentropic:ui/src/lib/extensions/tailwind-classes.ts:41`), bullet/ordered lists with Tailwind classes (`sentropic:ui/src/lib/extensions/tailwind-classes.ts:12`), Markdown load/save through the bridge, and a placeholder. Any finer claim (for example strike, blockquote, code block, horizontal rule, link handling) must be qualified on the final bundle, exactly as FE-2 §6.5 requires for its own bridge.
- **Value out.** `onUpdate` reads `editor.storage.markdown.getMarkdown()` and dispatches `change` only when the result differs from `lastValue` (`sentropic:ui/src/lib/components/TipTap.svelte:100`). There is no Tiptap JSON, HTML or ProseMirror position in the outward contract: the wire is a Markdown string.
- **Value in (focus guard).** A reactive watcher compares `value` to `lastValue` (`sentropic:ui/src/lib/components/TipTap.svelte:44`). While the editor is focused, an incoming value only updates `lastValue` (the edit in progress wins), except when the processed value is empty, which forces a reset (`shouldForceReset`, `sentropic:ui/src/lib/components/TipTap.svelte:47`) so a parent clearing the field after send still clears the editor. Otherwise `setContent` runs with the selection saved as raw ProseMirror offsets `{from, to}` and restored when still in range (`sentropic:ui/src/lib/components/TipTap.svelte:56`). This offset-based restore is the Sentropic capital FE-2 generalises to block-identity anchoring (FE-2 §5.6 rule 4); the two are not the same mechanism (§4.1).
- **`forceList`.** Three cooperating mechanisms, all functional (FE-2 §2.3 already classifies them so): `ensureListMarkdown` rewrites non-list lines into list Markdown before mount and on external updates (`sentropic:ui/src/lib/components/TipTap.svelte:25`, using `markdownToArray`/`arrayToMarkdown`); a `transaction` hook re-applies `toggleBulletList()` whenever the caret leaves a `listItem` (`sentropic:ui/src/lib/components/TipTap.svelte:112`); a capture-phase `keydown` listener blocks Tab and Ctrl+Shift chords and rewrites Enter on an empty `listItem` to `splitListItem` (`sentropic:ui/src/lib/components/TipTap.svelte:136`, registered at `:172`). Net effect: the document cannot leave list structure, and Enter/Tab semantics differ from a prose field. P0 has no list node, so none of this has a DS equivalent today (§4.1).
- **Styling coupling (not carried over).** The Tailwind extensions only override `renderHTML` to inject classes and inline padding (`sentropic:ui/src/lib/extensions/tailwind-classes.ts:12`); component CSS hides the empty trailing paragraph after a list and zeroes trailing margins (`sentropic:ui/src/lib/components/TipTap.svelte:203`). FE-2 themes through `--st-*` tokens instead (FE-2 §5.8); the class injection is app presentation, not editor behaviour.

### 2.5 The wrapper: `EditableInput.svelte` measured

File: `sentropic:ui/src/lib/components/EditableInput.svelte` (955 lines). This is the business wrapper FE-2 §10 rules must stay in Sentropic; B1 inventories it to draw that line precisely.

- **Three modes, one contract.** Props include `value`, `markdown`, `apiEndpoint`, `saveDelay`, `placeholder`, `disabled`, `locked`, `changeId`, `fullData`, `fullDataGetter`, `originalValue`, `references`, `forceList`, `multiline` (`sentropic:ui/src/lib/components/EditableInput.svelte:9`). `markdown` selects the Tiptap branch (`sentropic:ui/src/lib/components/EditableInput.svelte:676`); otherwise `multiline` selects `<textarea>` (`sentropic:ui/src/lib/components/EditableInput.svelte:615`) or `<input>` (`sentropic:ui/src/lib/components/EditableInput.svelte:634`). - **Autosave.** Default delay is the shared constant `AUTOSAVE_DEBOUNCE_MS = 200` (`sentropic:ui/src/lib/constants/autosave.ts:1`, imported at `sentropic:ui/src/lib/components/EditableInput.svelte:7`). Edits set `hasUnsavedChanges = (newValue !== originalValue)`, register in `unsavedChangesStore` under `changeId` when an endpoint exists, and schedule `saveWithBuffer` (`sentropic:ui/src/lib/components/EditableInput.svelte:87`, Markdown path at `:231`, plain path at `:198`). `performSave` builds the payload from `fullDataGetter()` when supplied, else `fullData`, else `{ value }`, with a guard that a single-primitive payload always carries the latest edited value, then `apiPut(apiEndpoint, payload)` (`sentropic:ui/src/lib/components/EditableInput.svelte:132`, call at `:163`). The saving indicator appears only after 1 s of saving. None of this — debounce, `apiPut`, store, flush — is editor behaviour; FE-2 §5.5 forbids `onSave`/autosave semantics in the DS component, and §4.1 classifies the whole block as stays-app-side.
- **Lock.** `isLocked = Boolean(locked || disabled)` (`sentropic:ui/src/lib/components/EditableInput.svelte:32`) gates every mutation entry: `toggleEditing`, `saveWithBuffer`, `performSave`, `handleInput`, `handleTipTapChange` and `saveImmediately` all return early when locked, and the Tiptap branch receives `disabled={isLocked}`. FE-2 keeps exactly this much in the DS (`editable`/`disabled`, RED 1) and leaves *why* a field is locked (role, object lock) to the host (§2.9).
- **Citations `[N]` — decoration, not a node.** The live mechanism is DOM post-processing over the rendered editor DOM: `processReferencesInTipTap` walks text nodes of the rendered `.ProseMirror` element and replaces `[1]`, `[2]`, … with `<a href="#ref-N">` elements built by `createReferenceLink`, re-run after updates and value changes (`sentropic:ui/src/lib/components/EditableInput.svelte:408`, `:428`, triggers at `:567`); clicks are intercepted by capture-phase delegation that prevents navigation and smooth-scrolls to the target (`sentropic:ui/src/lib/components/EditableInput.svelte:272`). B1 therefore records citations as a host decoration behaviour, not as an editor node/mark (§4.1 gives the parity consequence). **What is not proven:** that the literal `[N]` text survives decoration unchanged in the wire. The absence of the custom Mark does not show that the DOM mutation stays outside the ProseMirror document: `processReferencesInTipTap` replaces rendered text nodes directly (`textNode.parentNode.replaceChild(fragment, textNode)`, `sentropic:ui/src/lib/components/EditableInput.svelte:558`), and the resolved StarterKit carries `@tiptap/extension-link` (`sentropic:ui/package-lock.json:2283`), whose parsing/serialisation of bracket-adjacent text was not read in this session. ### 2.9 Collaboration hooks as observed in Sentropic (inventory only; design is B2)

B1 records these hooks because every parity verdict must say where they live. Their design is B2's file; nothing here proposes a DS collaboration feature.

- **Roles and the viewer rule.** Workspace roles are `viewer` / `commenter` / `editor` / `admin` (`sentropic:spec/COLLAB.md:19`). Mutations are forbidden for `viewer` (403) (`sentropic:spec/COLLAB.md:336`); inline editors are locked for viewers with no typing and no autosave (`sentropic:spec/COLLAB.md:346`). Pages project role plus lock state into `locked`/`isReadOnly` props: folder detail computes `isLockedByMe` / `isLockedByOther` from the lock snapshot and `isReadOnly` from the workspace scope (`sentropic:ui/src/routes/folders/[id]/+page.svelte:75`), matrix folds lock state into `isReadOnly` (`sentropic:ui/src/routes/matrix/+page.svelte:70`), dashboard and creation pages pass the read-only scope directly.
- **Object locks (code behaviour, documentary intent and host discipline kept apart).** Scope is object-level (`workspaceId + objectType + objectId`), stored in `object_locks` (`sentropic:spec/COLLAB.md:64`). API: fetch/acquire/release, request/accept/force unlock, presence record/list/leave (`sentropic:spec/COLLAB.md:70`), client in `sentropic:ui/src/lib/utils/object-lock.ts:31` (`LockObjectType` is `organization | folder | initiative`, `sentropic:ui/src/lib/utils/object-lock.ts:6`). Lifecycle: locks purge at API startup, when the holder has no SSE connection, and by periodic sweep emitting `lock_update` (`sentropic:spec/COLLAB.md:89`). UI: compact badge with overlapping avatars, "You are editing", unlock request by click, admin force-unlock inside the tooltip, presence shown for all roles (`sentropic:spec/COLLAB.md:97`). Three statements must not be merged. **(a) Code behaviour:** the mutation guard `requireLockOwnershipForMutation` (`sentropic:api/src/services/lock-service.ts:56`) returns without error when **no active lock exists** (`if (!lock) return;`, `:57`) and throws `409 { code: 'OBJECT_LOCKED', lock }` only when another user's active lock exists. The lock therefore does **not** by itself guarantee a single writer: a mutation with no lock held passes. **(b) Documentary intent:** `COLLAB.md:65` announces a TTL of "1 minute max, UI refresh every 30s"; the code sets a 60-second default (`DEFAULT_TTL_MS`, `lock-service.ts:23`) but applies only a 5-second **minimum** with no ceiling (`Math.max(5_000, ttlMs)`, `lock-service.ts:139`), so the documented maximum is intent, not an enforced bound. **(c) Host discipline:** single-writer behaviour in practice depends on the host acquiring the lock before editing and routing every mutation through the guard; that acquisition discipline is app-side (P15), and no CAS guarantee is attributed to the lock anywhere in this study. The actual concurrency guarantee at publication, where one exists, is the h2a FE-6 OCC/CAS discipline (B2 §2.4), not this lock.
- **Presence and SSE.** The existing `/streams/sse` channel carries `lock_update` and `presence_update` scoped to the current workspace (`sentropic:spec/COLLAB.md:114`, scoping rule at `:325`). Presence is recorded per object and listed as a snapshot; it carries user identity for display, never caret positions. There is no simultaneous-editing merge anywhere: the intended concurrency posture is "one writer per object, everyone else locked out, remote values merged at field granularity only when untouched" (§2.6), effective only under the host acquisition discipline of the previous bullet — the code guard alone passes mutations that hold no lock.
- **Unsaved-state coordination.** `unsavedChangesStore` (`sentropic:ui/src/lib/stores/unsavedChanges.ts:1`) collects per-`changeId` save functions so navigation guards can flush or block; it is app coordination, not editor state.

## 3. Observable behaviour — what a user can do, per surface

Only user-observable behaviour is stated here (no implementation mechanism). "Save" means the field persists without an explicit Save button; timing is the 200 ms debounce of §2.5 unless stated otherwise.

### 3.1 Markdown rich field (S1+S2a: templater text, score justification, folder context, matrix fields)

- Click into the text and type; paragraphs, headings and bullet/ordered lists render formatted while editing, with a placeholder when empty and editable. Bold/italic/code and other StarterKit formatting entered as Markdown or by keyboard appears formatted (exact set bounded by U-B1-1).
- `[1]`, `[2]` citations appear as blue clickable references; clicking scrolls to the reference entry instead of navigating. Deleting the bracket text removes the citation; the saved text still contains the bracket characters.
- Shortly after typing stops, the field saves by itself. A yellow marker/border shows unsaved work; a spinner shows a slow save. Navigating away flushes pending saves. A failed save keeps the unsaved indication.
- When a collaborator's newer value arrives while the field is untouched, the field updates in place. When it arrives mid-edit, the local text stays and remains marked unsaved (no silent overwrite, no merge inside the field).
- As viewer, or while another user holds the object lock, the same field shows formatted static text (templater) or an inert editor (other hosts): no caret editing, no save, including through paste and shortcuts (the observable half of the `COLLAB.md` rule).

### 3.2 Plain name/industry fields (S2b/S2c)

- Single-line fields size to their content; multiline name fields grow in height. Typing autosaves with the same unsaved/saving indications as §3.1. Values containing `[...]` are highlighted. Locked fields cannot be edited and do not save. On creation pages, no save fires until the entity exists.

### 3.3 Templater list field with `forceList` (S5)

- The field always shows a bullet list: pasting or typing plain lines turns them into bullets, and the caret cannot leave list structure. Tab does not indent, Ctrl+Shift chords do nothing, and Enter on an empty bullet creates another bullet instead of exiting the list. Deleting all bullets leaves an empty list editor (placeholder may be hidden behind the list chrome). Saving stores the items as separate list entries; the `references` list is never editable here.

### 3.4 Chat composer and message edit (S6, with S7/S8 fallbacks)

- Type a message with Markdown formatting; Enter-to-send and `@mention` completion are handled around the editor (the `@` menu lists workspace members and inserts the chosen member). Editing an existing message reopens its text with Cancel/Send. Sending clears the composer (a clear while focused still clears). While sending or without a session, the composer is inert.
- Without the rich snippet, the two fallbacks differ and must not be generalised into one behaviour. The comments `textarea` (S8) keeps Enter-to-send, mention completion, viewer/resolved gating and placeholders, with no formatting, and its disabled states genuinely forbid typing. The chat-ui plaintext composer (S7) keeps plain typing and placeholders, but: sending is disabled while sending or without session, typing is **not** actually forbidden in that state (only `aria-disabled` is set, §2.7), and mention completion is unavailable (empty floating layer). "The same actions work in plain text" is therefore false for S7 and is not claimed.

### 3.5 Settings and descriptor text fields (S10)

- Prompt, agent-description and config fields edit as plain text and persist only on explicit Save. The view-template descriptor edits as raw JSON with Save/Cancel; invalid JSON is refused at save. The workspace-override prompt is read-only until an override is created.

### 3.6 Non-behaviours (what the user never gets, at the pin)

- No formatting toolbar, slash menu, table/diagram/code editing UI, or `@` suggestion inside the Tiptap editor itself. No simultaneous co-editing: a second writer is locked out rather than merged. No offline queue beyond the unsaved flush: a failed `PUT` stays unsaved. No per-paragraph history or diff view in Sentropic; the per-paragraph edit return exists only in the h2a Focus contract, not in these surfaces.

#### 4.1.1 Special attention: the `references` extension

Three different things share the name, and the parity answer differs per thing: (1) the unused Tiptap Mark in `sentropic:ui/src/lib/extensions/references.ts:23` (no consumer, plugin returns `false`, no serialiser) — dead code, no parity owed; (2) the live citation decoration of §2.5 (DOM rewrite of `[N]` text, click-to-scroll) — host presentation over wire text whose stability across decoration is `unverified` (U-B1-7), App-side (P7); (3) the templater `references` *data* (title/url/excerpt lists rendered as link lists, `sentropic:ui/src/lib/components/TemplateRenderer.svelte:507`, supplied as the `references` prop) — host data, never editor content. The brief's premise "P0 has no such node" is therefore sharper than it looks: Sentropic has no live node either. Creating a DS citation node/mark now would invent a wire format (`[N]` would stop being plain text), break the Focus rule that a paragraph containing a link is preserved (FE-2 §6.2), and couple the DS schema to Sentropic's reference data. Recommendation R-B1-2 (§5) keeps citations as a host decoration for this increment. Two things must not be conflated. (1) **Guarantee status:** byte-identical round-trip of `[N]` text is a DS guarantee only for the undecorated editor; once a host decorates, stability is `unverified` (U-B1-7) until the decoration witness (decorate → type around the decoration → capture → remount, wire asserted at each step) passes in B1-L3. (2) **Safe decoration interface (to be defined; FE-2 §5.5 exposes none today):** decoration SHALL be applied outside the ProseMirror document — as a ProseMirror decoration / rendered-output transformation over the emitted document (the `renderMarkdownWithRefs` pattern over rendered HTML), never as a mutation of rendered editor DOM nodes; it SHALL be recomputed from the current document on each render, removed cleanly when the text changes, and it SHALL NOT create, delete or reparent document content, so capture and remount never see it. A host that cannot decorate under those rules keeps citations undecorated in the editor and decorated only in static rendering. The same discipline applies to the future host `forceList` wrapper (R-B1-3): its list-forcing transactions are host transactions over the DS editor's public surface, they must be re-witnessed under W2's per-editor expectations before S5 migrates, and no forcing rule may rely on mutating rendered DOM. If a concrete future need wants structured citations, it is a new versioned profile decision taken at that time (§8), not a B1 pack and not a standing question.

#### 4.1.2 Special attention: lists and `forceList` (FE-2 §6.4)

Lists are the largest real gap (P5+P6): four templater list **mount sites** plus incidental lists inside text fields. The four sites are layout variants of one renderer (§2.6): they count source mounts, not business fields — the number of list fields actually in use is a descriptor-and-corpus quantity, measured by the B1-L0 audit over descriptors and stored content, and no sizing in this study is derived from the mount count. Two gates must not be merged. The Focus gate (FE-2 §6.4: h2a codec/anchors evolve, new pin in both specs, joint FE-1/FE-2 witnesses) governs whether list items can carry Focus paragraph identities for the AI return. The Sentropic gate governs whether the DS offers an editable list profile at all for `apiPut`-saved fields. B1 proposes sequencing them independently (§7): Sentropic list adoption waits for a DS list profile qualified on its own corpus (W2), and Focus list editing waits for its own h2a evolution; neither green substitutes for the other. Until then, `forceList` fields stay on the Sentropic wrapper (P6) and text fields keep lists preserved — an observable narrowing (lists visible but not editable) that the adoption lot must state per field, never silently ship.

#### 4.1.3 Special attention: templater fields

The templater contributes the adoption order. Text fields (S4) are the RT-1 pilot: P1+P2+P7+P14 cover them with a host adapter that keeps buffers, sibling payloads, normalisation and autosave exactly where they are. Score justifications (S3) follow the same adapter with a different payload getter. List fields (S5) are blocked on P5/P6 and stay wrapped. `scores-summary`, `chart`, `component`, `child-list` and `entity-loop` need no editor (the loop renders locked print output today). Descriptor supply (`resolveViewTemplate`, cache) and the catalog JSON editor (S10) are untouched by editor parity. A "templater migration" therefore means the text-field class (four text mount sites, §2.6) plus the score-justification mount first — mount sites, not a count of business fields in use, which only the descriptor/corpus audit (B1-L0) can state — and never the descriptor system.

### 4.2 Differential parity witness design (iso-behaviour without copying code)

Goal: show that the DS editor and the Sentropic editor behave the same *observably* on the surfaces B1 claims as parity, without copying Sentropic code, fixtures derived from its source text, or its Tailwind classes. The design follows the RE precedents' differential harness (`ds:spec/SPEC_RE_XYFLOW_PARITY.md:350`, `ds:spec/SPEC_RE_BPMN_JS_PARITY.md:227`): scripted scenarios name the inventory rows they exercise, and coverage is the union over scenarios, checked mechanically.

- **Black-box boundary.** Both editors are driven only through public surfaces: mount with a value, dispatch real keyboard/clipboard/composition events, read the emitted value/document, the rendered DOM (roles, `data-paragraph-id`, preserved regions) and (Sentropic side) the `change` events / (DS side) `RichTextChangeEvent`s. No Sentropic source file, internal function (`ensureListMarkdown`, `processReferencesInTipTap`) or class name is imported, snapshotted or asserted. Sentropic behaviour enters only as *expected observable outcomes* recorded in scenario data (given/when/then over strings and DOM queries), written from §3.
- **Corpus (synthetic, provenance-stated).** Fixtures are newly written Markdown/plain strings covering: plain paragraphs, bold/italic/code mixes, hard breaks, headings, bullet/ordered/nested lists, blockquote, code fence, table, link/image paragraphs, `[N]` citations, identical twin paragraphs, CRLF/CR sources, trailing blank lines, empty field, whitespace/break-only paragraphs (FE-2 §6.6 cases), and hostile paste payloads (script, event handlers, `javascript:` links, remote images). Corpus header states synthetic provenance; real Sentropic exports, if the owner supplies them, join as an additional labelled fixture set at adoption (U-B1-4), never as copied code.
- **Witnesses.** W1 *Round-trip*: open/edit-nothing/close is byte-identical at block level on both editors; edit one middle paragraph and assert every neighbour, separator and preserved slice is unchanged (FE-2 RED 2 form). W2 *Lists*: list corpus mounts, edits, splits/merges items; passes only for the list profile, and until then must *fail as preservation* (lists visible, non-editable, byte-identical) — a green edit before the profile exists fails the witness. W3 *Paste*: each hostile and non-paragraph payload is inert or refused whole with document/selection unchanged and exactly one refusal signal (FE-2 RED 7 form). W4 *Concurrency/IME*: external update while focused/dirty/blurred/composing never overwrites local work, caret anchor (block + offset) survives clean updates, composition emits once and deferred capture returns composed text once (FE-2 RED 4/5 form, real Chromium). W5 *Lock/theme/locale*: viewer lock through typing/paste/shortcuts emits nothing and saves nothing; sentinel messages render with the `⟦untranslated:rich-text.<key>⟧` fallback; theme/locale switches preserve caret and scroll (FE-2 RED 1/8 form). Every W row is scored through the three-class matrix below, never as one shared expectation imposed on both editors.
- **Oracles independent of both implementations.** Expected Markdown is asserted as literal expected strings per scenario (not by re-running either bridge); Focus agreement, where claimed, is asserted host-side with the pinned `diffParagraphs` against a retained baseline (empty diff for unedited cycles), never by a DS-computed delta.
- **Three scenario classes, one expected result per editor (the witness matrix).** A single shared expectation for both editors is wrong wherever behaviour intentionally differs, so every scenario row carries a class and an expected observable **per editor** (Sentropic `TipTap.svelte` at the pin; DS editor at its specified surface): **(P) parity** — both editors must meet the same expectation (for example unedited round-trip identity at block level, locked inertness, no save on lock); **(D) intentional divergence** — each editor has its own stated expectation and both must hold (for example W3: Sentropic's StarterKit accepts list/heading pastes, the DS editor refuses them whole with exactly one `onUnsupportedPaste`; W4: Sentropic restores selection by raw offsets (`sentropic:ui/src/lib/components/TipTap.svelte:44`–`:68`) and lets the focused edit win, the DS editor anchors by `paragraphId` + intra-paragraph offset, defers capture during composition and surfaces local divergence as a conflict — `TipTap.svelte` has no paragraph identities, no deferred capture and no conflict surface, so no shared expectation may be written for those rows); **(G) DS-only guarantee** — only the DS column carries an expectation (representability flagging, `RichTextCaptureResult`, preserved-block byte identity under FE-2 §6.6), and the Sentropic column records `n/a (no such surface)` rather than a forced pass or fail. A scenario one editor cannot express yet (W2 before the list profile) is recorded as `preserved`/`unsupported` with the exact observable in that editor's column, not skipped and not scored against the other editor's expectation.
- **Gate form.** Each witness names its inventory rows (S1–S10, P1–P20) and its scenario class (P/D/G); the lot report lists, per editor, rows exercised, rows preserved, rows refused, with command output. The B1-L1 and B1-L3 gates (§7) consume exactly this matrix: a lot passes a witness only when every P row matches on both editors, every D row matches its per-editor expectation, and every G row matches on the DS side. Tamper control (precedent discipline): deleting or inventing a scenario row must fail the coverage check. No witness greps Sentropic source at runtime; the Sentropic side runs against its pinned build as a black box, or, where running it is impractical, against §3 expectations recorded as data with the pin cited. The second form is weaker and must be announced as expectation-parity, not execution-parity.

### 4.3 Options

Each option is judged on: effort, risk, licence, offline (no-CDN capability must remain possible), framework parity (Svelte/React/Vue/Angular, measured per stage, never claimed from types), fit with FE-2 (RT lots, P0 pin discipline) and fit with the h2a contract (no DS diff, no second return shape). Artefact size never outranks reactivity or atomicity of edits (owner rule).

The options separate two independent axes that must not be merged into one ballot: **Axis 1 — how new constructs are delivered** (Option A versus Option B, §4.3.1–§4.3.2), and **Axis 2 — how surfaces are shaped** (monolith versus preset family, §4.3.3). Presets and extensibility are decided separately: a preset is a tested surface configuration; a pack/catalogue entry is a construct-delivery mechanism. Either Axis-1 option can be combined with either Axis-2 shape, and the recommendation (§5) states one choice per axis.

#### 4.3.1 Option A (Axis 1) — DS-delivered named packs under versioned profiles

Shape: `packages/rich-text` grows DS-owned packs — a `lists` pack (`bulletList`/`orderedList`/`listItem`), later heading/blockquote/code packs — composed onto P0 behind named profile identifiers, delivered and released by the DS as new versioned profiles. Hosts select a finished profile; they do not compose constructs themselves.

- Effort: highest per construct, and the cost is intrinsic to the construct, not to the delivery shape: schema, identity carriage, Markdown serialisation, paste rules, representability analysis (FE-2 §6.6 test per new construct), the full RED list re-run, then re-qualification per framework adapter stage. Lists alone reopen the FE-2 §6.4 analysis. This qualification cost does **not** disappear under Option B; §4.3.2 prices it identically there.
- Risk: highest, and partly irreversible. Mutating `focus.markdown.p0@1` in place would break the pinned contract (codec segmentation, `assertParagraphText`, Appendix B pin); doing it correctly means a new versioned profile (`p1`), a new pin in both specs, and joint FE-1/FE-2 witnesses for Focus-bound fields. A DS-only green that the Focus codec refuses is a false parity claim (W2 is designed to catch exactly this).
- Licence/offline: clean (MIT Tiptap extensions only), offline preserved. Parity: qualification cost multiplies by four frameworks, paid centrally once per profile. Fit: contradicts FE-2 RT-D3 (P0 frozen, lists preserved until the gate) and the h2a boundary if rushed; legitimate only as a later, separately ratified profile evolution.

#### 4.3.2 Option B (Axis 1) — Host composition from a closed DS catalogue (open slot considered and rejected)

Shape: P0 stays frozen. Hosts compose the editor they need by naming constructs from a **closed** DS catalogue: a frozen union of DS-owned descriptors (pure data in `"."`, instantiated only inside `"./editor"`) resolved to a versioned `profileId`. Sentropic could compose lists when a list descriptor is qualified; another host composes nothing. This is the same construct catalogue as Option A with a different composition point — the applicable comparison is therefore not cost but governance: A couples every construct to a DS profile release that all hosts adopt together; B lets each host adopt a qualified construct on its own schedule, at the price of more composed-profile combinations to qualify and announce. The per-construct qualification cost (schema, serialisation, paste, representability, RED witnesses, per-framework stages) is identical in both options and is claimed in neither as a saving.

- Effort: lowest to first adoption (the pilot needs no new construct at all). Each later construct costs the same qualification as in Option A; what B saves is release coupling, not qualification.
- Risk and the open-slot rejection, with corrected objections. The **open** form — accepting live Tiptap `Extension` objects from hosts — is rejected on four demonstrable grounds: (1) **serialisation** — arbitrary nodes/marks escape the `RichTextDocument` wire, producing unserialisable content and FE-2 §6.6 failures with no owner; (2) **security** — paste and sanitisation guarantees (FE-2 §7) vary per host-supplied extension and can no longer be witnessed once for the DS; (3) **qualification** — the composed schema space becomes unbounded, so framework parity and the RED list become unmeasurable per composition; (4) **dependency control** — the MIT-only allow-list (FE-2 §9.2, no `@tiptap-pro/*`) becomes unenforceable at the DS boundary. One earlier objection is **withdrawn as inexact**: accepting extensions through `"./editor"` does not by itself contaminate the pure `"."` entry — contamination would occur only if live Tiptap types were placed in `"."`; pure descriptor data in `"."` with instantiation confined to `"./editor"` keeps RED-P's import graph intact, and the closed form is specified exactly that way. The closed form avoids all four retained objections: the descriptor union has no case for host-invented constructs, every catalogue entry carries declared serialisation, paste behaviour and representability handling before any host can select it, and the allow-list is enforceable by construction.
- Licence/offline: clean only in the closed form (catalogue is allow-listed; hosts bundle what they compose, no CDN). Parity: measurable only in the closed form (same descriptor set → same schema on every framework). Fit: preserves the P0 pin and the h2a boundary; the Focus profile remains the default composition.

#### 4.3.3 Axis 2 — One editor for every surface (C-monolith) versus a small family of presets (C-family)

These are two shapes for the surface layer, orthogonal to §4.3.1–§4.3.2; they are stated as one axis, not as a third delivery option.

- **C-monolith.** Every Sentropic editable — rich, plain, chat, settings — migrates onto the one Tiptap component with per-surface props. Effort looks cheapest (one migration) and is not: plain fields lose native form semantics and autosize chrome must be reimplemented inside a ProseMirror surface; the chat Enter/mention contract fights a document editor's Enter semantics; settings JSON fields gain nothing. Risk: maximises regression surface (all 24 sites change behaviour class at once) and forces one editor where no editor is needed. Licence/offline preserved, but parity measurement fails (behaviour differs per misapplied surface) and user value regresses (form fields, composer keys).
- **C-family.** One headless core (`packages/rich-text` `"."` + `"./editor"`) with a small preset family: `prose` (P0 paragraphs), `plain` (existing DS `Input`/`Textarea`, no Tiptap), `composer` (controlled string surface for chat, rich or plain rendering behind the chat shell), each preset a thin tested configuration, never a second editor implementation. Effort: one core plus three thin presets, each reusing an existing DS surface (`Input`, `Textarea`, `ChatComposer` shell) instead of reimplementing it. Risk: blast radius stays per preset and adoption proceeds field-class by field-class. Both shapes keep a single core, so the D23 "no second editor" rule holds; a per-framework reimplementation (FE-2 §4.1 option 3, already rejected there) is not re-proposed. Licence/offline/parity/fit: family preserves all four.

### 5.1 Why not the alternatives (one paragraph each)

Option A as the B1 vehicle spends the scarcest resource — profile qualification across four frameworks, gated by an h2a contract evolution B1 does not own — before the first field migrates, and it couples every host to one DS profile release. Option B in open form trades a small short-term saving for the loss of the demonstrable guarantees of §4.3.2 (serialisation, security, qualification, dependency control). The C monolith regresses the 7 plain sites and the chat key contract to save adapter code that the family reading shows is thin. The recommended combination keeps each of those costs where measurement puts it: core once, presets thin, constructs qualified once and composed by hosts, business logic untouched in the host.

### 5.2 Fit checks

Licence: MIT-only catalogue, no Pro/cloud, no copied code (behavioural reference only); LGPL estate code (including the B3 reference) never enters these packages. Offline: hosts bundle the composed editor; no CDN, no fetch, `connect-src 'none'` compatible (FE-2 §7/§8). Parity: Svelte first (RT-1), other frameworks by FE-2 stage gates with real vertical scenarios; the closed catalogue is what makes "same preset, same schema" testable on each framework. Reactivity/atomicity: one editor instance per field, per-block conversion only (FE-2 §13.3 invariants); no whole-document reparse per keystroke is introduced by presets or wrappers.

### 6.3 With h2a and Sentropic (hosts)

- **h2a / Focus:** consumed by reference at `98060bd0a` (Appendix B). - **Sentropic (FE-7 direction):** adoption is a host adapter inside `EditableInput`'s contract, preserving `apiPut` payloads, `fullDataGetter` sibling reassembly, normalisation helpers (`sentropic:ui/src/lib/utils/markdown.ts:38`), the unsaved store and lock projection bit-for-bit at the network boundary. Rollback per field is "render the previous wrapper", because the wire (Markdown/plain strings) never changes format during migration.
- **Representability gate before any save, unmount or field switch (blocking for adoption).** Keeping the current autosave of emitted strings is not sufficient. FE-2 §6.6 guarantees faithful live ⇔ capture ⇔ remount equality only for representable paragraphs; a flagged (non-representable) paragraph's captured wire may remount to different content or to no paragraph, and no host path may treat that remount as faithful. The host adapter SHALL therefore, for every migrated field: (1) read `representability` from each `RichTextChangeEvent` and from `captureDocument()`'s `RichTextCaptureResult` before any `apiPut` — a flagged draft is not saved as if it were the visible content; it stays in the live editor, keeps its unsaved indication, and is surfaced to the user through injected host messages as not-yet-savable, with the draft preserved; (2) never unmount or switch the field away from a flagged draft without an explicit host decision that keeps the live draft (keep the editor mounted, or block navigation through the existing unsaved-changes guard) — silently unmounting and remounting from the flagged capture is prohibited; (3) treat a later edit that clears the flag as the save trigger: once every paragraph is representable, the normal autosave path resumes and saves the then-current strings. This is host behaviour around the DS surface; the DS only reports the flag (once B1-L0c lands) and never transforms the draft. The gate is witnessed RED-first in B1-L3 (§7): save → remount must reproduce the visible content for representable drafts, and a flagged draft must survive a save attempt plus a field switch with its visible content intact in the live editor.
