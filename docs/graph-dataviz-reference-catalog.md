# Catalogue de références graphes, processing et applications

Date du relevé : **2026-09-15**. Mandat §§5/7. État : **M0 inventorié ; couverture M5 à réaliser**.

Ce catalogue décrit les capacités à reprendre avec le code Sentropic et des implémentations autonomes. Il n’autorise aucune copie de code tiers, installation runtime, intégration commerciale ou dépendance à ELK, Graphviz, JointJS, libavoid, MSAGL, Bryntum, Handsontable ou autres produits cités. Les noms servent de références de couverture. Les dépendances déjà présentes restent traitées par l’inventaire de migration, sans réécriture opportuniste.

Les noms `@sentropic/graph` et `@sentropic/dataviz-*` restent préservés. Le processing, les modèles, les moteurs de rendu, l’interaction, l’état inter-vues et les applications gardent des responsabilités distinctes.

## Résultat et traçabilité

- **21 algorithmes ELK**, **60 groupes d’options**, **286 entrées d’options (279 identifiants distincts)** : axes séparés ; groupes homonymes conservés grâce aux identifiants complets.
- **10 moteurs/entrées de layout Graphviz**, dont `nop` et `nop2` ; le guide d’écriture de plugins est exclu du décompte des moteurs.
- **186 applications/recettes JointJS**, avec les deux pages de catalogue suivies jusqu’à absence de lien suivant : 100 + 86 cartes. Les vedettes répétées ne sont pas recomptées.
- **15 entrées Sentropic actuelles** : vrais solveurs, wrappers et builders explicitement distingués.
- Le [catalogue JSON](graph-dataviz-reference-catalog.json) contient chaque identifiant, URL, source capturée, équivalent actuel, statut, clé de rapprochement, appartenance des options aux groupes et support annoncé par algorithme. Les SHA-256, dates UTC et en-têtes `Last-Modified` des réponses sont dans `sources`.

`partial` signifie capacité apparentée présente dans le périmètre M0, sans conformité au moteur tiers. `not covered` signifie qu’aucune équivalence n’est établie par les sources M0. Tous les items de couverture restent **planned**, y compris lorsqu’une primitive Sentropic existe. Les tests des moteurs tiers, la conformité des apps et l’exécution navigateur n’ont pas été effectués dans ce relevé.

Les clés **GD-M5-PROCESSING** et **GD-M5-APPS** sont des clés stables de rapprochement du programme, pas des UUID Track. Le présent catalogue n’effectue aucune écriture Track ; la liaison aux UUID relève du registre du programme.

## 2. ELK : axe groupes et options

Source : [index officiel des groupes](https://eclipse.dev/elk/reference/groups.html), [index des options](https://eclipse.dev/elk/reference/options.html). Les **60 pages de groupe ont été lues**. Le JSON conserve leurs options directes et sous-groupes, puis les 286 entrées d’options (279 IDs distincts) avec leur URL et les algorithmes qui les annoncent. Les domaines de valeurs, unités, interactions, valeurs par défaut et erreurs de chaque option restent à qualifier en M5.

Le nombre d’options directes peut être nul lorsqu’un groupe ne contient que des sous-groupes. Une option sans groupe explicite reste inventoriée. Sept variantes spécifiques aux algorithmes partagent un ID avec une option générale : `hierarchyHandling`, `spacing.individual`, `priority` et `layered.priority.shortness`. Leur clé inclut le chemin documentaire/scope ; elles restent distinctes. Les liens `*_option_entry_keys` conservent cette précision, en complément des IDs. Les groupes et algorithmes portant le même ID, par exemple `org.eclipse.elk.box`, sont distingués par le type d’entrée ; les groupes `spacing`, `compaction` et les variantes `whiteSpaceElimination`/`whitespaceElimination` ne sont pas fusionnés.

### Contrat de processing à qualifier

Les nouvelles capacités utilisent des snapshots versionnés du document et des vues, une projection de processing explicite, des contraintes typées et des phases composables. Les spécialisations métier émettent des contraintes et réutilisent ces phases. Le résultat doit fournir rectangles, ports, routes, labels, identités, métriques et diagnostics, avec pont de compatibilité vers `PositionFrame`.

Le lot M5 doit mesurer séparément placement généraliste (layered/Sugiyama, arbre, radial, force, stress, grille, packing, compaction, déchevauchement), routage (orthogonal, octilinéaire, courbe, évitement, ports, labels, self-loops) et contraintes/opérabilité (seed, déterminisme, incrémental, annulation, diagnostics). Le `metro` actuel ne couvre pas le routage octilinéaire. Le routage graphique simple actuel ne prouve pas l’évitement d’obstacles. Un résultat worker périmé doit être rejeté par révision avant d’écraser une modification récente ; la présence actuelle d’un worker ne prouve pas cette garantie.

## 6. Acceptation et limites restantes

- **Inventaire M0** : IDs uniques, aucun groupe homonyme fusionné, liens algorithme→options et groupe→options résolus, pagination JointJS entièrement parcourue, clés de rapprochement présentes à chaque entrée. Ces invariants structurels ont été vérifiés sur le JSON généré.
- **Processing M5** : chaque capacité doit avoir fixtures contraintes/cas impossibles, diagnostics, preuve seed/stabilité/incrémental, performance mesurée et annulation/révision worker ; documenter les sous-ensembles sans prétendre une équivalence universelle.
- **Apps M5** : chaque référence doit aboutir à une recette utilisant les APIs publiques, avec preuves clavier/focus/IME/a11y, thèmes, interaction, transaction/undo, persistance via ports et limites de parité entre frameworks. Une démo visible ne prouve pas sa conformité métier.
- **Statut** : le catalogue est livré ; les implémentations, la qualification sémantique détaillée des 286 options, les exécutions navigateur et les fixtures métier restent ouvertes. Aucune dépendance ajoutée, aucun code tiers copié, aucune écriture Track réalisée par ce sous-livrable.
