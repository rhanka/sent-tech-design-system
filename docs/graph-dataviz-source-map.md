# M0 — Correspondance des sources graph/dataviz vers le DS

Date : **2026-09-15**. Programme owner de rapatriement ; exécutant : **astra**. Périmètre : `@sentropic/graph` et les **cinq** `@sentropic/dataviz-*`, leurs exports publics et les capacités hors package déjà identifiées. Cette consolidation reprend les deux inventaires M0 préparés par le conducteur, puis complète leur granularité au symbole à partir des sources accessibles. Elle ne refait pas un audit fonctionnel général.

**Décision appliquée :** le DS devient la référence des bibliothèques ; **M1 conserve les noms des packages, les noms exportés, les modules d'implémentation, les signatures et comportements existants**. L'état inter-vues reste dans `@sentropic/dataviz-core`, avec ses quatre adaptateurs. Les couches de responsabilité indiquées ci-dessous ne sont pas des déplacements de code déjà effectués.

Les 495 exports core sont disponibles via cinq points d'entrée publics mais doivent toujours référencer **une seule implémentation canonique**. Angular expose deux composants, malgré sa grande surface transitive ; ce total ne signifie pas une parité des composants avec les autres frameworks.

Le fichier [graph-dataviz-source-map.json](graph-dataviz-source-map.json) contient **une ligne logique par couple package/export** avec origine et ligne source, valeur/type, destination publique, destination canonique, décision, responsabilité, clé principale Track et dépendance au core. La clé d'identité est `<nom-package>#<nom-export>`. Les manifests complets et leurs empreintes SHA-256 sont embarqués. Aucune ligne ne manque de destination, de décision ou de clé ; aucune identité de couple n'est dupliquée.

### Vérification reproductible

```bash
node docs/graph-dataviz-source-map.audit.mjs
```

Le script charge TypeScript **5.9.3** du checkout dataviz, énumère les exports via `checker.getExportsOfModule`, puis compare les noms à un parcours **indépendant de l'AST** : déclarations exportées, types explicites, aliases, imports réexportés localement, étoiles transitives et namespaces. Les doubles chemins vers un même symbole, par exemple `BOX_SHAPE_CODE`, sont rapprochés par origine. Les **118 defaults Svelte** et les exports nommés des blocs `<script module>` sont traités explicitement. Aucun namespace exporté n'a été trouvé. Un nouveau sous-chemin public non cartographié fait échouer la vérification : il n'est pas ignoré.

Les chemins locaux sont surchargeables par `GRAPHIFY_SOURCE_ROOT`, `DATAVIZ_SOURCE_ROOT` et `SOURCE_MAP_TYPESCRIPT`. `--write` régénère uniquement l'inventaire JSON adjacent ; la commande sans option vérifie la correspondance enregistrée. Le script ne modifie ni les sources lues, ni Track. Les deux repos sources et TypeScript doivent être accessibles pour rejouer la preuve.

**Résultat mesuré :** 3 547 noms côté checker = 3 547 côté AST ; 0 destination absente ; 0 couple dupliqué. La preuve couvre les **surfaces source**. Les suites runtime, builds, tarballs et artefacts actuellement publiés n'ont pas été exécutés/comparés dans cette sous-tâche : conformité de distribution = `unverified`, à prouver en M1.

## 8. Rapprochement Track et limites de ce livrable

Les six clés M1 sont stables, une par package et propriétaire d'exécution. Chaque alias core dans un adaptateur porte comme dépendance `GD-M1-DATAVIZ-CORE`. Les capacités hors package utilisent `GD-M2-PROCESSING`, `GD-M2-WORKERS`, `GD-M6-GRAPHIFY`. Le programme doit compléter les items existants, puis seulement en créer si nécessaire. **Cette sous-tâche n'écrit pas Track.** Les IDs réels, propriétaires et état de synchronisation sont fournis par le checkpoint / manifest de replay du programme.

Restant après cette preuve M0 : transférer réellement source/tests/doc/distribution (M1), exécuter les preuves d'import/types/build/packaging/consommateurs, définir les frontières M2 et traiter le moteur force/worker hors package, puis basculer les consommateurs et retirer les copies actives en M6. Un nom cartographié ou un build réussi ne prouve ni la conformité métier, ni l'adoption d'un consommateur.
